# 复核结果合同

<!-- devflow-plan-authority:v1 -->
## 指定计划为执行依据，禁止执行模型另建计划

本节约束执行角色，不禁止经授权的规划角色首次制定计划或正式修订计划。用户指定/批准的原计划及正式引用的设计、整改版本共同构成执行依据；原有用户指令及后续明确范围变更继续有效。

执行模型必须完整读取原文并保留路径、现有版本/hash和任务/验收编号。禁止额外创建、重写或更新 implementation_plan.md、客户端计划工件、局部实施计划或其他替代方案，再按自己的版本开发。即使同一工具/模型兼任规划和执行，当前执行角色也不能自行转为规划角色、自行批准改写。

只允许维护标明“执行进度（非计划）”的事实记录：原编号/章节→实际实现→测试情况→当前状态/未完成原因。不重定义设计或任务，不把记录作为新的执行依据。

发现原文不可实施或存在设计冲突时，执行模型提交原章节、代码证据和受影响条目，暂停受阻部分，交规划模型修订原计划的正式版本。

## 并行审查与汇总

主审按模块、调用链或风险边界，将互不依赖的审查范围分派给多个子 Agent 并行处理，明确原需求/计划依据、负责范围及相邻接口。每个审查 Agent 都只读，只检查当前代码的功能实现遗漏、正确性、异常与边界、并发、事务、权限、安全及可维护性，不追查执行模型声明的事情是否做过，也不重复运行测试。

主审汇总并去重发现，核清共因、意见冲突和跨模块交互，补查未覆盖的关联后，统一输出代码质量结论和可执行修复意见。不得让无依赖的模块按固定次序串行审查，不将子 Agent 的每条发现分别派发成整改轮次，也不重新逐项重复其已完成的审查。并发能力有限时分批并行；只剩一个独立范围时可单目标处理，无法创建子 Agent 时如实说明能力限制。

审查侧状态仅需“质量通过 / 需要修改 / 需用户输入”。问题和修复说明以正文为主，可附文件与行号，不强制逐项算法、测试或证据 schema。记录读过什么可选，不作为放行证明。两阶段审查、独立计数与连续三次整改后接管均保持原流程；平台不校验子 Agent 数量、分工证明或审查材料完整度。

默认接受执行模型已完成自测的说明。不要求 tests_validity_checked、coverage 全真、逐文件账本、原始报告、宿主调用或自查证明。不为这些材料提出补测整改。阅读测试源码以理解接口不等于开展测试审计；原计划用于判断当前实现是否遗漏或错误，不用于核查执行过程的声明。

每项问题提供位置、原因、影响和可执行修复意见，并区分确认缺陷、误报、历史问题和非必需建议。原范围内修复直接发送代码审查意见，免于重新生成全量 Plan。只有缺少必要用户决策时列出待确认问题。不得在未知情况下编造确定方案。

通过时给出质量通过结论。复核者只读，服务端负责路由。功能效果由用户实际确认，不能把质量通过改写成人工验收通过。

repair 意见还应满足 [整改文档合同](repair-document-contract.md)：有依据的代码问题和可执行修复意见，设计深度按问题复杂度。

职责、主链路、两阶段计数与三次接管见 [职责与调度](../../devflow/references/role-and-schedule.md)。
