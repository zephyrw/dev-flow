# 复核结果合同

<!-- devflow-plan-authority:v1 -->
## 指定计划为执行依据，禁止执行模型另建计划

用户指定/批准的原计划及正式引用继续作为执行依据。恢复、审批、普通修复和质量整改不能覆盖原计划；明确授权的范围变化在原文中补充，不另建版本或副本。

完整读取原文并保留原路径和任务/验收编号。禁止另建 implementation_plan.md、客户端计划工件或局部实施计划替代原文。同一模型兼任多个角色也不能自行批准改变范围。

允许在原计划更新 checkbox、事实状态和问题说明；只有实际完成才将 `[ ]` 改为 `[x]`，已派发、阶段推进或声明完成不等于完成。已有过程记录可引用原编号说明实际结果，不重新定义计划。

原文确有不可实施的设计冲突时，提交原章节、代码事实和影响，只暂停受阻部分，由规划角色在保留原文的基础上补充必要说明；范围改变需明确授权，普通修复不重新规划。

## 审查范围与边界

审查基准是用户当前需求、已批准设计及本次实际变更。真实 diff 是入口，但不能漏掉“需求要求实现却根本未写入 diff”的代码缺失。阅读未修改的调用方、被调用方和共享模块，只为判断本次实现是否正确及影响范围。不得以审查为由开展全仓治理或处理无关历史问题。

主审按模块、调用链或风险边界，将互不依赖的审查范围分派给多个子 Agent 并行处理，明确原需求/计划依据、负责范围及相邻接口。每个审查 Agent 都只读，只检查当前代码的功能实现遗漏、正确性、异常与边界、并发、事务、权限、安全及可维护性，不追查执行模型声明的事情是否做过，不要求新增测试证明工具，也不重复运行测试。

主审汇总并去重发现，核清共因、意见冲突和跨模块交互，补查未覆盖的关联后，统一输出代码质量结论和可执行修复意见。不得让无依赖的模块按固定次序串行审查，不将子 Agent 的每条发现分别派发成整改轮次，也不重新逐项重复其已完成的审查。并发能力有限时分批并行；只剩一个独立范围时可单目标处理，无法创建子 Agent 时如实说明能力限制。

审查侧状态仅需“质量通过（passed） / 需要修改（changes_required） / 需用户输入（need_user）”。每个阻塞问题在正文中说明代码具体位置、触发条件、原因、后果、与本次需求或变更的关系及最小修复意见。策略 2：人工前执行质量整改一次，第二次复核仍有问题由规划模型直接修复；人工后有问题直接规划修复。平台不校验子 Agent 数量、分工证明或审查材料完整度。

默认接受执行模型已完成自测的说明。严格禁止核验测试真实性、报告日志、时间戳、用例账本或自查证明，禁止要求新增脚本、探针、校验器等证明工具。阅读测试源码仅用于理解接口及代码行为，测试源码中的代码错误按代码问题指出；不得据此开展覆盖率、测试真实性或流程审计。需求分支没有实现属于代码问题；缺测试报告、缺测试用例或无法证明执行过不构成本次代码审核不通过的理由。

历史报告、旧整改文本和完成声明仅作为历史背景，不自动产生新的审核职责；旧整改中的测试证明工具要求不继续执行，已存在的证明工具运行失败不能推导业务代码不通过。每项问题区分确认缺陷、误报、历史问题和非必需建议；非必需建议仅放入可选 notes，不阻塞通过。无确认的相关代码问题时直接给出通过结论。

通过时给出质量通过结论。复核者只读，服务端负责路由。功能效果由用户实际确认，不能把质量通过改写成人工验收通过。

repair 意见还应满足 [整改文档合同](repair-document-contract.md)：有依据的代码问题和可执行修复意见，设计深度按问题复杂度。
