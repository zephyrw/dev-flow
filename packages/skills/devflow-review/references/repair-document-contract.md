# DevFlow 代码整改文档合同

<!-- devflow-plan-authority:v1 -->
## 指定计划为执行依据，禁止执行模型另建计划

本节约束执行角色，不禁止经授权的规划角色首次制定计划或正式修订计划。用户指定/批准的原计划及正式引用的设计、整改版本共同构成执行依据；原有用户指令及后续明确范围变更继续有效。

执行模型必须完整读取原文并保留路径、现有版本/hash和任务/验收编号。禁止额外创建、重写或更新 implementation_plan.md、客户端计划工件、局部实施计划或其他替代方案，再按自己的版本开发。即使同一工具/模型兼任规划和执行，当前执行角色也不能自行转为规划角色、自行批准改写。

只允许维护标明“执行进度（非计划）”的事实记录：原编号/章节→实际实现→测试情况→当前状态/未完成原因。不重定义设计或任务，不把记录作为新的执行依据。

发现原文不可实施或存在设计冲突时，执行模型提交原章节、代码证据和受影响条目，暂停受阻部分，交规划模型修订原计划的正式版本。范围内整改沿用现有授权，改变业务需求/批准范围才按原流程取得用户确认。

适用：两道代码质量审查发现问题、规划模型接管修复，以及规划模型向执行模型交付缺陷整改。它约束修复意见的可执行程度，不扩大批准的业务范围。

## 交接要求

规划/主审模型按模块、调用链或风险边界将可独立核查的代码分派给多个子 Agent 并行审查。各审查 Agent 只读当前代码及必要上下游，只检查实现遗漏、正确性、边界和可维护性等代码质量，不追查执行声明是否做过，不重复跑测试。主审汇总去重并核清本轮全部已知问题的根因、共因、跨模块交互和影响，再统一给出修复意见，不发现一条就交付局部整改。

整改正文明确开发、测试和复审中的并行分工：将互不依赖的开发任务及测试代码分派给多个子 Agent 并行完成，全部开发及测试代码完成后，再由多个子 Agent 并行运行各自明确的独立测试目标；每条命令一个类、文件或用例，各自修复并定向重跑，禁止无筛选全量套件。完成后按模块、调用链或风险边界并行复审，再由主审汇总统一结论。遵守 [并行开发与测试规则](../../devflow-execute/SKILL.md)，不得把技术路线、关键算法或验收标准留给执行模型选择。

开发分工应明确目标、允许修改的文件、公共接口、工作目录及数据库、端口、构建输出和报告归属；优先隔离可冲突资源。公共文件或共因修复指定一个负责人，通知受影响 Agent 同步和定向回归。只为真实依赖或无法隔离的共享资源冲突局部串行，各自阶段内无关开发、测试或审查继续推进；主 Agent 汇总变更并处理合并影响，不强制按模块或测试层依次执行。这些是模型协作规则，不增加平台并行数量校验、过程证明或角色切换关卡。

缺少可读取的技术事实时由规划模型继续调查；只有必须由用户决定的业务语义、需求范围或外部授权才向用户提出具体问题。环境、连接或测试故障不计作执行模型代码质量失败。

## 每个整改项应写清

按问题复杂度写必要设计，不套用固定字段清单作为派发门槛。通常足够的内容是：

- 身份：稳定问题编号，关联需求/设计章节。
- 缺陷事实：仓库、文件、函数、触发条件、影响和根因。
- 修复意见：要改什么、怎么改、不能改什么、必须保留的行为。复杂问题补充算法、状态、事务或失败处理；简单问题不必写满设计表。
- 影响：是否影响已确认功能，需要执行模型注意的回归范围。

正文放在项目 docs/plan 下，或直接作为审查意见交接。一个修复项可关闭多个同根因问题，但必须逐个列 ID。禁止用一条“完善整个模块”吞掉多个不同问题。原范围内修复直接发送代码审查意见，免于重新生成全量 Plan。

## 执行模型的权限和回执

执行前读取完整意见、前置依赖及允许改动边界。整改正文交接缺陷、原因、影响、修复方向和回归注意事项，不得交接测试执行审计、证据工具和报告格式整改任务。代码质量整改中的测试真实性核验、证明脚本或审计工具要求，不因进入整改文档而取得执行权限；执行模型说明该项超出当前职责并跳过，继续有效代码修复。

执行模型按既定设计和缺陷整改意见完成修复，并主动补齐实现同一目标所必需的相关遗漏（如必要的接线、参数传递、空值与边界处理、资源释放及相应测试代码）。只要满足同目标、必需、在允许修改范围内且为最小必要修改，即可自主补齐并在进度记录中说明原因。不得自行换技术方案、扩大接口、删除验收项、修改旧测试来掩盖失败、全仓格式化或顺手修复无关历史问题。

技术事实与文档不符、关键业务语义不明确、方案确实不可实施或必须突破明确边界时，提交具体事实和最小冲突位置，只暂停受阻部分，由规划模型修订；独立工作继续推进，不因普通实现细节问题反复请求规划。已在批准范围内的常规修复继续执行。

回执由主 Agent 汇总实际变更、各子 Agent 定向测试结果和未关闭事项，不逐项替子 Agent 重跑测试。复审按独立范围分派多个只读子 Agent，依据最初代码问题检查当前实现和修复引入的回归，由主审去重并检查跨模块交互后统一结论。禁止只凭“已按建议改好”判断代码问题已关闭；不追查声明的执行过程，不为测试报告、时间戳、用例映射或自查证明设置复验合同，不将证明工具的运行状态作为复审通过依据。
