## 指定计划为执行依据，禁止执行模型另建计划

本节约束执行角色，不禁止经授权的规划角色首次制定计划或正式修订计划。用户指定/批准的原计划及正式引用的设计、整改版本共同构成执行依据；原有用户指令及后续明确范围变更继续有效。

执行模型必须完整读取原文并保留路径、现有版本/hash和任务/验收编号。禁止额外创建、重写或更新 implementation_plan.md、客户端计划工件、局部实施计划或其他替代方案，再按自己的版本开发；禁止把“细化”“重新组织”“先做核心”作为缩减原范围、接口链路、依赖顺序和验收条件的理由。即使同一工具/模型兼任规划和执行，当前执行角色也不能自行转为规划角色、自行批准改写。

只允许维护标明“执行进度（非计划）”的事实记录：原编号/章节→实际实现→原始测试证据→当前状态/未完成原因。不重定义设计或任务，不把记录作为新的执行依据。客户端自动产生的计划工件不自动取得授权，不能据其替代原文。

发现原文不可实施或存在设计冲突时，执行模型提交原章节、代码证据和受影响条目，暂停受阻部分，交规划模型修订原计划的正式版本；不受影响的既定工作可继续。范围内整改沿用现有授权，改变业务需求/批准范围才按原流程取得用户确认。审查和交付始终逐项核对原计划完整要求；替代清单全勾选或旧反例不再命中不能作为完成证据。

适用：两道代码质量审查发现问题、规划模型接管修复，以及规划模型向执行模型交付缺陷整改。它约束修复任务的确定程度，不扩大批准的业务范围，也不以文字承诺代替修复后的复验。

## 交接前必须确定

规划模型先完整读取当前代码、相关上下游及已有日志和报告，核清本轮全部已知问题的根因、共因和影响，再给出唯一完整修复设计。完成全范围核查后统一派发，不发现一条就交付局部整改。执行模型核对整份整改并完成全部修改和测试代码后统一运行测试，遵守 [完整开发、整批修复后统一测试](../../devflow-execute/SKILL.md)。不得把技术路线、关键算法、状态迁移、接口字段、数据处理或验收标准留给执行模型选择。不能用“自行优化”“按最佳实践”“补齐测试”“类似处理其他地方”代替完整说明。

缺少可读取的技术事实时由规划模型继续调查；只有必须由用户决定的业务语义、需求范围或外部授权才向用户提出具体问题。在答案确定前返回 incomplete，不派发带未决项的整改任务。环境或证据缺失不计作执行模型代码质量失败。

## 每个整改项的必填内容

| 内容 | 必须达到的精度 |
| --- | --- |
| 身份与依据 | 稳定 finding_id、repair_item_id，工作流、审查阶段、交付修订、计划修订、输入指纹、反馈游标；关联需求/设计章节。 |
| 缺陷事实 | 仓库、文件、函数/符号、审查时行号、触发条件、最小复现步骤、预期与实际、原始证据位置、影响和根因；区分已复现与静态确认。 |
| 唯一修复设计 | 明确输入输出、字段/类型、校验、算法、状态前后关系、事务与锁边界、幂等键、失败/超时/重启处理；不适用的字段注明理由。不能只有原则。 |
| 修改边界 | 逐项列出允许修改/新增/删除的仓库相对文件及函数、每处目的；列出禁止改动项和必须保留行为。禁止通配“相关文件”。 |
| 实施顺序 | 有序步骤及依赖，每步写明要改什么、前置条件、完成产物和下一步触发条件；必要时给关键伪代码或明确代码片段。 |
| 验证合同 | 稳定场景 ID、测试层、数据、实际操作、预期断言、缺陷修复前失败点、修复后结果；覆盖正向、负向、异常/并发/恢复中适用的分支。 |
| 回归与功能影响 | 沿真实调用链列出受影响旧功能和所需单元/集成/E2E 回归；说明是否影响人工已确认场景，不能无依据写“无影响”。 |
| 完成与停止条件 | 逐条关闭所需的代码证据/原始报告/验证命令，何种事实冲突必须交还规划模型，不能执行的动作；明确所有问题都需有对应处置。 |

正文放在项目 docs/plan 下，采用当前已批准文档版本规则；结构化 repair_plan 的每项必须引用同一正文版本和对应 finding_id。一个修复项可关闭多个同根因问题，但必须逐个列 ID 并各自验收。禁止用一条“完善整个模块”吞掉多个不同问题。

## 执行模型的权限和回执

执行前读取完整正文、当前版本、前置依赖及允许改动边界。执行模型只决定不影响设计与行为的局部写法，不得自行换技术方案、扩大接口、删除验收项、修改旧测试来掩盖失败、全仓格式化或顺手重构。

技术事实与文档不符、必需文件/接口不存在、明确方案不能成立或必须超出边界时，提交具体事实和最小冲突位置，由规划模型修订完整整改文档；不能猜测另一方案，也不因普通实现问题重复请求用户批准。已在批准范围内的常规修复继续执行。

回执逐项列 repair_item_id → 实际变更文件/函数 → 原始测试和报告 → 尚未关闭事项。复审者按最初缺陷复现和验收合同复验，同时检查修复引入的回归。禁止以“已按建议改好”或测试数量代替逐项关闭。

## 派发门槛

changes_required 只有在阻塞问题都有完整修复项、所有引用与版本一致、必填字段齐全且不存在未决设计时，才允许自动派发执行。文档不完整须由规划模型补全，不先派发，也不增加执行模型拒绝计数。

结构校验只能证明字段齐全；规划模型仍须证明设计来自真实代码、根因正确、步骤可实施。不能宣称任何文档能数学上保证一次修复全部问题。要求是交接时设计确定、执行后证据充分、原问题与回归逐项复验通过。

## 程序调度的正式计划逐项复核

native-v2 每轮初始开发、正式整改或用户反馈修复完成后，执行顺序固定为：完整开发 → 统一测试 → 交付核验及执行成功退出 → 程序再次调起执行模型对照正式计划逐项复核 → 核清全部遗漏/偏离的根因、整批修复后统一测试、交付核验及成功退出 → 规划模型独立代码质量审查。不得直接开放人工核验或把首次完成自述当成这次复核。人工核验前的质量审查通过后才交用户；人工核验后的整改也不能跳过执行复核。

复核必须重新读原始计划及当前正式批准的整改/修订全文，按原编号关联真实实现、测试和未完成项。使用 AUTHORITATIVE_PLANS.json、HANDOFF.md 与 handoff.json 中程序给出的版本及 self_check.check_ids；正式范围变更引用对应批准修订。禁止创建或使用 implementation_plan.md、客户端计划工件或其他局部计划替代原文。逐项报告属于执行事实记录，不是另一份实施计划。

当前复核轮次的交付清单必须包含 plan_self_check，并符合 plan-self-check.schema.json：绑定请求、源交付、当前 run_id、plan_revision、plan_hash、authority_hash；完整覆盖全部 check_ids，逐项提供代码/测试报告/用例定位，记录发现问题及实际修复证据。遗漏、重复编号、空证据、未解决问题、旧轮次/旧计划/旧输入报告、进程失败均阻断规划审查；代码改动后提交当前轮次有效测试与新交付。正常开发轮次不能自行填报告冒充程序调度。

程序校验报告及当前交付的绑定和完整性，不能保证模型判断语义正确；规划模型仍须独立检查实际代码、测试真实性与原计划覆盖。缺少本轮有效自查报告不得放行。自查不计入任何质量关卡的三次拒绝次数；暂停/停止后不得自行继续，不新增后台轮询，不改变既有界面布局。
