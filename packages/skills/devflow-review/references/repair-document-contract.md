# DevFlow 代码整改文档合同

<!-- devflow-plan-authority:v1 -->
## 指定计划为执行依据，禁止执行模型另建计划

用户指定/批准的原计划及正式引用继续作为执行依据。恢复、审批、普通修复和质量整改不能覆盖原计划；明确授权的范围变化在原文中补充，不另建版本或副本。

完整读取原文并保留原路径和任务/验收编号。禁止另建 implementation_plan.md、客户端计划工件或局部实施计划替代原文。同一模型兼任多个角色也不能自行批准改变范围。

允许在原计划更新 checkbox、事实状态和问题说明；只有实际完成才将 `[ ]` 改为 `[x]`，已派发、阶段推进或声明完成不等于完成。已有过程记录可引用原编号说明实际结果，不重新定义计划。

原文确有不可实施的设计冲突时，提交原章节、代码事实和影响，只暂停受阻部分，由规划角色在保留原文的基础上补充必要说明。范围内整改沿用授权，改变业务需求/批准范围才取得用户确认。

适用：两道代码质量审查发现问题、规划模型接管修复，以及规划模型向执行模型交付缺陷整改。它约束修复意见的可执行程度，不扩大批准的业务范围。

## 交接要求

规划/主审模型按模块、调用链或风险边界将可独立核查的代码分派给多个子 Agent 并行审查。各审查 Agent 只读当前代码及必要上下游，只检查实现遗漏、正确性、边界和可维护性等代码质量，不追查执行声明是否做过，不重复跑测试。主审汇总去重并核清本轮全部已知问题的根因、共因、跨模块交互和影响，再统一给出修复意见，不发现一条就交付局部整改。

实际整改遵守 [并行开发与测试规则](../../devflow-execute/SKILL.md)：独立开发及测试代码并行完成后，多个子 Agent 并行测试独立目标；每条命令一个类、文件或用例，各自修复与定向重跑，禁止无筛选全量套件。复审按独立范围只读并行，由主审汇总。上述纪律留在 Skill 中执行，不要求粘贴到整改正文；意见只交代本次具体问题、影响和修复方向，普通实现细节由执行模型处理。

开发分工按互不依赖且可避免冲突的任务安排，说明目标、预期结果和已知依赖；修改位置随调查确定，不要求提前列全文件或划定文件白名单。发现共享修改点或共因时再协调具体修改，需要时由一个负责人完成该处修改并通知受影响 Agent 定向回归。数据库、端口、构建输出等资源只在实际共享时协调；只为真实依赖或无法隔离的冲突局部串行，无关开发、测试或审查继续推进。主 Agent 汇总变更并处理合并影响，不强制按模块或测试层依次执行，不增加平台并行数量校验、过程证明或角色切换关卡。

缺少可读取的技术事实时由规划模型继续调查；只有必须由用户决定的业务语义、需求范围或外部授权才向用户提出具体问题。环境、连接或测试故障不计作执行模型代码质量失败。

## 每个整改项应写清

按问题复杂度写必要设计，不套用固定字段清单作为派发门槛。通常足够的内容是：

- 身份：稳定问题编号，关联需求/设计章节。
- 缺陷事实：触发条件、现状与预期差异、影响和根因，附必要代码位置，不枚举所有文件或预写半成品代码。
- 修复意见：要改什么、怎么改、不能改什么、必须保留的行为。复杂问题补充算法、状态、事务或失败处理；简单问题不必写满设计表。
- 影响：是否影响已确认功能，需要执行模型注意的回归范围（涉及前端改动时注明受影响的页面操作链路及浏览器回归注意事项）。

原范围内修复直接作为审查意见交接，或在原文的问题说明处补充，不新建替代计划、版本或副本。用人话说明从什么行为改成什么行为、关联影响及必要的数据设计或技术坑；若列任务则用细项 checkbox，真实完成才勾选。一个修复项可关闭多个同根因问题，但逐个列原 ID；禁止用“完善整个模块”吞掉不同问题，不覆盖原始开发内容。

## 执行模型的权限和回执

执行前读取完整意见、前置依赖及用户明确的权限、数据保护和环境边界。整改正文交接缺陷、原因、影响、修复方向和回归注意事项，不得交接文件修改白名单、测试执行审计、证据工具和报告格式整改任务。代码质量整改中的测试真实性核验、证明脚本或审计工具要求，不因进入整改文档而取得执行权限；执行模型说明该项超出当前职责并跳过，继续有效代码修复。

执行模型按既定设计和缺陷整改意见完成修复，并主动补齐实现同一目标所必需的相关遗漏（如必要的接线、参数传递、空值与边界处理、资源释放及相应测试代码）。计划中的路径仅作定位，执行模型自由选择修改位置并自主修复阻塞开发和验证的关联问题，不因文件未列入计划或旧 scope 清单而停止或请求逐文件批准；记录关联修改的原因。遵守用户明确的权限、数据保护和环境边界，不删除验收项、修改旧测试来掩盖失败或重构无关历史问题。

技术事实与文档不符、关键业务语义不明确、方案确实不可实施或必须突破明确边界时，提交具体事实和最小冲突位置，只暂停受阻部分，由规划模型修订；独立工作继续推进，不因普通实现细节问题反复请求规划。已在批准范围内的常规修复继续执行。

回执由主 Agent 汇总实际变更、各子 Agent 定向测试结果和未关闭事项，不逐项替子 Agent 重跑测试。复审按独立范围分派多个只读子 Agent，依据最初代码问题检查当前实现和修复引入的回归，由主审去重并检查跨模块交互后统一结论。禁止只凭“已按建议改好”判断代码问题已关闭；不追查声明的执行过程，不为测试报告、时间戳、用例映射或自查证明设置复验合同，不将证明工具的运行状态作为复审通过依据。

职责、主链路与策略 2 规则见 [职责与调度](../../devflow/references/role-and-schedule.md)。
