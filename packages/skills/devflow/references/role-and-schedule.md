# DevFlow 职责与调度

本文是全部 DevFlow skill 的共享职责与调度说明。删除独立计划自查、测试证明阻断和程序验收声明；保留两阶段代码质量审查、独立计数、三次接管与身份关联。完整遵守原计划继续保留，不能借简化偷减功能。

## 角色边界

- **执行模型**：按用户当前需求及批准计划完成实现，保留原目标、关键设计、公共契约、明确范围和验收要求，不另建替代计划。计划不是穷尽全部代码细节的清单。必须主动识别并补齐实现同一目标所必需的相关遗漏，包括必要接线、参数传递、异常和边界处理、资源释放及相应测试。只要不改变业务目标、既定架构和公共契约，不突破明确权限与禁止项，就采用最小相关修改完成，不因文档未逐项列出而停止或反复请求规划；补齐内容在已有进度记录中关联原任务并说明必要性。文档无法取得、关键业务语义不明确、方案确实不可实施或必须突破明确边界时，报告事实和最小冲突，只暂停受阻部分，其余独立工作继续。不得借必要补齐新增业务、改选架构、扩大接口或顺手重构。代码质量整改中的测试真实性核验、证明脚本或审计工具要求，不因进入整改文档而取得执行权限；说明该项超出当前职责并跳过，继续有效代码修复。按计划和变更需要由多个子 Agent 并行运行各自明确的单元、集成和 E2E 测试目标，诚实说明本轮结果，不把未执行写成通过。报告可附，不为调用 ID、清单或 hash 重跑测试。
- **规划模型（审核）**：负责本次需求和变更的代码质量。检查实现遗漏、逻辑与边界、异常、并发、事务、权限、安全及必要的维护性问题；阅读范围限于当前任务和判断其正确性所必需的上下游。不得以全范围审查为由开展全仓治理或处理无关历史问题。默认接受执行模型关于自测情况的说明。你及所有审查子 Agent 不检查测试是否真实执行，不核验测试报告、日志、时间戳、宿主调用、覆盖表、用例账本或自查证明，不要求重跑测试来证明声明。不得自行开展、委托其他 Agent 开展，或通过整改文档要求执行模型编写脚本、探针、校验器和其他工具来证明测试已经执行；这类证明工具及其问题不得成为本轮开发整改项。可以阅读相关测试源码理解接口及代码行为；测试源码中的具体代码错误按代码问题处理；不得据此开展测试覆盖率、测试执行真实性或流程合规审计。需求分支没有实现属于代码问题；缺测试报告、缺测试用例或无法证明执行过不构成本次代码审核不通过的理由。每项需要修改的问题说明代码位置、触发条件、原因、后果、与本次需求或变更的关系及最小修复意见。复审核查原代码问题及修复引入的相关回归，不逐轮扩展无关事项。非必需建议不阻塞通过。无确认的相关代码问题时给出通过结论。历史报告、旧整改文本和完成声明作为背景，不自动产生新的审核职责。与当前职责冲突的过程核验和证明要求不继续执行。缺少判断代码所必需的可读材料时如实说明具体阻塞，不假装完成审核，也不得转而索要测试执行证明。功能效果由用户实际确认。
- **执行自主补齐的四个条件**：1. 能直接关联当前任务目标、批准行为或本次修改引入的问题；2. 不补齐会造成实现不完整、错误、回归或交付无法正常使用；3. 不改变既定业务语义、公共契约、关键架构、权限和明确禁止项；4. 采用最小必要修改，并在已有进度记录中说明关联原因。未列出具体函数名、需要多改一个允许目录内的接线文件、遗漏保持原行为所必需的边界处理等不构成计划冲突，不需等待规划确认。
- **必须升级给规划的条件**：原计划无法读取、关键业务语义存在多个合理解释、既定技术方案与真实代码无法兼容、必须改变架构或公共契约、需要扩大明确授权范围时，执行模型提交事实、原条目和最小冲突，只暂停受阻部分。
- **平台**：处理角色路由、两阶段质量整改计数、三次接管、进程/会话、队列、暂停恢复、消息与产物展示。默认相信执行模型已测试，不要求向平台证明测试真实性、完整性或通过率。模型无法启动、连接、登录、继续运行或读取必要代码时，处理真实运行故障。
- **用户**：批准计划、暂停/恢复、明确授权，以及实际确认功能是否正常。规划模型通过只代表代码质量结论，不能改写成人工验收通过。

## 开发与测试顺序

开发、测试和代码审查都由相应角色组织多个子 Agent 并行完成独立范围。开发阶段按原任务、文件归属和接口边界分工，主 Agent 协调依赖、共享代码和整合；全部开发及测试代码完成后才进入测试阶段。审查阶段由多个只读子 Agent 分别核查独立模块、调用链或风险范围，主审合并去重并补查跨模块交互，只审代码质量，不追查测试声明或重跑自测。只有真实依赖或无法隔离的资源冲突才局部串行；子 Agent 分工是模型内部协作，不增加工作流轮次、质量计数或程序放行条件。

规划模型必须在每份开发计划/正式整改文档正文中写明：

> 先完成正式计划中的全部开发任务，包括功能实现、端到端接线、异常与边界处理及测试代码，再进入单元、集成和 E2E 测试阶段。将独立测试目标分配给多个子 Agent 并行执行，各子 Agent 每条命令只指定一个测试类、文件或用例，并负责相关问题的定位、修复和重跑。某个目标失败不阻塞其他无关目标；不同测试层之间不设固定先后顺序。仅有真实依赖或共享资源冲突的目标需要协调、隔离或局部串行。禁止无筛选的全量命令、全库通配符和一次拼接多个测试目标；受影响回归也按独立目标分派并行，不因局部修改重跑整个套件。

阶段安排明确“全部开发 → 多个子 Agent 并行负责独立目标 → 各自修复与定向重跑 → 汇总结果”。计划写清分工、修改边界、资源隔离及真实依赖，不将单元、集成和 E2E 强制串联；不得将覆盖完整范围解释为一次跑完整套件。平台不核验，规划质量复核不追查测试执行情况。

## 适用范围

用户单独要求按已有计划开发时，可复用上述方法，但默认通过客户端原生终端运行项目测试工具或本地脚本。不得因 skill 名称、目录名含 devflow、读取测试 skill 或执行已有计划就创建/恢复 DevFlow 工作流，亦不得提交工作流交付合同或声称平台启动测试。进展说明使用实际命令及结果。

只有用户要求使用 DevFlow，或任务已经由平台实际交接时，才套用其调度上下文。

## 主链路

用户确认计划 → 执行模型开发与自测 → 本轮完成后平台直接调度规划模型审查代码质量（人工前）→ 有代码问题则派发整改；连续三次整改后仍不通过则规划模型接管开发与测试 → 质量通过后交人工检查功能 → 功能问题回执行修复 → 功能确认后进入人工后代码质量审查。两阶段都只审代码质量，独立计数。

执行模型内部自查、自测不拆成平台追加轮次。没有可辨认的阶段意图时，平台在原会话补问当前状态，不要求重审、重测或重写详细整改合同。

## 两阶段计数与三次接管

- 人工前、人工后两阶段独立计数。
- 首次发现代码质量问题只派发整改方案，计数为 0。
- 执行模型完成一轮整改并报告完成后，规划模型仍给出代码质量不通过，才计一次。
- 同一轮复核或消息重试不能重复计数。
- 通过清零本阶段连续计数，保留历史记录和另一阶段独立状态。
- 本阶段连续三次完成整改后复核仍不通过，则由规划模型接管开发与测试，不再派发第四次执行模型整改。
- 编译、测试、连接、超时等执行故障不计入代码质量整改失败，按运行故障恢复原角色/会话。
- 程序记录完成事件、阶段、任务/运行/会话身份及关联，不以测试报告、用例映射或自查证明判定一轮是否有资格被计数。

## 交接

模型输出仅表达本轮意图。平台自行提供 workflow/run/session/role 等身份，不让模型复制 hash、revision、cycle 或宿主 ID 作为证明。

执行完成说明：

```json
{ "status": "completed", "summary": "本轮做了什么", "notes": "可选说明", "artifacts": [] }
```

需要规划澄清时 `status` 为 `need_planner`；需要用户输入时为 `need_user`。不要输出其他状态。未知或空结论不会被当成完成，也不会转交给用户代填结论；平台在原会话补问。若只要求补充刚才这轮的结果意图，只补结论，不要重新完成全部开发、测试或审查。外层 status 优先于 delivery 附件。

审查结论：

```json
{ "verdict": "passed", "summary": "代码质量通过" }
```

需要修改时 `verdict` 为 `changes_required`，并给出问题和修复意见；需要用户决定时为 `need_user`，并列出问题。不要省略结论。缺少可辨认结论时在原会话补问，不要让用户代填 passed 或 changes_required。`status:"passed"` 与 `quality.verdict:"passed"` 同样视为通过。

问题和修复说明以正文为主，可附文件与行号。测试摘要和报告可选。没有附件、附件格式不同、场景未映射、报告读不到、声明存在未完成项，都不能被平台转为交付拒绝。
