# 职责与调度（quality_policy_version = 2）

本文是全部 DevFlow skill 的共享职责与调度说明。**策略 2 已取代“两阶段独立计数 / 连续三次整改后接管”。** 平台只按模型明确结果和人的明确操作安排下一项工作，不判断结果是否真实。

## 核心原则

DevFlow 是极轻量调度和展示工具，不参与任何代码、功能、测试、整改报告或交付证据校验。

## 完整主链路

用户确认计划 → 执行模型开发与自测 → 规划模型首次代码质量复核 → 有问题则执行质量整改**一次**并自测 → 规划模型再次复核 → 仍有问题则**规划模型直接修代码（不跑测试）** → 执行模型测试（可修测试期间相关小问题）→ **测试完成后不再复核**：人工前直接交人工审核；人工后直接规划提交 → 人工功能审核 → 功能问题回执行修复并测试，再回人工 → 人工确认后最终质量复核 → 有问题由规划模型直接修复 → 执行测试 → **直接规划模型实际 git commit** → 原有本地集成收尾。

## 角色职责

| 用途 | 角色 | 改代码 | 跑测试 |
| --- | --- | --- | --- |
| planning | planner | 按规划边界 | 否 |
| implement（首次开发、首次质量整改） | executor | 是 | 是 |
| quality_review | planner | 本轮只复核 | 否 |
| planner_takeover（规划质量修复） | planner | 是 | **否** |
| executor_test | executor | 可修测试暴露的相关问题 | **是** |
| functional_fix | executor | 是 | 是 |
| planner_commit | planner | 本轮只提交，不顺手修代码 | 否 |

- **规划复核**：只判断本任务相关代码质量；默认接受自测说明；不核验测试真实性；无必需修改的问题就通过；首次失败给可执行的详细整改报告。
- **规划修复**：修复后阅读代码自查；不运行测试/构建/lint/typecheck；可改相关测试源码。
- **执行测试**：跑必要测试；修复测试暴露的本任务相关小问题并重测；完成后直接交人工或规划提交；不请求新一轮规划复核。
- **规划提交**：只暂存并提交本任务代码；不顺手修代码；不主动跑测试；严禁将 worktree 的临时端口配置、本地数据库或临时实例文件暂存或提交。

## 确定规则

1. 人工前一旦进入规划接管，当前质量报告由规划模型修复，不退回执行质量整改。
2. 人工后有问题直接规划修，不套用人工前一次机会。
3. 测试阶段不是只读；执行模型可修复测试暴露的本任务相关问题并重测。
4. 测试期间的相关小修改**不复核**；测完按 phase 直达人工或规划提交。
5. 规划修复后的执行测试完成，即使改了代码也不追加规划复核或人工重确认。
6. 功能修复必须回人工；人确认全部问题修复后才进入最终质量复核。
7. 最终测试完成直接规划提交；提交轮不顺手改代码，且检查并排除临时 worktree 配置。
8. 说明材料不驱动额外关卡；平台不扫描 diff 或文件数判定“再审一次”。
9. DevFlow 不校验测试真实性、证据、覆盖率；不要求证明脚本。
10. 新增业务另走原需求变更机制。
11. 涉及前端影响的任务，执行测试职责包含 OpenTabs 仿人工真实浏览器核验。确需用户真实登录或回答问题时，模型输出 need_user 并附带 user_interaction 交互请求，系统暂停本轮等待用户输入，用户确认后续接原上下文；这属于既有的 need_user 机制，不新增工作流状态或平台测试关卡。

## 平台职责

平台处理角色路由、阶段、会话归属、队列、暂停恢复和状态保存。默认相信执行模型已测试，不要求向平台证明测试真实性。模型无法启动、连接、登录或读取必要代码时，处理真实运行故障。
