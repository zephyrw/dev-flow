# DevFlow 统一入口

用户只负责表达需求、回答必要业务问题、批准图解计划和实操验收。不要让用户选择内部 Skill、填写 JSON、执行接入命令或粘贴长提示词。

## 先识别上下文

1. 使用当前任务的真实工作目录；读取项目规则。获取真实会话 ID（环境 `CODEX_THREAD_ID` 可用时）；没有则省略，不编造。
2. 用户明确要求新 worktree 时设 `new_worktree`；明确使用当前目录时设 `existing_workspace`；未指定默认新 worktree，在计划里说明。
3. 问题排查、复杂任务标记 `complex`；普通局部修改为 `simple`。使用新的幂等键，网络重试复用同一个键。
4. 调用 `devflow_start`，传入需求原文、简短标题和以上上下文。用户明确新需求用 `intent=new`，明确继续用 `continue`，其余 `auto`。同一轮已获得工作流 ID 时后续调用携带它；不要重新建任务。

## 按返回结果继续，不让用户手动串工具

| next_action | 你需要做的事 |
|---|---|
| onboard | 读取同级 `../devflow-project-onboard/SKILL.md`。调查代码、生成运行配置和三层测试合同，调用 `devflow_register_project`。然后再次调用入口，为原需求写计划。最小端口/健康检查适配并入本次批准计划；此时不启动项目。 |
| plan | 读取 `../devflow-plan/SKILL.md` 及其合同参考。复用入口返回的工作流、项目哈希、仓库路径和基线；完成调查、必要澄清及图解计划，再提交审批。 |
| open_workflow | 用普通话说明当前阶段，提供返回的控制台链接。不要轮询。用户要修改计划时读取现有计划和版本，按规划规范修订后重新审批；执行中要求先在控制台停止。 |
| select_project / select_workflow | 按可读项目名/任务名请用户澄清，不能选“最近一次”。 |
| prepare_repository | 根据目录实际状态补齐 Git 前提；不要为了建基线擅自提交用户已有业务修改。 |

交接只说：“计划已提交，打开这个链接看图并批准。”不要求用户理解 hash、revision、MCP 或模型会话编号。

## 固定行为

- 所有程序使用当前 Windows 用户及已有 agy/Codex 登录；绝不创建用户、切换用户或配置账户 ACL。
- 启动由本地 MCP 桥接器自动完成。首次安装后若入口不可用，说明需重启 Codex 加载配置；不要假装已经调用服务。
- GPT-6 调研及独立复核；Gemini 执行和测试。计划批准前不开发；Gemini 执行后不让 GPT-6 监工。
- 复杂任务三文档，普通任务一文档；图解优先，计划没有未决项或执行者自选方案。
- 修改范围最小；按 `../devflow-test/SKILL.md` 覆盖单元、集成、E2E 三层。E2E 覆盖新需求全部流程和受影响旧功能回归；Web E2E 使用真实浏览器，不另设浏览器验收层。不适用项写明原因并审批，人工功能确认保留。
- 人工验收后服务触发独立复核；通过自动本地提交，有问题生成修复计划再审批；发布只接受用户另行指令。
- 用户明确暂停测试时立即停下测试，不用历史证据证明新改动通过。
