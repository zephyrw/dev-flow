## 指定计划为执行依据，禁止执行模型另建计划

收到“按某计划/整改文档完整执行”时，保留用户指定原文及其正式引用，不将其当作需要重新规划的新需求，也不因客户端习惯先生成 implementation_plan.md。执行阶段使用 devflow-execute 的规则：执行模型不得额外创建实施计划或以自写摘要、局部整改方案替代原计划；进度清单只能逐项引用原编号，不改变范围或验收。

只有首次需求尚无确定计划，或用户明确要求重新规划、流程正式交给规划角色修订时，才进入规划。已有计划如需登记/接入，复用原文和版本；发现冲突交规划模型修订，不能由执行模型自行换方案。相同工具/模型也必须遵守当前角色边界。

# DevFlow 统一入口

用户只负责表达需求、回答必要业务问题、批准图解计划和实操验收。不要让用户选择内部 Skill、填写 JSON、执行接入命令或粘贴长提示词。

## 先识别上下文

1. 使用当前任务的真实工作目录；读取项目规则。获取真实会话 ID（环境 `CODEX_THREAD_ID` 可用时）；没有则省略，不编造。
2. 用户明确要求新 worktree 时设 `new_worktree`；明确使用当前目录时设 `existing_workspace`；未指定默认新 worktree，在计划里说明。
3. 问题排查、复杂任务标记 `complex`；普通局部修改为 `simple`。使用新的幂等键，网络重试复用同一个键。
4. 对用户明确提出且尚无正式计划的新任务，先读取 `devflow_list_tool_profiles`，复用用户配置的规划/执行 Profile，调用 `devflow_create_native_task` 传入真实仓库根目录、完整需求、引用、工作区模式及幂等键；规划由程序调度，返回控制台链接。配置不明确先澄清，不硬编码模型。已有工作流或已有指定计划需要接入时调用 `devflow_start`，传入需求原文、简短标题和以上上下文。用户明确新需求用 `intent=new`，明确继续用 `continue`，其余 `auto`。同一轮已获得工作流 ID 时后续调用携带它；不要重新建任务。

## 按返回结果继续，不让用户手动串工具

| next_action | 你需要做的事 |
|---|---|
| onboard | 读取同级 `../devflow-project-onboard/SKILL.md`。调查代码、生成运行配置和三层测试合同，调用 `devflow_register_project`。然后再次调用入口，为原需求写计划。最小端口/健康检查适配并入本次批准计划；此时不启动项目。 |
| plan | 读取 `../devflow-plan/SKILL.md` 及其合同参考。复用入口返回的工作流、项目哈希、仓库路径和基线；完成调查、必要澄清及图解计划，再提交审批。 |
| open_workflow | 用普通话说明当前阶段，提供返回的控制台链接。不要轮询。用户要修改计划时读取现有计划和版本，按规划规范修订后重新审批；执行中要求先在控制台停止。 |
| select_project / select_workflow | 按可读项目名/任务名请用户澄清，不能选“最近一次”。 |
| prepare_repository | 根据目录实际状态补齐 Git 前提；不要为了建基线擅自提交用户已有业务修改。 |

交接只说：“计划已提交，打开这个链接看图并批准。”不要求用户理解 hash、revision、MCP 或模型会话编号。

## 固定行为

- 所有程序使用当前操作系统用户及所选工具已有登录；绝不创建用户、切换用户或配置账户 ACL。
- 启动由本地 MCP 桥接器自动完成。首次安装后若入口不可用，说明需在当前客户端重新加载 MCP 配置；不要假装已经调用服务。
- 规划、执行、自查与质量审查使用 ExecutionSpec 中冻结的 Profile；支持单工具承担全部角色及多工具协作，不固定客户端或模型。计划批准前不开发，按阶段由程序调度，不启动监工轮询。
- 复杂任务三文档，普通任务一文档；图解优先，计划没有未决项或执行者自选方案。
- 修改范围最小；按 `../devflow-test/SKILL.md` 覆盖单元、集成、E2E 三层。E2E 覆盖新需求全部流程和受影响旧功能回归；Web E2E 使用真实浏览器，不另设浏览器验收层。不适用项写明原因并审批，人工功能确认保留。
- 人工前与人工后均有程序调度的质量审查；范围内按完整正式整改计划自动修复，范围变化才重新审批。最终通过后本地提交；自有 worktree 先吸收主分支、重新验证新候选、合回成功再清理。当前工作区只提交任务变更并保留用户原有改动；推送和发布只接受用户另行指令。
- 用户明确暂停测试时立即停下测试，不用历史证据证明新改动通过。

## 程序调度的正式计划逐项复核

native-v2 每轮初始开发或正式质量整改完成后，执行顺序固定为：开发与自测 → 交付核验及成功退出 → 程序独立调度执行模型按正式计划逐项自查、修复遗漏并重测 → 规划模型独立质量审查。首轮质量通过才开放人工核验；人工功能问题修复同样必须经过程序自查，再直接交用户复测，全部功能确认后进入最终质量审查。人工前、人工后两关分别计数；各关连续三次执行模型整改仍不合格，程序调度规划模型接管修复，自查后再进入审查。不得用首次完成自述代替程序自查，不得伪造人工确认。

复核必须重新读原始计划及当前正式批准的整改/修订全文，按原编号关联真实实现、测试和未完成项。使用当前运行的 HANDOFF.json 中 authorities、check.check_ids 与 check_schema；旧入口使用 AUTHORITATIVE_PLANS.json、HANDOFF.md、handoff.json 和 self_check.check_ids，均以程序交付的真实版本为准；正式范围变更引用对应批准修订。禁止创建或使用 implementation_plan.md、客户端计划工件或其他局部计划替代原文。逐项报告属于执行事实记录，不是另一份实施计划。

当前复核轮次的交付清单必须包含 plan_self_check，并符合本轮 check_schema（旧入口为 plan-self-check.schema.json）：绑定请求、源交付、当前 run_id、plan_revision、plan_hash、authority_hash；完整覆盖全部 check_ids，逐项提供代码/测试报告/用例定位，记录发现问题及实际修复证据。遗漏、重复编号、空证据、未解决问题、旧轮次/旧计划/旧输入报告、进程失败均阻断规划审查；代码改动后提交当前轮次有效测试与新交付。正常开发轮次不能自行填报告冒充程序调度。

程序校验报告及当前交付的绑定和完整性，不能保证模型判断语义正确；规划模型仍须独立检查实际代码、测试真实性与原计划覆盖。缺少本轮有效自查报告不得放行。自查不计入任何质量关卡的三次拒绝次数；暂停/停止后不得自行继续，不新增后台轮询，不改变既有界面布局。
