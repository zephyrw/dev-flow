## 指定计划为执行依据，禁止执行模型另建计划

收到“按某计划/整改文档完整执行”时，保留用户指定原文及其正式引用，不将其当作需要重新规划的新需求，也不因客户端习惯先生成 implementation_plan.md。执行阶段使用 devflow-execute 的规则：执行模型不得额外创建实施计划或以自写摘要、局部整改方案替代原计划；但必须按计划主动补齐实现同一需求所必需的相关遗漏（接线、参数、边界、资源释放及测试），满足同目标、必需、在允许目录下且最小修改时自主完成并记录；进度清单逐项引用原编号，不改变既定目标、架构或公共契约。

首次需求没有计划时进入规划；已有计划登记、接入或恢复时直接复用原件。审批、普通修复和整改不能覆盖原计划，不另建版本或副本。关键设计冲突交规划角色说明，明确授权的范围变化在原文中补充，不能自行换方案。原文可更新 checkbox、状态和问题说明，只有实际完成才将 `[ ]` 改为 `[x]`。

# DevFlow 统一入口

用户只负责表达需求、回答必要业务问题、批准图解计划和实操验收。不要让用户选择内部 Skill、填写 JSON、执行接入命令或粘贴长提示词。

## 先识别上下文

1. 使用当前任务的真实工作目录；读取项目规则。获取真实会话 ID（环境 `CODEX_THREAD_ID` 可用时）；没有则省略，不编造。
2. 用户明确要求新 worktree 时设 `new_worktree`；明确使用当前目录时设 `existing_workspace`；未指定默认新 worktree，在计划里说明。**【Worktree 规范约束】严禁在主工作区同级或任意外部路径创建 worktree；所有独立 worktree 必须且仅能在主工作区根目录下的 `.worktrees/` 目录内创建（如 `<source_root>/.worktrees/<workflow_id>/<repo_id>` 或 `<source_root>/.worktrees/<branch_or_id>`）；严禁在主工作区直接执行切换分支等影响已有未提交工作的操作；主工作区必须确保 `.gitignore` 配置忽略 `.worktrees/`。**
3. 问题排查、复杂任务标记 `complex`；普通局部修改为 `simple`。使用新的幂等键，网络重试复用同一个键。
4. 对用户明确提出且尚无正式计划的新任务，先读取 `devflow_list_tool_profiles`，复用用户配置的规划/执行 Profile，调用 `devflow_create_native_task` 传入真实仓库根目录、完整需求、引用、工作区模式及幂等键；规划由程序调度，返回控制台链接。配置不明确先澄清，不硬编码模型。已有工作流或已有指定计划需要接入时调用 `devflow_start`，传入需求原文、简短标题和以上上下文。用户明确新需求用 `intent=new`，明确继续用 `continue`，其余 `auto`。同一轮已获得工作流 ID 时后续调用携带它；不要重新建任务。

## 按返回结果继续，不让用户手动串工具

| next_action | 你需要做的事 |
|---|---|
| onboard | 读取同级 `../devflow-project-onboard/SKILL.md`。调查代码、生成运行配置，调用 `devflow_register_project`。然后再次调用入口，为原需求写计划。最小端口/健康检查适配并入本次批准计划；此时不启动项目。 |
| plan | 读取 `../devflow-plan/SKILL.md` 及其合同参考。复用入口返回的工作流、项目哈希、仓库路径和基线；完成调查、必要澄清及图解计划，再提交审批。 |
| open_workflow | 用普通话说明当前阶段，提供返回的控制台链接，不轮询。读取现有原计划，只补充用户明确授权的变化；真正改变批准范围才按现有流程确认，普通恢复、进度勾选和范围内修复不重写计划或重新审批。 |
| select_project / select_workflow | 按可读项目名/任务名请用户澄清，不能选“最近一次”。 |
| prepare_repository | 根据目录实际状态补齐 Git 前提；不要为了建基线擅自提交用户已有业务修改。 |

交接只说：“计划已提交，打开这个链接看图并批准。”不要求用户理解 hash、revision、MCP 或模型会话编号。

## 固定行为

- 开发、测试和代码质量审查均按独立范围使用多个子 Agent 并行推进：开发按原计划划分模块和文件归属，全部开发及测试代码完成后再并行测试；审查按独立代码范围只读并行，主审汇总去重并核查跨模块问题。主 Agent 协调真实依赖、共享接口和资源冲突，不把无关任务强制串行，不增加平台校验。
- 执行模型按 `../devflow-execute/SKILL.md` 先完成正式范围内全部开发及测试代码，再由多个子 Agent 并行测试独立目标，每条命令一个测试类、文件或用例，各自修复和定向重跑。只为真实依赖或资源冲突局部串行，禁止无筛选全量套件，已完成且未受影响的结果不重跑。纪律留在 Skill 中执行，不要求复制到计划正文，不增加平台校验或切换关卡。
- 所有程序使用当前操作系统用户及所选工具已有登录；绝不创建用户、切换用户或配置账户 ACL。
- 启动由本地 MCP 桥接器自动完成。首次安装后若入口不可用，说明需在当前客户端重新加载 MCP 配置；不要假装已经调用服务。
- 规划、执行与质量审查使用 ExecutionSpec 中冻结的 Profile；支持单工具承担全部角色及多工具协作，不固定客户端或模型。计划批准前不开发，按阶段由程序调度，不启动监工轮询。
- 工具与模型边界见 [model-config.md](references/model-config.md)：系统默认只有规划/执行两槽，审查等三项为任务级覆盖；保存后下次派发生效，当前 Run 不换；首次授权验证成功后跨任务复用，不是每轮验证；不能自动换更合适的模型。目录成功、登录成功、访问成功、业务验证成功互相独立。`--tools` 只分发客户端/Skill，不代替默认角色。`devflow_list_tool_profiles` 列出配置摘要，不声称等于授权。
- 计划用人话说明现状、目标变化、功能逻辑、关联影响和必要数据设计、技术坑，任务以细项 checkbox 表达；普通实现细节由执行模型完成，不要求半成品代码或全文件清单。已有原计划保持原件，需要时配图，不为复杂度强制拆出多份文档。
- 修改范围最小；按 `../devflow-test/SKILL.md` 覆盖单元、集成、E2E 三层，涉及前端影响的任务额外落实 OpenTabs 仿人工真实浏览器核验；身份无关本地场景优先免密开发会话，确需用户登录或回答时发出交互弹窗。E2E 覆盖新需求全部流程和受影响旧功能回归；Web E2E 使用真实浏览器。不适用项写明原因并审批，人工功能确认保留。
- 人工前与人工后均有代码质量审查；人工前执行质量整改一次，第二次复核仍有问题由规划模型直接修复（不跑测试）后交执行测试；测试完成后不再复核。人工后有问题直接规划修复。最终测试完成由规划模型实际 git commit。当前工作区只提交任务变更并保留用户原有改动；推送和发布只接受用户另行指令。
- 用户明确暂停测试时立即停下测试。

测试执行采用“全部开发完成后，多个子 Agent 并行负责独立目标，每条命令一个目标，各自修复和重跑”的规则；只有真实依赖或资源冲突才局部串行，完整覆盖不等于运行全量套件。规划复核只审相关代码质量，禁止审计测试真实性，禁止索要测试证明工具。

职责、主链路与策略 2 规则见 [职责与调度](references/role-and-schedule.md)。
