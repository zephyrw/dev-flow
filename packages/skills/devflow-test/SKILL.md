## 指定计划为执行依据，禁止执行模型另建计划

测试范围、场景和通过标准从用户指定/已批准的原计划及正式修订导出，逐项保留原验收编号；执行模型另写的局部计划、implementation_plan.md 或进度清单不构成新的测试依据，也不能据此删减原场景或降低断言。

执行模型不得为实施或自测另建替代计划。每个必需流程同时核对正常成功与适用的拒绝/异常行为，包含新需求全流程与受影响旧功能回归；旧缺陷探针“不再命中”不等于原计划功能已完成。测试设计与原计划冲突时提交事实给规划模型修订，不能自行改验收后宣布通过。

测试使用当前任务已冻结的执行配置，不因目录更新或“更合适”的模型而改换。保存后的默认只影响下次派发。首次授权验证成功后跨任务复用，不是每轮验证。目录成功、登录成功、访问成功、业务验证成功互相独立；测试通过不能用来证明模型已登录或已授权。系统默认只有规划/执行两槽。详情见 [model-config.md](../devflow/references/model-config.md)。

测试职责只给执行模型。执行模型应结合实际代码变更主动补齐必要的单元、集成与回归用例，真实执行并诚实说明状态。平台与规划复核不消费测试证明合同，不核验原始报告、日志、时间戳、宿主调用、用例映射或覆盖表，不为这些材料提出补测整改；严禁建立给审核者看的测试真实性证明工具、探针、签名或账本系统。

# 测试责任

自动测试仍按单元、集成、E2E 三层组织；存在前端影响时，执行模型还必须额外使用 OpenTabs 完成一轮仿人工真实浏览器核验。这是执行职责，不是工作流新增阶段或平台验收门槛。人工功能确认是用户判断业务是否符合需求，仍然保留，不能由自动测试代签。

## 三层覆盖与真实浏览器核验

| 层次/阶段 | 必须验证的行为 |
|---|---|
| 单元 | 修改涉及的业务规则、状态转换、边界值、异常分支和缺陷回归；依赖可隔离，断言实际输出及副作用。 |
| 集成 | 模块、接口、鉴权、事务、数据库及必要服务之间的交互；使用隔离测试环境中的真实组件验证目标边界，不能用全链路 mock 代替。 |
| E2E | 从用户入口到可观察业务结果的新需求全部业务流程，以及变更影响分析识别的旧功能回归流程。Web 项目通过真实浏览器操作页面并连接真实应用、后端和测试数据存储；无 Web 界面的 CLI/服务按其真实入口完成端到端验证。 |
| **OpenTabs 仿人工核验** | 凡本次变更影响前端展示、交互或页面业务链路，执行模型在完成正式开发后，必须额外使用 OpenTabs 原生工具操作真实浏览器进行一轮仿人工核验。普通 E2E、接口测试、jsdom、静态截图或 mocked 页面不能替代这一轮。 |

三层及前端真实浏览器核验默认必需。确实不适用时在计划 exemptions 或测试记录写明项目事实、具体理由和替代验证；“没时间”“没装工具”“环境启动失败”不构成不适用，也不能自动降级为人工验收。

## 前端真实浏览器核验核心原则

1. **真实入口全链路操作**：从真实页面入口按人的顺序点击、输入、提交、切换、刷新并检查结果；覆盖本次需求和真实受影响旧流程。
2. **视觉与数据核对**：实际查看关键截图，检查布局、样式、间距、遮挡与响应式；同时通过页面 DOM／脚本／CDP 相关能力核对用户实际看见的数据和控件状态。不能只保存截图不看，也不能通过修改前端内部状态伪造通过。详见 [真实浏览器核验规范](references/real-browser-verification.md)。
3. **本地免密优先**：本地场景与角色、权限、租户、登录状态无关时，优先匿名访问或使用隔离的免密开发会话，不要求用户登录。免密不能关闭业务授权规则，不能替代真实后端和数据，也不能用于证明登录／权限功能正确。确需真实身份且不能安全自动建立会话时，才请求用户完成登录、扫码或其他必要操作。详见 [本地免密与认证策略规范](references/local-auth-strategy.md)。
4. **通用人机交互与隐私边界**：涉及需要用户真实登录或回答问题时，使用已有 `need_user` 与通用交互机制暂停当前轮次并弹窗。请求前保存非敏感停留位置、停止登录页采集，不轮询登录或占住模型等待。用户确认后续接原执行上下文，先复查页面与登录事实再继续。执行模型不得代点自己发出的人工确认。
5. **记录与透明汇报**：如实记录实际通过、失败、未执行与环境阻塞项，填写核验工件。工件留在本地，不得包含具体临时端口或密码凭证。详见 [真实浏览器核验记录模板](references/browser-verification-record.md)。
6. **worktree 环境隔离**：新 worktree 的前后端、测试和调试端口必须与主工作区、其他 worktree 及当前其他实例不同；同步更新代理、WebSocket、HMR 和 baseURL。具体端口、地址、会话及目录只存于本地临时配置，不得提交或合并回主工作区。

## 从需求和影响范围导出用例

1. 逐项枚举新需求的用户角色、入口、业务分支和结果，覆盖正常、异常、权限、边界、刷新/持久化等适用场景，不能只做一条成功路径或页面冒烟。
2. 从真实 diff 向上查调用方、向下查依赖，并检查共享组件、数据结构、公共接口、配置、权限和状态变化；把可能影响的旧流程逐项列为回归场景。需要扩大回归范围时，先列出受影响的具体测试目标，再分派给多个子 Agent 并行执行独立目标；覆盖范围较广不允许使用全量套件命令。
3. 区分新需求与旧功能回归；没有受影响旧功能时给出调用链和差异依据，不能直接写“无”。
4. 测试层用 unit、integration、e2e，涉及前端时包含 opentabs 真实核验。具体测试名称和命令由执行模型落实。

## 真实 E2E 与仿人工核验区别

- Web E2E 使用真实浏览器引擎，有头或无头均可。点击、输入、提交后验证业务结果；需要持久化的场景还要刷新、重查或从下游读取结果。
- 仅请求接口、jsdom、组件挂载、静态截图、可见性断言或整条业务接口被拦截返回固定数据，都不足以证明完整 Web E2E。
- 自动化的 Web E2E 脚本主要保证功能回归断言自动化；存在前端影响时，执行模型仍须在此之外亲自使用 OpenTabs 执行仿人工核验，实际观察渲染结果。
- 缺陷修复应验证测试能捕获原缺陷，再确认修复后通过。跳过、零用例、恒真断言和仅由模型撰写的“通过”说明均不算通过。

## 自测与反馈

规划模型必须将以下规则写入计划正文及阶段安排：先完成正式计划中的全部开发任务，包括功能实现、端到端接线、异常与边界处理及测试代码，再进入单元、集成和 E2E 测试阶段。将独立测试目标分配给多个子 Agent 并行执行，各子 Agent 每条命令只指定一个测试类、文件或用例，并负责相关问题的定位、修复和重跑。某个目标失败不阻塞其他无关目标；不同测试层之间不设固定先后顺序。仅有真实依赖或共享资源冲突的目标需要协调、隔离或局部串行。禁止无筛选的全量命令、全库通配符和一次拼接多个测试目标；受影响回归也按独立目标分派并行，不因局部修改重跑整个套件。

执行时序详见 [完整开发后多子 Agent 并行测试](../devflow-execute/SKILL.md)。初次开发和正式整改先完成全部实现及测试代码；进入测试阶段后，多子 Agent 并行测试并各自修复、重跑失败目标。只有会影响另一运行目标的代码或资源需要协调，不等待无关层或整个套件结束。通过且不受影响的目标不重复运行。用户反馈保留复现步骤、预期结果及相应回归用例。恢复测试子任务时交给直接父 Agent，已完成或用户取消的不重跑；不把 delivered 当成测试已遵从。

每条测试命令必须明确目标；没有筛选参数、筛选失效、匹配多个文件/类时，先修正本地脚本或改用框架的单目标命令，不能默认退回全量。并发数为 1 仍不代表只选中了一个目标。该要求由执行模型落实，平台不添加过程校验，规划复核不追查测试证明。自动测试后保留人工功能确认。

普通任务使用项目原生测试命令或本地脚本；仅用户要求或已处于真实 DevFlow 交接上下文才使用工作流调度。不得因目录名含 devflow、读取本 skill 或执行已有计划就创建/恢复工作流，亦不得声称平台启动测试。实际执行方式按终端命令报告。

职责、主链路与策略 2 规则见 [职责与调度](../devflow/references/role-and-schedule.md)。
