## 指定计划为执行依据，禁止执行模型另建计划

测试范围、场景和通过标准从用户指定/已批准的原计划及正式修订导出，逐项保留原验收编号；执行模型另写的局部计划、implementation_plan.md 或进度清单不构成新的测试依据，也不能据此删减原场景或降低断言。

执行模型不得为实施或自测另建替代计划；测试记录只保存原编号、实际操作、用例、原始报告和结果。每个必需流程同时核对正常成功与适用的拒绝/异常行为，包含新需求全流程与受影响旧功能回归；旧缺陷探针“不再命中”不等于原计划功能已完成。测试设计与原计划冲突时提交事实给规划模型修订，不能自行改验收后宣布通过。

# 测试合同

在制定验收项、开发自测、处理用户反馈和代码质量复核时使用。自动测试只有单元、集成、E2E 三层；Web E2E 本身使用真实浏览器，不另设“真实浏览器验收”或 OpenTabs 第四层。人工功能确认是用户判断业务是否符合需求，仍然保留，不能由自动测试代签。

## 三层覆盖

| 层次 | 必须验证的行为 |
|---|---|
| 单元 | 修改涉及的业务规则、状态转换、边界值、异常分支和缺陷回归；依赖可隔离，断言实际输出及副作用。 |
| 集成 | 模块、接口、鉴权、事务、数据库及必要服务之间的交互；使用隔离测试环境中的真实组件验证目标边界，不能用全链路 mock 代替。 |
| E2E | 从用户入口到可观察业务结果的新需求全部业务流程，以及变更影响分析识别的旧功能回归流程。Web 项目通过真实浏览器操作页面并连接真实应用、后端和测试数据存储；无 Web 界面的 CLI/服务按其真实入口完成端到端验证。 |

三层默认必需。确实不适用时在计划 exemptions 写明项目事实、具体理由和替代验证，随计划批准；“没时间”“没装工具”“环境启动失败”不构成不适用，也不能自动降级为人工验收。

## 从需求和影响范围导出用例

1. 逐项枚举新需求的用户角色、入口、业务分支和结果，覆盖正常、异常、权限、边界、刷新/持久化等适用场景，不能只做一条成功路径或页面冒烟。
2. 从真实 diff 向上查调用方、向下查依赖，并检查共享组件、数据结构、公共接口、配置、权限和状态变化；把可能影响的旧流程逐项列为回归场景。无法可靠缩小影响范围时运行所属模块完整回归，公共基础设施变化运行相关项目完整 E2E。
3. 在现有计划/测试材料中维护覆盖表：需求或受影响旧功能 → 影响依据 → 测试层 → 稳定场景 ID → 操作、输入和结果断言 → 实际用例及原始报告。区分新需求与旧功能回归；没有受影响旧功能时给出调用链和差异依据，不能直接写“无”。
4. 测试层用 unit、integration、e2e；新需求和回归都放入 tests 的 steps、assertions、expected_case_ids，并与任务关联。native-v2 由执行模型将每个场景 ID 通过 acceptance_mappings 映射到真实用例、执行记录和报告，不凭用例数量或通过率认定覆盖完整。

## 真实 E2E 与有效证据

- Web E2E 使用真实浏览器引擎，有头或无头均可。点击、输入、提交后验证业务结果；需要持久化的场景还要刷新、重查或从下游读取结果。
- 仅请求接口、jsdom、组件挂载、静态截图、可见性断言或整条业务接口被拦截返回固定数据，都不足以证明完整 Web E2E。外部边界使用测试替身时明确边界及未验证部分，不能据此声称真实外部集成已通过。
- 浏览器工具属于 E2E 的执行工具，不限定 OpenTabs，不要求另装浏览器扩展、登记额外验收场景或重复跑一轮浏览器测试。
- 保存真实命令、cwd、退出码、当前代码和环境身份、逐用例结果及原始报告；浏览器失败时保留 trace、截图和相关日志。成功场景复用同一次 E2E 报告，不为展示再重复测试。
- 跳过、零用例、缺映射、旧报告、恒真断言和仅由模型撰写的“通过”说明均不算通过。缺陷修复应验证测试能捕获原缺陷，再确认修复后通过。

## 自测、反馈与复核

执行模型负责完成适用三层自测。开发时按影响范围运行测试；交付时提交当前代码上全部必需场景的有效证据，平台核验报告和覆盖，不重复接管测试执行。修改代码或环境后，按证据有效性规则重跑失效测试，不能用修改前结果证明新版本通过。

用户反馈的每个问题都要保留复现步骤、结果断言及对应回归用例；修复同时检查其影响的旧流程。质检模型复核覆盖表、真实测试实现、断言强度和原始报告；漏测或证据不足就要求补齐，不能用浏览器截图或人工确认替代自动测试。自动测试通过后仍按工作流保留用户功能确认。

## 程序调度的正式计划逐项复核

native-v2 每轮初始开发或正式质量整改完成后，执行顺序固定为：开发与自测 → 交付核验及成功退出 → 程序独立调度执行模型按正式计划逐项自查、修复遗漏并重测 → 规划模型独立质量审查。首轮质量通过才开放人工核验；人工功能问题修复同样必须经过程序自查，再直接交用户复测，全部功能确认后进入最终质量审查。人工前、人工后两关分别计数；各关连续三次执行模型整改仍不合格，程序调度规划模型接管修复，自查后再进入审查。不得用首次完成自述代替程序自查，不得伪造人工确认。

复核必须重新读原始计划及当前正式批准的整改/修订全文，按原编号关联真实实现、测试和未完成项。使用当前运行的 HANDOFF.json 中 authorities、check.check_ids 与 check_schema；旧入口使用 AUTHORITATIVE_PLANS.json、HANDOFF.md、handoff.json 和 self_check.check_ids，均以程序交付的真实版本为准；正式范围变更引用对应批准修订。禁止创建或使用 implementation_plan.md、客户端计划工件或其他局部计划替代原文。逐项报告属于执行事实记录，不是另一份实施计划。

当前复核轮次的交付清单必须包含 plan_self_check，并符合本轮 check_schema（旧入口为 plan-self-check.schema.json）：绑定请求、源交付、当前 run_id、plan_revision、plan_hash、authority_hash；完整覆盖全部 check_ids，逐项提供代码/测试报告/用例定位，记录发现问题及实际修复证据。遗漏、重复编号、空证据、未解决问题、旧轮次/旧计划/旧输入报告、进程失败均阻断规划审查；代码改动后提交当前轮次有效测试与新交付。正常开发轮次不能自行填报告冒充程序调度。

程序校验报告及当前交付的绑定和完整性，不能保证模型判断语义正确；规划模型仍须独立检查实际代码、测试真实性与原计划覆盖。缺少本轮有效自查报告不得放行。自查不计入任何质量关卡的三次拒绝次数；暂停/停止后不得自行继续，不新增后台轮询，不改变既有界面布局。
