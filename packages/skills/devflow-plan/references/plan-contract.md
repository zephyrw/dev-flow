## 指定计划为执行依据，禁止执行模型另建计划

首次需求没有计划时制定计划；已有用户指定/批准的原计划及正式引用继续作为执行依据。恢复、审批、普通修复和整改不能覆盖原计划；明确授权的范围变化在原文中补充，不另建版本或副本。

完整读取原文并保留原路径和任务/验收编号。禁止另建 implementation_plan.md、客户端计划工件或局部实施计划替代原文，禁止借细化缩减范围、接口链路或验收条件。同一模型兼任多个角色也不能自行批准改变范围。

允许在原计划更新 checkbox、事实状态和问题说明；只有实际完成才将 `[ ]` 改为 `[x]`，已派发、阶段推进或口头声明不等于完成。已有过程记录可按原编号说明实现、测试和未完成原因，不替代原计划，也不为恢复再建一份计划。

原文确有不可实施的设计冲突时，提交原章节、代码事实和影响，只暂停受阻部分。规划角色保留原文并补充必要说明；改变业务需求/批准范围才取得用户确认，范围内普通修复不重新规划或重做已完成工作。

以 MCP `devflow_submit_plan` 暴露的参数 Schema 为结构参考，不要求业务项目包含 DevFlow 自身源码。按接口传递工作流 ID、并发版本、幂等键和 `plan`；内部审批身份与并发字段不等于要求文档版本或副本。

先读取登记项目的完整配置；每个仓库基线必须是已核实的 commit ID。

正文用人话写清现状、目标从什么变成什么、功能与逻辑变化、关联影响，以及完整技术设计、必要的数据设计和技术坑；按功能拆成全部细项 checkbox 任务，说明真实依赖和可观察的完成结果。不要写成半成品代码或全文件清单。结构化字段按当前 Schema 提供精简索引，不要求正文逐字段展开。`task.paths` 可省略，仅作定位参考；`plan.scope` 和旧路径字段只作兼容元数据，不是文件或目录修改白名单，不要求填写允许修改路径。执行模型自由选择修改位置，主动补齐必要接线、参数、边界、测试及阻塞开发和验证的关联问题；遵守用户明确的权限、数据保护和环境边界，只有真实改变业务需求才询问用户。

新计划优先使用 `task_model: "native-v2"`。在 `native-v2` 下：
- 正文说明完整业务需求和必要设计，搭配精简的需求、模块 `modules`、任务 `tasks`、验收项 `tests` 与依赖索引，普通实现细节由执行模型处理，不要求预写函数或实现代码；
- 验收项使用稳定业务编号，规定验证层次、场景和预期结果；具体测试名称、命令参数不在规划阶段锁定，由执行模型编写具体测试用例；
- 索引不重复存储整段正文，执行模型通过原生文件工具直接阅读完整设计正文。

测试责任覆盖 unit、integration、e2e 三层；存在前端影响时，增加 OpenTabs 仿人工真实浏览器核验责任，正文写清真实操作场景、截图/可见数据预期与认证策略（身份无关优先匿名/免密开发会话；依赖角色/租户规划真实测试身份；确需人工登录时走通用人机交互）。不适用的测试层需填写具体理由并随计划批准。计划正文、图解和索引用于表达与展示，不强制增加 machine-readable 测试证明字段，不作为角色切换质量门槛。人工功能确认另行保留。

实际测试遵守 devflow-test：先完成正式范围内全部开发及测试代码，再由多个子 Agent 并行负责独立目标，每条命令只指定一个测试类、文件或用例，各自修复和定向重跑；只有真实依赖或资源冲突局部串行，禁止无筛选全量套件。保留已完成且未受影响的结果。此为 Skill 中的执行约定，不要求复制到计划正文，不添加核验字段或交接门禁。

调用 submit_plan 后给用户审批地址并结束当前回合。

开发和审查的独立范围仍按对应 Skill 并行分工，主 Agent 协调共享接口与真实依赖；审查只读，主审汇总跨模块问题，不核验测试声明。正文只需说明本任务必要的协作边界，不粘贴通用调度纪律，不增加平台门禁。

职责、主链路与策略 2 规则见 [职责与调度](../../devflow/references/role-and-schedule.md)。
