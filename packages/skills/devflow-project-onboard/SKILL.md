## 指定计划为执行依据，禁止执行模型另建计划

用户已提供计划/整改文档并要求执行时，接入仅调查和登记真实仓库、运行环境与测试配置，保留原计划的身份、完整范围和验收编号，不额外创建局部实施计划替换它。接入发现与原设计冲突时提交事实交规划模型修订原计划，不能由执行模型重新规划后执行。只有原需求尚无确定计划时，才在接入后进入首次规划。

1. 读取用户指定仓库及项目规则，登记单仓/多仓、真实 Git common directory 与基线。
2. 从实际配置、脚本和代码定位技术栈；不假设前后端框架或默认端口。
3. 查明启动、构建、单元、集成和 E2E 命令及真实报告格式。
4. 确定命令入口、参数数组、cwd、环境变量和依赖，不允许任意 shell 文本。
5. 明确数据库、缓存、消息、注册中心、定时任务及外部服务的测试隔离规则。
6. 明确动态端口、前端 API 目标和运行身份标记的最小接入修改。
7. 按 `../devflow-test/SKILL.md` 确定真实 E2E 入口、浏览器/后端/测试数据隔离、测试账号引用和新需求及旧功能回归范围；Web E2E 自带真实浏览器验证，不另设 OpenTabs 测试层。保留用户功能确认清单。
8. 对业务行为和环境归属的已知疑问先询问用户，随后形成唯一确定配置。
9. 根据 devflow_register_project 的参数合同生成项目配置和测试命令，直接登记；新项目不要求 browser_scenes，使用其默认空列表。用户不填写或导入 JSON。
10. 回到 devflow_start；已有用户指定计划时复用该原文和版本，只有尚无确定计划时才为原始需求制定完整计划。端口、前端代理和健康检查所需的最小代码适配一并列入计划，在人工批准后由执行模型完成。
11. 配置登记本身不执行命令；环境在实施完成后准备。将运行配置和数据范围写入审批正文。不要求额外安装 OpenTabs；不得覆盖个人模型配置或创建/切换操作系统用户。

## 程序调度的正式计划逐项复核

native-v2 每轮初始开发或正式质量整改完成后，执行顺序固定为：完整开发 → 统一测试 → 交付核验及成功退出 → 程序独立调度执行模型按正式计划完整逐项自查、汇总全部问题及根因、整批修复后统一测试 → 规划模型独立质量审查。首轮质量通过才开放人工核验；人工功能问题修复同样必须经过程序自查，再直接交用户复测，全部功能确认后进入最终质量审查。人工前、人工后两关分别计数；各关连续三次执行模型整改仍不合格，程序调度规划模型接管修复，自查后再进入审查。不得用首次完成自述代替程序自查，不得伪造人工确认。

复核必须重新读原始计划及当前正式批准的整改/修订全文，按原编号关联真实实现、测试和未完成项。使用当前运行的 HANDOFF.json 中 authorities、check.check_ids 与 check_schema；旧入口使用 AUTHORITATIVE_PLANS.json、HANDOFF.md、handoff.json 和 self_check.check_ids，均以程序交付的真实版本为准；正式范围变更引用对应批准修订。禁止创建或使用 implementation_plan.md、客户端计划工件或其他局部计划替代原文。逐项报告属于执行事实记录，不是另一份实施计划。

当前复核轮次的交付清单必须包含 plan_self_check，并符合本轮 check_schema（旧入口为 plan-self-check.schema.json）：绑定请求、源交付、当前 run_id、plan_revision、plan_hash、authority_hash；完整覆盖全部 check_ids，逐项提供代码/测试报告/用例定位，记录发现问题及实际修复证据。遗漏、重复编号、空证据、未解决问题、旧轮次/旧计划/旧输入报告、进程失败均阻断规划审查；代码改动后提交当前轮次有效测试与新交付。正常开发轮次不能自行填报告冒充程序调度。

程序校验报告及当前交付的绑定和完整性，不能保证模型判断语义正确；规划模型仍须独立检查实际代码、测试真实性与原计划覆盖。缺少本轮有效自查报告不得放行。自查不计入任何质量关卡的三次拒绝次数；暂停/停止后不得自行继续，不新增后台轮询，不改变既有界面布局。
