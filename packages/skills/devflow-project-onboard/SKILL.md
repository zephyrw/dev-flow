## 指定计划为执行依据，禁止执行模型另建计划

用户已提供计划/整改文档并要求执行时，接入仅调查和登记真实仓库、运行环境与测试配置，保留原计划的身份、完整范围和验收编号，不额外创建局部实施计划替换它。接入发现与原设计冲突时提交事实交规划模型修订原计划，不能由执行模型重新规划后执行。只有原需求尚无确定计划时，才在接入后进入首次规划。

1. 读取用户指定仓库及项目规则，登记单仓/多仓、真实 Git common directory 与基线。
2. 从实际配置、脚本和代码定位技术栈；不假设前后端框架或默认端口。
3. 查明启动、构建及单元、集成、E2E 的单目标命令、筛选参数和报告格式。测试入口应明确指定一个类/文件/用例，不能把无筛选全量命令作为默认配置；不支持筛选时将最小脚本适配纳入计划。
4. 确定命令入口、参数数组、cwd、环境变量和依赖，不允许任意 shell 文本。
5. 明确数据库、缓存、消息、注册中心、定时任务及外部服务的测试隔离规则。
   同时查明开发工作区、共享构建产物、报告和客户端子 Agent 能力，供计划安排开发、测试及只读代码审查的并行分工；优先隔离实际冲突资源，不将整个工作区默认设为串行。此项用于模型协作，不增加程序交接校验。
6. 明确动态端口、前端 API 目标和运行身份标记的最小接入修改。
7. 按 `../devflow-test/SKILL.md` 确定真实 E2E 入口、浏览器/后端/测试数据隔离、测试账号引用和新需求及旧功能回归范围。保留用户功能确认清单。接入只登记真实仓库与运行需要，不把环境健康或集成测试证明作为人工入口门槛。
8. 对业务行为和环境归属的已知疑问先询问用户，随后形成唯一确定配置。
9. 根据 devflow_register_project 的参数合同生成项目配置和测试命令，直接登记。用户不填写或导入 JSON。
10. 回到 devflow_start；已有用户指定计划时复用该原文和版本，只有尚无确定计划时才为原始需求制定完整计划。端口、前端代理和健康检查所需的最小代码适配一并列入计划，在人工批准后由执行模型完成。
11. 配置登记本身不执行命令；环境在实施完成后准备。将运行配置和数据范围写入审批正文。不得覆盖个人模型配置或创建/切换操作系统用户。接入不改系统默认规划/执行槽，也不把 `--tools` 当成角色设置。首次授权验证成功后跨任务复用，不是每轮验证；不能自动换更合适的模型。目录成功不等于登录、访问或业务验证成功。详情见 [model-config.md](../devflow/references/model-config.md)。

测试执行采用“全部开发完成后，多个子 Agent 并行负责独立目标，每条命令一个目标，各自修复和重跑”的规则；只有真实依赖或资源冲突才局部串行，完整覆盖不等于运行全量套件。规划复核只审相关代码质量，禁止审计测试真实性，禁止索要测试证明工具。

职责、主链路、两阶段计数与三次接管见 [职责与调度](../devflow/references/role-and-schedule.md)。
