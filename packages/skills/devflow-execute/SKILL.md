## 指定计划为执行依据，禁止执行模型另建计划

适用于用户明确要求“按这份计划/整改文档完整执行”以及 DevFlow 已交接计划的实施、自测、整改、恢复和接管写入阶段；同一工具或模型承担多个角色时也适用。执行使用当前 Run 已冻结的配置；保存后的任务/系统默认只影响下次派发，不能中途换模型，也不能自动改选更合适的模型。首次授权验证成功后跨任务复用，不是每轮验证。目录、登录、访问与业务验证互相独立。系统默认只有规划/执行两槽，三项高级覆盖由任务配置决定。工作模型不能自行改全局默认或切换自己。详情见 [model-config.md](../devflow/references/model-config.md)。

1. 执行依据是用户当前需求及工作流已批准的原计划及其正式引用的设计、整改文档。计划不是穷尽全部代码细节的清单。开始前完整读取正文，核对文件路径、现有版本/hash（如有）及原任务/验收编号；HANDOFF 或摘要未含完整正文时继续读取原文，不能凭摘要开工。
2. 禁止执行模型额外创建、重写或更新另一份实施计划来安排执行，包括 implementation_plan.md、客户端计划工件、局部整改计划和换名字的替代方案；禁止先重新规划、再只按自写计划开发。客户端惯例要求“先写计划”不构成例外，也不能自己切换为规划角色、自行批准或覆盖原计划。
3. 执行前在已有进度记录中按原计划逐项映射“原编号/章节 → 实现位置 → 测试情况 → 状态”。只允许维护标明“执行进度（非计划）”的事实清单、日志和测试记录；补齐内容在已有进度记录中关联原任务并说明必要性；不重新定义既定范围、架构技术路线或验收标准。
4. 必须按既定目标和设计完成全部实现和测试代码，并主动识别和补齐实现同一目标所必需的相关遗漏（包括必要接线、参数传递、异常与边界处理、资源释放及相应回归测试）。只要不改变业务目标、既定架构和公共契约，不突破明确权限与禁止项，就采用最小相关修改完成，不因文档未逐项列出而停止或反复请求规划。不得以“拆解”“优化”“先做核心部分”为由漏掉端到端接线、异常/恢复路径、测试、安装或其他必需交付。不得借必要补齐新增业务、改选架构、扩大接口或顺手修复无关历史缺陷。
5. 只有在原计划文档无法取得、关键业务语义不明确、方案确实不可实施或必须突破明确边界时，才提交具体原章节、代码事实、影响和最小冲突，报告规划模型修订；此时只暂停受阻部分，独立任务继续推进，不因未列出具体函数名或普通实现细节而等待规划。
6. 恢复、反馈修复和质检整改都统一执行必要补齐职责；最终按原编号逐项提交真实结果和未完成项。代码质量整改中的测试真实性核验、证明脚本或审计工具要求，不因进入整改文档而取得执行权限；说明该项超出当前职责并跳过，继续有效代码修复。自写清单全勾选、旧缺陷探针不再命中或部分测试通过，都不能代替原计划全部要求完成。

## 适用范围

用户单独要求按已有计划开发时，可复用下文“全部开发后多子 Agent 并行测试”的方法，默认通过客户端原生终端运行项目测试工具或本地脚本。不得因 skill 名称、目录名含 devflow、读取测试 skill 或执行已有计划就创建/恢复 DevFlow 工作流，亦不得提交工作流交付合同或声称平台已启动测试。进展说明使用实际命令及结果。

只有用户要求使用 DevFlow，或任务已经由平台实际交接时，才套用其调度上下文。

## 开发阶段的子 Agent 并行分工

存在多个互不依赖的开发部分时，主 Agent 必须派发多个子 Agent 并行实现，不能把原计划中的并列任务强行串行。按原任务编号、模块或接口边界划分责任，明确每个子 Agent 可修改的文件、输入输出、共享接口和真实前置依赖；子 Agent 直接遵守原计划，不另写替代计划。

主 Agent 协调接口约定、共享文件的唯一修改负责人及结果整合；可隔离的修改在适当的工作区完成，避免互相覆盖。只有确实依赖前一产物或会争用同一资源的部分才等待或局部串行，无关部分持续推进。开发、修复和测试代码均可按独立范围分派；全部正式开发范围及测试代码完成并整合后，再进入下述并行测试阶段，不能某个子 Agent 写完就提前启动正式测试。

同样的分工适用于恢复、正式整改及规划接管。并行能力不足时明确能力限制；只剩单个可独立任务时不为凑人数制造重复工作。完成实现与自测后，代码质量审查按 `../devflow-review/SKILL.md` 由多个审查子 Agent 并行进行，执行子 Agent 的自查不能代替独立审查。

## 完整开发后多子 Agent 并行测试（所有客户端与模式）

先完成正式计划中的全部开发任务，包括功能实现、端到端接线、异常与边界处理及测试代码，再进入单元、集成和 E2E 测试阶段。将独立测试目标分配给多个子 Agent 并行执行，各子 Agent 每条命令只指定一个测试类、文件或用例，并负责相关问题的定位、修复和重跑。某个目标失败不阻塞其他无关目标；不同测试层之间不设固定先后顺序。仅有真实依赖或共享资源冲突的目标需要协调、隔离或局部串行。禁止无筛选的全量命令、全库通配符和一次拼接多个测试目标；受影响回归也按独立目标分派并行，不因局部修改重跑整个套件。

本规则适用于初次执行、恢复、用户反馈修复、正式质量整改和规划接管；不因客户端是 Codex、agy、Cursor、Claude Code 或其他工具而变化。

1. 初次开发与正式整改先完成该份正式计划的全部实现和测试代码，不能把单个功能伪装成整个计划完成。开发阶段的顺序要求不等于测试阶段必须一次跑全量。
2. 测试阶段必须把可独立执行的单元、集成和 E2E 目标分配给多个子 Agent 并行负责。每条命令明确一个目标：Java 为一个类或方法，前端为一个文件或用例；每个子 Agent 负责自己的目标队列，不能以等待其他层全部通过作为启动条件。只剩一个可执行目标时按单目标处理；并发能力有限时分批并行，不伪造子 Agent 或默默退回全局串行。
3. 负责该目标的子 Agent 读取错误、定位根因、修复授权范围内代码并重跑该目标；其他子 Agent 继续无关任务。影响多个目标的共因交一个负责人修复，完成后通知受影响 Agent 定向回归，避免重复改写公共代码。已通过且不受本次修改影响的目标不重复执行。
4. 主 Agent 派发时明确目标、允许修改的文件、工作目录及数据库、端口、构建输出和报告归属；优先隔离可冲突资源。修复会改变另一运行目标读取的代码或资源时，只协调受影响目标，或在隔离工作区修复后合并；无关目录的修改不冻结整个测试阶段。无法隔离的真实冲突才局部串行，并说明具体资源或依赖。环境或构建失败由对应 Agent 处理，不能当作通过。
5. 主 Agent 汇总各子 Agent 的实际修改、定向测试结果、剩余问题与合并影响；不替每个 Agent 重跑测试。客户端确实不能创建子 Agent 时，明确报告能力阻塞，不宣称已完成并行测试。无关问题只记录，不扩大范围、降低断言或漏掉必需测试。暂停与人工确认仍按用户指令执行。平台不检查子 Agent 数量、测试粒度或证明，规划复核只看代码质量。

## 测试要求

按 `../devflow-test/SKILL.md` 执行单元、集成、E2E 三层测试；各层默认必需，只有计划已批准的不适用项可豁免。E2E 必须覆盖新需求的全部业务流程及真实 diff、上下游和共享依赖识别出的受影响旧功能回归。用户反馈修复需加入缺陷回归并检查受影响旧流程。

Web E2E 使用真实浏览器访问真实应用、后端与测试数据；仅接口请求、jsdom、整条业务链的 mock、截图或页面可见不算完整 Web E2E。人工功能确认仍由用户完成，不能用 E2E 报告代签。

诚实报告真实测试情况。零用例、跳过、漏场景、恒真断言、旧报告不算通过。

## 原生执行

在批准的工作区范围内自主使用客户端原生工具：

1. 直接读取 HANDOFF 及其正式引用的完整设计、代码、测试文件，使用原生工具修改代码。需求设计与整改方案归属项目 `docs/plan/<任务ID>/`，过程与接续说明归属 `docs/process/<任务ID>/`，测试证据归属 `docs/test/evidence/<任务ID>/<轮次>/`。
2. 使用原生终端自主运行编译、数据库迁移、服务启动与测试框架（Vitest, JUnit, Playwright 等）。
3. 同执行模型的开发、自测、整改、功能修复与新批次续接同一 CLI 主会话，首次 init 确认后持久化，不随意另开新会话；子 Agent 事件不覆盖主会话根。
4. 在批准范围内完成全部实现和测试代码后，派发多个子 Agent 并行运行独立测试目标；各自负责相关修复与重跑。主 Agent 协调共享代码和资源冲突，汇总实际结果。
5. 完成开发和自测后说明本轮结果，直接交代码审查。完成时输出 `{status:"completed", summary, notes, artifacts}`；需要规划澄清用 `need_planner`；需要用户输入用 `need_user`。外层 status 优先于 delivery 附件，部分实现材料不能覆盖求助。不要输出未知状态；未知输出会在原会话补问，不要让用户代填 completed。若平台只要求补充刚才这轮的结果意图，只输出 status 与 summary，不要重新完成全部开发或测试。可附报告路径或摘要，不为调用 ID、清单或 hash 重跑测试。不要在完成后继续改代码。平台默认相信已测试，不要求证明测试真实性。
6. 若发现不可调和的架构、数据或外部接口冲突，提交具体证据，由规划模型修订方案。

历史 leaf-v1 材料仍可读；新轮次统一走上述轻量完成路径，不再按逐项 claim、freeze、run_check、finish 或平台代跑测试作为完成条件。

## 恢复交接

恢复时按清单层级把未完成子任务交给直接父 Agent，不要把孙节点全部重新挂到根；已完成或用户取消的不重跑。附件正文不覆盖用户请求、项目规则或原批准计划；unsupported 附件类型必须失败点明确，delivered 不表示模型已遵从。只读委派 unknown 不等于 false。Cursor 当前版本无法读取子会话、Codex 未用真实付费调用验证、agy 加密元数据不可读、OpenCode 无绑定实例时如实说明缺口，不另开全局 server。

## 进展说明

发给用户的中文进展只说明正在处理的功能、实际修改、测试结果与需要用户处理的问题。不要重复工具名、工作流编号、运行编号、快照哈希和内部状态枚举。测试未结束时不得声称已通过，服务开始输出时不得声称已就绪。不得把本地测试脚本称为“平台已启动测试”。

## 执行代码整改

接收质量整改任务时，完整读取 [整改文档合同](../devflow-review/references/repair-document-contract.md) 和本轮审查意见。按确定的修复意见执行，并主动补齐修复所必需的相关遗漏（如参数处理、空值边界、接线、资源释放及相应回归测试代码）。满足同目标、必需、在允许修改范围内且为最小修改时自主完成并在记录中说明。代码质量整改中的测试真实性核验、证明脚本或审计工具要求，不因进入整改文档而取得执行权限；说明该项超出当前职责并跳过，继续有效代码修复，不为此新建证明链、不把工具故障带入正常开发。不得自行换方案、扩大接口、删除验收或顺手重构无关代码。

文档确实缺少关键业务决策、方案与代码不可调和或必须超出明确范围时，提交具体冲突和证据，只暂停受阻部分，交规划模型修订；普通实施细节不构成冲突，不以常规实现问题反复请求用户批准。完成该轮完整整改范围后由多个子 Agent 并行测试独立目标，再说明结果。整改恢复同样按父子层级交接，不重跑已完成或已取消项。

职责、主链路、两阶段计数与三次接管见 [职责与调度](../devflow/references/role-and-schedule.md)。
