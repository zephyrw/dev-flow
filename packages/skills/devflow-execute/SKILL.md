阶段首次交接时读取本阶段需求和必要材料。同一原生会话内的指导、回答、暂停恢复和调用重试直接沿用会话上下文；不因新 Run 重读计划、HANDOFF、任务或进度，不要求平台重复提供这些内容。后续用户消息按原文处理，阶段内部自行完成任务。

## 指定计划为执行依据，禁止执行模型另建计划

适用于用户明确要求“按这份计划/整改文档完整执行”以及 DevFlow 已交接计划的实施、自测、整改、恢复和接管写入阶段；同一工具或模型承担多个角色时也适用。执行使用当前 Run 已冻结的配置；保存后的任务/系统默认只影响下次派发，不能中途换模型，也不能自动改选更合适的模型。首次授权验证成功后跨任务复用，不是每轮验证。目录、登录、访问与业务验证互相独立。系统默认只有规划/执行两槽，三项高级覆盖由任务配置决定。工作模型不能自行改全局默认或切换自己。详情见 [model-config.md](../devflow/references/model-config.md)。

1. 执行依据是用户当前需求及工作流已批准的原计划和正式引用。计划用人话说明业务变化与必要设计，不是半成品代码或全文件清单。开始前完整读取原件，核对原路径和任务/验收编号；HANDOFF 或摘要未含完整正文时继续读取原文，不能凭摘要开工。恢复、审批、普通修复和整改不能覆盖原计划，不另建版本或副本；明确授权的范围变化才在原文中补充。
2. 禁止执行模型额外创建、重写或更新另一份实施计划来安排执行，包括 implementation_plan.md、客户端计划工件、局部整改计划和换名字的替代方案；禁止先重新规划、再只按自写计划开发。客户端惯例要求“先写计划”不构成例外，也不能自己切换为规划角色、自行批准或覆盖原计划。
3. 按原编号维护实际进度，允许在原计划更新细项 checkbox、状态和问题说明；只有实际完成才将 `[ ]` 改为 `[x]`，不能因已派发、阶段推进或声明完成就勾选。已有过程记录可补充实现位置、测试结果和未完成原因；必要补齐关联原任务，不重新定义既定范围、架构或验收标准，不把进度清单替换为新计划。
4. 必须按既定目标和设计完成全部实现和测试代码，并主动识别和补齐实现同一目标所必需的相关遗漏（包括必要接线、参数传递、异常与边界处理、资源释放及相应回归测试）。只要不改变业务目标、既定架构和公共契约，不突破明确权限与禁止项，就采用最小相关修改完成，不因文档未逐项列出而停止或反复请求规划。不得以“拆解”“优化”“先做核心部分”为由漏掉端到端接线、异常/恢复路径、测试、安装或其他必需交付。不得借必要补齐新增业务、改选架构、扩大接口或顺手修复无关历史缺陷。
5. 只有在原计划文档无法取得、关键业务语义不明确、方案确实不可实施或必须突破明确边界时，才提交具体原章节、代码事实、影响和最小冲突，报告规划模型修订；此时只暂停受阻部分，独立任务继续推进，不因未列出具体函数名或普通实现细节而等待规划。
6. 恢复、反馈修复和质检整改都统一执行必要补齐职责；最终按原编号逐项提交真实结果和未完成项。代码质量整改中的测试真实性核验、证明脚本或审计工具要求，不因进入整改文档而取得执行权限；说明该项超出当前职责并跳过，继续有效代码修复。自写清单全勾选、旧缺陷探针不再命中或部分测试通过，都不能代替原计划全部要求完成。

## 适用范围

用户单独要求按已有计划开发时，可复用下文“全部开发后多子 Agent 并行测试”的方法，默认通过客户端原生终端运行项目测试工具或本地脚本。不得因 skill 名称、目录名含 devflow、读取测试 skill 或执行已有计划就创建/恢复 DevFlow 工作流，亦不得提交工作流交付合同或声称平台已启动测试。进展说明使用实际命令及结果。

只有用户要求使用 DevFlow，或任务已经由平台实际交接时，才套用其调度上下文。

## 开发阶段的子 Agent 并行分工

存在多个互不依赖且可避免冲突的任务时，主 Agent 派发子 Agent 并行实现，不能把并列任务强行串行。分工说明任务目标、预期结果和已知前置依赖；修改位置由实际调查确定，不要求提前列全文件或划定文件白名单，也不为分工遍历分析整个项目。子 Agent 直接遵守原计划，不另写替代计划。

调查中发现共享修改点时，相关 Agent 协调具体修改及先后，必要时由一个负责人完成该处修改，避免互相覆盖；可隔离的修改在适当的工作区完成。只有确实依赖前一产物或争用同一资源的部分才等待或局部串行，无关部分持续推进。开发、修复和测试代码均可按独立任务分派；全部正式开发范围及测试代码完成并整合后，再进入下述并行测试阶段，不能某个子 Agent 写完就提前启动正式测试。

同样的分工适用于恢复、正式整改及规划接管。并行能力不足时明确能力限制；只剩单个可独立任务时不为凑人数制造重复工作。完成实现与自测后，代码质量审查按 `../devflow-review/SKILL.md` 由多个审查子 Agent 并行进行，执行子 Agent 的自查不能代替独立审查。

## 完整开发后多子 Agent 并行测试（所有客户端与模式）

先完成正式计划中的全部开发任务，包括功能实现、端到端接线、异常与边界处理及测试代码，再进入单元、集成和 E2E 测试阶段。将独立测试目标分配给多个子 Agent 并行执行，各子 Agent 每条命令只指定一个测试类、文件或用例，并负责相关问题的定位、修复和重跑。某个目标失败不阻塞其他无关目标；不同测试层之间不设固定先后顺序。仅有真实依赖或共享资源冲突的目标需要协调、隔离或局部串行。禁止无筛选的全量命令、全库通配符和一次拼接多个测试目标；受影响回归也按独立目标分派并行，不因局部修改重跑整个套件。

本规则适用于初次执行、恢复、用户反馈修复、正式质量整改和规划接管；不因客户端是 Codex、agy、Cursor、Claude Code 或其他工具而变化。

1. 初次开发与正式整改先完成该份正式计划的全部实现和测试代码，不能把单个功能伪装成整个计划完成。开发阶段的顺序要求不等于测试阶段必须一次跑全量。
2. 测试阶段必须把可独立执行的单元、集成和 E2E 目标分配给多个子 Agent 并行负责。每条命令明确一个目标：Java 为一个类或方法，前端为一个文件或用例；每个子 Agent 负责自己的目标队列，不能以等待其他层全部通过作为启动条件。只剩一个可执行目标时按单目标处理；并发能力有限时分批并行，不伪造子 Agent 或默默退回全局串行。
3. 负责该目标的子 Agent 读取错误、定位根因、修复授权范围内代码并重跑该目标；其他子 Agent 继续无关任务。影响多个目标的共因交一个负责人修复，完成后通知受影响 Agent 定向回归，避免重复改写公共代码。已通过且不受本次修改影响的目标不重复执行。
4. 主 Agent 派发时明确测试目标、工作目录和已知依赖，需要时协调数据库、端口或构建输出等共享资源，不预先限定修复文件清单。修复会改变另一运行目标读取的代码或资源时，只协调受影响目标，或在隔离工作区修复后合并；无关修改不冻结整个测试阶段。无法隔离的真实冲突才局部串行，并说明具体资源或依赖。环境或构建失败由对应 Agent 处理，不能当作通过。
5. 主 Agent 汇总各子 Agent 的实际修改、定向测试结果、剩余问题与合并影响；不替每个 Agent 重跑测试。客户端确实不能创建子 Agent 时，明确报告能力阻塞，不宣称已完成并行测试。无关问题只记录，不扩大范围、降低断言或漏掉必需测试。暂停与人工确认仍按用户指令执行。平台不检查子 Agent 数量、测试粒度或证明，规划复核只看代码质量。

## 测试要求

源码及测试代码完成并整合后，按 [开发验证与交付边界](../devflow/references/development-validation.md) 分别完成正式类型检查、生产构建与受影响测试。类型检查覆盖测试夹具及其导入模块；测试转译运行或排除 tests 的编译不能代替。代码修改或合并使旧结果失效时重跑受影响检查；必需检查失败或未执行不得宣称交付完成。检查由执行阶段负责，规划接管修复及提交角色保持原边界。

按 `../devflow-test/SKILL.md` 执行单元、集成、E2E 三层测试；各层默认必需，只有计划已批准的不适用项可豁免。E2E 必须覆盖新需求的全部业务流程及真实 diff、上下游和共享依赖识别出的受影响旧功能回归。用户反馈修复需加入缺陷回归并检查受影响旧流程。

涉及前端影响的任务，在完成正式开发与三层测试代码后，执行模型还必须使用 OpenTabs 原生工具操作真实浏览器，完成一轮仿人工真实核验；普通 E2E、Mock 页面不能替代这一轮。本地场景与身份无关时优先匿名或免密开发会话；确需人工登录或回答时发出 `need_user` 交互弹窗。详见 [真实浏览器核验规范](../devflow-test/references/real-browser-verification.md) 与 [本地免密与认证策略规范](../devflow-test/references/local-auth-strategy.md)。

以用户原文与已批准计划为准，单元、集成、E2E、OpenTabs 四项责任和结果分别核对；E2E 的 passed/skipped 不改变 OpenTabs 状态，不能只允许计划并存而漏执行。若仅缺 OpenTabs，就检查本次实际可用的工具与真实浏览器入口，实际操作并观察后说明结果；不凭空声称工具可用或不可用。已完成且未受影响的前三项保留，不为补第四项全量重跑；真实阻塞如实报告，不增加平台验证或证明材料。

Web E2E 使用真实浏览器访问真实应用、后端与测试数据；仅接口请求、jsdom、整条业务链的 mock、截图或页面可见不算完整 Web E2E。人工功能确认仍由用户完成，不能用 E2E 报告代签。

诚实报告真实测试情况。零用例、跳过、漏场景、恒真断言、已失效的旧报告不算通过；当前任务已完成且未受影响的结果可以复用。

## Worktree 路径、端口与本地环境隔离规范

涉及独立 worktree 执行时，严格遵守以下红线约束：
1. **工作区分支与状态保护**：所有分支检出、文件修改和提交操作必须完全在指定的独立 worktree 工作区中进行；严禁在主工作区（主仓库根目录）直接执行 `git checkout` 切换分支，绝不得干扰主工作区正在进行的其他任务或未提交修改。
2. **前后端与调试端口独立**：每个新增 worktree 的前端、后端、测试（如 Playwright E2E fixture server）及调试端口必须与主工作区（默认前端 5173、后端 4810）及其他兄弟 worktree 互不冲突。端口对应的 API 代理、WebSocket、HMR、测试 baseURL 和后端允许的本地开发 Origin 必须同步指向当前实例。
3. **临时配置绝不提交或合并**：本地运行器生成的 `instance.json`、`devflow.runtime.yaml`、临时数据库和端口登记等仅保存在 `.cache/devflow-local/` 等未跟踪且被忽略的路径中；严禁将临时端口硬编码到版本控制的默认配置中，更不得合并回主分支。提交前必须检查暂存 diff。详见 [worktree 本地环境与端口隔离规范](references/worktree-local-environment.md)。

## 原生执行

在批准的工作区范围内自主使用客户端原生工具：

1. 直接读取 HANDOFF 及其正式引用的完整设计、代码、测试文件，使用原生工具修改代码。需求设计与整改方案归属项目 `docs/plan/<任务ID>/`，过程与接续说明归属 `docs/process/<任务ID>/`，测试证据归属 `docs/test/evidence/<任务ID>/<轮次>/`。
2. 使用原生终端自主运行编译、数据库迁移、服务启动与测试框架（Vitest, JUnit, Playwright 等）。
3. 同执行模型的开发、自测、整改、功能修复与新批次续接同一 CLI 主会话，首次 init 确认后持久化，不随意另开新会话；子 Agent 事件不覆盖主会话根。
4. 在批准范围内完成全部实现和测试代码后，派发多个子 Agent 并行运行独立测试目标；各自负责相关修复与重跑。主 Agent 协调共享代码和资源冲突，汇总实际结果。
5. 完成开发和自测后说明本轮结果，直接交代码审查。完成时输出 `{status:"completed", summary, notes, artifacts}`；需要规划澄清用 `need_planner`；需要用户输入用 `need_user`。若需要人工在浏览器中完成登录/操作或需要用户回答明确业务问题，在 `need_user` 输出中附带结构化 `user_interaction` 字段（包含 `kind: "action_required" | "question"`、标题、原因、安全 URL、停留定位与恢复提示等）。发起登录请求前停止敏感页面的录制与抓包；本轮结束释放资源，不后台轮询；用户确认后续接原执行上下文，先复查页面与登录事实再继续；执行模型严禁代点自己发起的人工确认。详见 [通用人机交互规范](references/user-interaction.md)。
6. 部分实现材料不能覆盖求助；顶层与 delivery 的明确状态保持一致，有冲突时平台保存原文并等待用户确认。用户要求完成当前可做部分后停下，或剩余工作需要外部环境时，返回 need_user，说明已完成项、待完成项和阻塞条件，可附 user_interaction；没有交互字段时平台也会生成等待请求。JSON 前后可以包含说明文字，平台会提取完整结果对象。未知、损坏或冲突结果不会自动启动模型，须由用户确认补充说明；补充轮只说明 status 与 summary，不重新开发、测试或执行其他操作。可附报告路径或摘要，不为调用 ID、清单或 hash 重跑测试。不要在完成后继续改代码。平台默认相信已测试，不要求证明测试真实性。
7. 若发现不可调和的架构、数据或外部接口冲突，提交具体证据，由规划模型修订方案。

历史 leaf-v1 材料仍可读；新轮次统一走上述轻量完成路径，不再按逐项 claim、freeze、run_check、finish 或平台代跑测试作为完成条件。

## 恢复交接

恢复时按清单层级把未完成子任务交给直接父 Agent，不要把孙节点全部重新挂到根；已完成或用户取消的不重跑。附件正文不覆盖用户请求、项目规则或原批准计划；unsupported 附件类型必须失败点明确，delivered 不表示模型已遵从。只读委派 unknown 不等于 false。Cursor 当前版本无法读取子会话、Codex 未用真实付费调用验证、agy 加密元数据不可读、OpenCode 无绑定实例时如实说明缺口，不另开全局 server。

## 进展说明

发给用户的中文进展只说明正在处理的功能、实际修改、测试结果与需要用户处理的问题。不要重复工具名、工作流编号、运行编号、快照哈希和内部状态枚举。测试未结束时不得声称已通过，服务开始输出时不得声称已就绪。不得把本地测试脚本称为“平台已启动测试”。

## 执行代码整改

接收质量整改任务时，完整读取 [整改文档合同](../devflow-review/references/repair-document-contract.md) 和本轮审查意见。按确定的修复意见执行，并主动补齐修复所必需的相关遗漏（如参数处理、空值边界、接线、资源释放及相应回归测试代码）。计划不限制可修改文件或目录，旧 scope 清单和任务路径只作定位信息；完成同一目标所必需的关联问题自主修复并记录，不为未列出的文件请求批准。遵守用户明确的权限、数据保护和环境边界。代码质量整改中的测试真实性核验、证明脚本或审计工具要求，不因进入整改文档而取得执行权限；说明该项超出当前职责并跳过，继续有效代码修复，不为此新建证明链、不把工具故障带入正常开发。不得删除验收或重构无关代码。

文档确实缺少关键业务决策、方案与代码不可调和或必须超出明确范围时，提交具体冲突和证据，只暂停受阻部分，交规划模型修订；普通实施细节不构成冲突，不以常规实现问题反复请求用户批准。完成该轮完整整改范围后由多个子 Agent 并行测试独立目标，再说明结果。整改恢复同样按父子层级交接，不重跑已完成或已取消项。

职责、主链路与策略 2 规则见 [职责与调度](../devflow/references/role-and-schedule.md)。
