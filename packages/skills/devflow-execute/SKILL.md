## 指定计划为执行依据，禁止执行模型另建计划

适用于用户明确要求“按这份计划/整改文档完整执行”以及 DevFlow 已交接计划的实施、自测、整改、恢复和接管写入阶段；同一工具或模型承担多个角色时也适用。

1. 执行依据是用户指定或工作流当前已批准的原计划及其正式引用的设计、整改文档。开始前完整读取正文，核对文件路径、现有版本/hash（如有）及原任务/验收编号；HANDOFF.md、索引或摘要未含完整正文时继续读取原文，不能凭摘要开工。
2. 禁止执行模型额外创建、重写或更新另一份实施计划来安排执行，包括 implementation_plan.md、客户端计划工件、局部整改计划和换名字的替代方案；禁止先重新规划、再只按自写计划开发。客户端惯例要求“先写计划”不构成例外，也不能自己切换为规划角色、自行批准或覆盖原计划。
3. 执行前在已有进度记录中按原计划逐项映射“原编号/章节 → 实现位置 → 测试与证据 → 状态”。只允许维护标明“执行进度（非计划）”的事实清单、日志和测试记录；不重新定义范围、技术路线、接口、依赖顺序或验收标准，不把局部清单当作全部任务。
4. 按原计划已确定的设计连续实现和自测，可决定不改变设计的局部代码写法、测试函数名和命令参数。不得以“拆解”“优化”“先做核心部分”为由漏掉端到端接线、异常/恢复路径、测试、安装或其他必需交付。
5. 原文缺失、冲突、不可实施或需要超范围时，提交具体原章节、代码事实、影响和最小冲突，交规划模型修订原计划的正式版本；暂停受阻部分，不擅自另写方案执行。明确不依赖冲突的原计划任务可继续。只有确需改变业务需求/批准范围时才依既有规则请用户决定。
6. 恢复、反馈修复和质检整改都重新核对同一原计划及正式修订；最终按原编号逐项提交真实结果和未完成项。自写清单全勾选、旧缺陷探针不再命中或部分测试通过，都不能代替原计划全部要求完成。

## 所有模式的测试与质检要求

按 `../devflow-test/SKILL.md` 执行单元、集成、E2E 三层测试；各层默认必需，只有计划已批准的不适用项可豁免。E2E 必须覆盖新需求的全部业务流程及真实 diff、上下游和共享依赖识别出的受影响旧功能回归；逐项关联场景 ID、操作、输入、结果断言、实际用例和原始报告。用户反馈修复需加入缺陷回归并检查受影响旧流程。

Web E2E 使用真实浏览器访问真实应用、后端与测试数据；仅接口请求、jsdom、整条业务链的 mock、截图或页面可见不算完整 Web E2E。浏览器操作已包含在 E2E，不再独立执行 OpenTabs/真实浏览器验收。人工功能确认仍由用户完成，不能用 E2E 报告代签。

报告必须对应当前代码和环境，保留真实执行记录和逐用例结果。零用例、跳过、漏场景、恒真断言、旧报告不算通过；用例通过数不能替代覆盖核对。

### 原生执行与终局核验模式 (native-v2)

在 native-v2 模式下，执行模型在批准的工作区范围内自主使用客户端原生工具：
1. 原生文件工具：直接读取 HANDOFF.json（旧入口为 HANDOFF.md）及其正式引用的完整设计、代码、测试文件，使用原生工具修改代码。无需通过分页接口反复抓取。
2. 原生终端与测试：使用原生终端自主运行编译、数据库迁移、服务启动与测试框架（Vitest, JUnit, Playwright 等）。
3. 连续开发与自测：在批准范围内跨模块连续开发，自行排查修复编译和断言错误，无需逐细项频繁开始与声明。
4. 终局核验交付：所有必需验收项自测通过后，按本轮 HANDOFF 的输出合同返回 {delivery: ...}，或在提供 worker MCP 的旧入口调用 `devflow_deliver` 提交交付清单（包含实现结果、宿主真实执行记录、原始测试报告路径及用例映射）。DevFlow 被动记录宿主工具的开始和结束事件，核对测试输入版本及报告。交付核验通过后等待本轮执行器成功结束，由程序单独调度正式计划逐项复核；复核修复与新交付完成后再交规划模型审查，通过后才开放人工核验；不要在交付后继续改代码。报告写入各仓库 .reports/ 或 reports/ 目录，或项目已登记的报告路径。清单必须包含 schema_version=v2、唯一 submission_id、workflow_id、run_id、conversation_id、plan_revision、plan_hash，以及实现项、执行、报告和场景映射。缺少本轮开始/结束事实时返回证据不足，不沿用旧报告。
5. 设计冲突上报：若发现不可调和的架构、数据或外部接口冲突，调用 `devflow_report_conflict` 提交具体证据，由规划模型修订方案。

### 受管细项模式 (leaf-v1 兼容)
1. 首先调用 devflow_execute_context，然后按 section 读取 plan、skill、tasks、tests、scope、feedback、environment。next_offset 非 null 必须继续读取完整分段；参数可用 section=tool、id=工具名查询。
2. 核对 workflow、revision、package hash、阶段和 task IDs；不匹配就报告阻塞。
3. 按 DAG 顺序实施，使用受控文件工具与已登记 check ID。
4. 修改前读取文件并取得 hash；变更必须符合允许路径和既定核心算法。
5. 不修改冻结计划、进度真值、控制配置、权限、共享仓库状态或发布凭证。
6. 编写有效回归测试，证明目标失败能被测试捕获，再实施局部修复。
7. 检查命令由 Runner 执行；禁止把文字总结或旧报告当作通过证据。
8. devflow_claim_task 仅提交实现声明，程序验证后才会勾选。
9. 当前计划不可行、需要新增范围时提交 blocker 并停止。
10. 用户反馈在原范围内则按反馈修复；仍需重跑验证，不绕过人工验收。
11. 明确报告本轮实现、检查、未完成项与阻塞；不直接提交、不推送、不发布。
12. 本轮结束释放模型资源；不要自己循环等待长测试或浏览器资源。


以下受管检查、环境工具和 freeze/finish 顺序仅适用于旧模式；native-v2 使用原生工具测试并通过 devflow_deliver 交付，平台不重复执行同一轮测试。

开发每个可验证功能后立即调用 devflow_run_check 运行相关单元测试；模块接通后运行集成测试，链路可操作后运行 E2E。开发阶段运行检查不会冻结整个任务，不要求所有细项先完成。通过结果绑定检查时的代码快照，修改代码后需要重测。

需要构建、启动或重启服务时调用 devflow_environment(action=start/restart)，使用 status/logs 获取真实健康状态和日志。启动失败由你读取诊断、修复并再次启动；不能把常规构建或语法错误交还用户。所有功能实现后调用 devflow_freeze，逐项重新执行交付测试，全部通过后 devflow_finish。

细项声明只证明提交了实现记录。开发完成与验证完成是两个维度：实现及相关基础检查通过才显示开发完成，当前代码与环境的关联测试全部通过才显示验证完成，开发阶段测试也计入进度。最终交付仍需冻结快照并完成全套交付验证。重复提交相同代码不会增加进度；优先读取 diagnostics.checks 的最新原始失败记录，修复实际失败项。

## 旧受管模式的操作授权、用户指导和故障恢复

- 需要未登记的诊断、依赖安装等命令时，调用 devflow_request_operation，提供具体 executable、args、repo_id、cwd 和原因。授权在工作台完成，不能要求用户另开客户端，也不能尝试原生终端绕过。提交请求后结束本轮；系统会保留会话并在用户决定后恢复。
- 每次恢复都读取 feedback、operations、diagnostics。已批准请求使用 devflow_run_operation(request_id) 执行一次；拒绝请求不能执行，按用户意见调整。等待授权不属于失败。
- 用户可以在工作台中途补充指导。旧轮次可能被结束，恢复后以最新反馈和计划为准，保留已有实现，不从头重做。
- 检查、构建和启动错误先自行排查修复，修复失败时可调用 devflow_diagnose 请求规划模型只读诊断。新增范围必须返回完整修订计划并等待审批。诊断不等于独立复核，不能据此声称交付通过。

## 细项进度

上下文 task_model=leaf-v1 时，先调用 devflow_start_task(task_id, summary) 开始细项；同一任务可更新 summary 描述实际进展。文件修改只能落在当前细项批准的 paths。前置任务需完成实现核验。完成后调用 devflow_claim_task，平台检查 completion_checks 并保存文件哈希；检查不通过就修正，不能跳到下一项。实现过程中运行关联测试；任务全部实现后 freeze，再按交付测试清单逐项运行，直至 finish。旧计划没有 task_model 时继续旧合同，不能自行猜测子任务或上报不存在的编号。

测试失败只影响验证结果，不能据此重复声明所有未变化的实现。代码实际修改后才重新核对相应实现。允许切换到前置细项修复；切换不会把上一细项自动标为完成。只匹配到类名、import 或占位代码不代表业务已经实现，禁止据此虚报。测试必须操作目标行为并验证结果；恒真断言不能作为业务测试。

发给用户的中文进展只说明正在处理的功能、实际修改、测试结果与需要用户处理的问题。不要重复工具名、工作流编号、运行编号、快照哈希和内部状态枚举；这些由平台技术详情保存。测试未结束时不得声称已通过，服务开始输出时不得声称已就绪。

## 执行代码整改文档

接收质量整改任务时，完整读取 [整改文档合同](../devflow-review/references/repair-document-contract.md) 和本轮冻结的完整整改正文。核对 finding_id、交付/计划版本、允许修改文件、前置依赖和验收条件，按确定步骤执行；只可决定不改变既定设计与行为的局部写法，不得自行换方案、扩大接口、删除验收或顺手重构。

文档缺少关键设计、与实际代码冲突或必须超出范围时，提交具体冲突和证据，交规划模型补全或修订；不能自行猜测，也不以常规实现问题反复请求用户批准。交付回执逐项关联 repair_item_id、实际文件/函数、真实测试及报告和未关闭事项。只有原缺陷验证及要求的旧功能回归都通过，才能声明对应整改项完成。

## 程序调度的正式计划逐项复核

native-v2 每轮初始开发或正式质量整改完成后，执行顺序固定为：开发与自测 → 交付核验及成功退出 → 程序独立调度执行模型按正式计划逐项自查、修复遗漏并重测 → 规划模型独立质量审查。首轮质量通过才开放人工核验；人工功能问题修复同样必须经过程序自查，再直接交用户复测，全部功能确认后进入最终质量审查。人工前、人工后两关分别计数；各关连续三次执行模型整改仍不合格，程序调度规划模型接管修复，自查后再进入审查。不得用首次完成自述代替程序自查，不得伪造人工确认。

复核必须重新读原始计划及当前正式批准的整改/修订全文，按原编号关联真实实现、测试和未完成项。使用当前运行的 HANDOFF.json 中 authorities、check.check_ids 与 check_schema；旧入口使用 AUTHORITATIVE_PLANS.json、HANDOFF.md、handoff.json 和 self_check.check_ids，均以程序交付的真实版本为准；正式范围变更引用对应批准修订。禁止创建或使用 implementation_plan.md、客户端计划工件或其他局部计划替代原文。逐项报告属于执行事实记录，不是另一份实施计划。

当前复核轮次的交付清单必须包含 plan_self_check，并符合本轮 check_schema（旧入口为 plan-self-check.schema.json）：绑定请求、源交付、当前 run_id、plan_revision、plan_hash、authority_hash；完整覆盖全部 check_ids，逐项提供代码/测试报告/用例定位，记录发现问题及实际修复证据。遗漏、重复编号、空证据、未解决问题、旧轮次/旧计划/旧输入报告、进程失败均阻断规划审查；代码改动后提交当前轮次有效测试与新交付。正常开发轮次不能自行填报告冒充程序调度。

程序校验报告及当前交付的绑定和完整性，不能保证模型判断语义正确；规划模型仍须独立检查实际代码、测试真实性与原计划覆盖。缺少本轮有效自查报告不得放行。自查不计入任何质量关卡的三次拒绝次数；暂停/停止后不得自行继续，不新增后台轮询，不改变既有界面布局。
