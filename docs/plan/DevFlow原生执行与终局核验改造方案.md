# DevFlow 原生执行与终局核验改造方案

<!-- devflow-plan-authority:v1 -->
## 指定计划为执行依据，禁止执行模型另建计划

执行模型收到本方案、用户指定的整改文档及其正式引用后，必须完整读取并直接实施，禁止额外创建、重写或更新 implementation_plan.md、客户端计划工件、局部实施/整改计划或其他替代方案来执行。不能先自行重新规划，再把原要求压缩成局部修改范围。规划模型正式产出的整改版本必须关联原计划，保留其未关闭要求；执行模型不得再次改写。

已有进度记录只能标为“执行进度（非计划）”，逐项关联原任务/验收编号、实现位置、真实测试证据和未完成项，不变更技术路线、接口、依赖顺序或验收标准。原文缺失、冲突或不可实施时提交具体事实交规划模型正式修订；暂停受阻部分，可继续明确不受影响的原计划任务。相同工具/模型承担多个角色时也不得自行越过规划修订权限。

交接、恢复、测试和复核都回到原计划及正式修订的完整要求，核对真实成功与适用的拒绝/异常流程；自写清单全部完成、探针不再命中或部分测试通过，不构成全任务完成。本节是提示与交接规则，运行时校验是否已实现须另以代码和测试证明。

日期：2026-09-15。依据：本会话确认的职责边界及用户要求“按计划完整完成修改和测试”。

## 1. 目标

规划模型提供完整、确定的开发设计；执行模型使用客户端原生工具连续完成实现、测试和修复；DevFlow 负责整体调度与最终结果核对。保留详细设计，取消逐细项状态、逐文件代理、逐工具权限进程和程序重复调度测试。降低额外 Token、CPU、内存与磁盘 IO。

## 2. 职责

规划必须确定需求范围、技术栈、架构与模块边界、数据库表字段关系索引约束、迁移与数据库文件管理、主要类和接口契约、核心算法与事务异常逻辑、环境配置和服务启动要求、测试框架与层次、测试数据初始化隔离清理、验收场景与预期结果、模块依赖和实施顺序。方案只有一套确定设计，不把总体设计交给执行模型。

执行模型决定具体编辑动作、测试函数名称、样例值、fixture/mock、断言写法和实际命令调用，并按既定架构完成调试。业务参数由设计规定，测试样例参数由执行模型填写。可在批准范围内连续修改多个模块，不办理逐细项开始/声明。普通编译、配置和实现错误自行修复；架构、数据结构、外部接口或核心业务规则必须变化时，提交具体冲突证据，由规划模型修订原方案并沿用计划审批规则。

DevFlow 保存方案、审批与历史，管理工作流和执行会话生命周期，展示已有输出，接收交付，批量核对和更新完成状态，衔接人工验收、独立复核与提交。程序不控制每次编辑和测试。

## 3. 流程

需求调查 → 完整方案 → 用户批准 → 原生执行会话 → 开发/测试/修复 → 交付清单与终局核对 → 程序调度执行模型对照正式计划逐项复核（修复、重测、新交付） → 规划模型代码质量审查 → 人工功能核验 → 规划模型终审 → 提交。任一整改轮次均须重新经过执行模型正式计划复核。

终局发现问题时一次性汇总反馈给原会话，补齐后再次交付，不创建平行任务，不清空实现和历史。保留暂停状态，不自动恢复原工作流。

## 4. 工作包与计划合同

一份设计正文加一份精简结构化索引。索引保留需求、模块、任务、验收项、依赖与设计章节引用，不重复存储整段正文。验收项使用稳定业务编号，规定验证层次、场景和预期结果；具体测试名称、命令参数不在规划阶段锁定。

新合同采用 native-v2 模式；旧 leaf-v1/legacy 合同可读并保留历史。首次交接用原生文件工具读取完整工作包，不经过 1000 字符分页。恢复保留 conversation_id，交接新增反馈和方案差异，避免重复读取全部设计。

## 5. 原生执行

允许客户端原生读取、搜索、局部修改、终端、浏览器与测试工具。取消仅准许 devflow_worker 的策略、每次工具调用新起 PowerShell/Node 的 PreToolUse 链、当前细项路径写入门禁。工作目录和整体批准范围继续有效。

执行模型尽早验证依赖、数据库初始化、构建、最小应用启动及页面/接口可访问，再扩展业务。按方案框架自主安排单元、集成、E2E 与相关回归。DevFlow 不在模型结束后再运行一套测试。最终交接工具只负责接收结果或报告真实设计冲突，不提供受管测试运行入口。

## 6. 交付清单

包含四组信息：

1. 实现结果：需求/模块/任务映射、实现位置、方案修订、未完成项。
2. 原始执行记录：来自宿主已有工具记录的调用标识、实际命令和目录、开始结束时间、退出码、输出位置。不得以模型自报退出码替代。
3. 原始测试报告：仓库相对路径、格式、所属原始执行、用例与验收项映射。
4. 输入指纹：业务源码、测试源码、配置、锁文件、迁移和脚本；排除依赖目录、产物、日志和报告。不能只用 Git HEAD 代表未提交工作区。

验收项 → 具体测试 → 原始工具执行 → 框架原始报告。原始输出与模型说明分别保存来源。缺少宿主执行记录时判证据不完整，不编造成功、不改用 DevFlow 重跑。

## 7. 终局核验算法

核对 workflow/run/conversation/plan/workspace 身份；遍历全部必需验收项；关联宿主原始执行与真实退出码；解析 JUnit、Vitest、Playwright 报告；检查必需场景不缺失、不失败、不跳过，空报告不通过，用例可唯一定位；核对报告来源和最终输入版本；检查归档文件哈希；汇总全部问题；通过后事务内批量更新状态。

测试名称不与规划函数名强绑定。额外用例不能代替必需场景。模型声明已实现、证据核对通过、人工验收、独立复核分别显示。报告只能证明执行结果，不证明业务覆盖充分；测试合理性由最终审查判断。

验证批次边界生成文件指纹，终局核对一次，不对每条测试调用整仓库 Git snapshot，不创建临时 Git index。模块输入及依赖映射支持复用未受影响的证据；公共配置变化使关联测试失效。修复只补做失效/缺失项，不能因阶段切换让所有证据无条件作废。

## 8. 模块与类

沿用 TypeScript、Fastify、React、SQLite。

- Engine：管理方案、执行、交付、验收和复核大阶段。
- Scheduler：调度整体工作流与执行名额。
- HandoffBuilder：完整工作包与恢复增量。
- AgyNativeAdapter：原生启动、续接、输出与生命周期。
- NativeRunRecordReader：读取宿主已有原始工具执行事实。
- DeliveryImporter：接收交付清单并归档报告。
- EvidenceValidator：验收映射、结果、来源与版本核验。
- WorkspaceFingerprintService：验证批次输入指纹。
- BufferedEventSink：按字节和时间缓冲日志，限制内存。
- 现有报告解析器继续使用。

新路径退出 start_task、claim_task、apply_files、强制 read/search、run_check 和 freeze 依赖。旧路径仅为历史兼容，不成为新任务默认。

## 9. 数据存储

保留 SQLite entities/events 和现有 ID，不新建第二套业务库。新增实体类型：

- delivery：工作流、轮次、方案版本、交付状态、输入清单引用、提交时间。
- test_execution：宿主调用标识、命令、目录、时间、退出码、报告引用。
- acceptance_result：验收项、具体执行/用例映射、结果、原因。
- input_manifest：模块输入范围、文件指纹、时间。
- delivery_issue：核对问题、关联模块/验收项、处理状态。
- run_usage：宿主真实提供的输入/输出/缓存/推理 Token 数值。

数据库保存元数据和索引，日志一份、报告一份，不将每个输出块重复写 JSONL 与数据库。统计 token 字段不按凭证抹除。历史证据保留，但不直接转为新模式有效证据。

## 10. 资源与 UI

日志按 500 ms 或 64 KiB 批量写入；关键状态可靠持久化；前端 500 ms 合并刷新；普通输出不逐条成为数据库业务事件；查看页面不扫描源码、不计算哈希、不启动测试。缓存有字节上限。

默认 1 个开发执行器、1 套活动验证环境。框架并行度由项目方案规定，模型落实原生配置。同一工作流复用正常服务。暂停保存现场并停止继续执行；停止结束该工作流拥有的执行进程和服务；保留环境由用户明确选择。恢复服务不自动续跑已暂停任务。

界面展示大阶段、近期模块活动、原始输出和阻塞。任务完成在终局批量更新，不为进度条强制调用工作流工具。

## 11. 迁移

在原工作流迁移，保留 ID、计划、代码、会话、暂停状态和历史。旧计划中的设计与场景转为新合同，原函数名仅作历史关联。迁移执行模式由原工作流的方案审批确认。不擅自更新业务代码，不恢复真实任务，不重建并行任务。

项目从 D:/Code 移到 C:/Code 后，使用真实项目根和相对路径。根路径重绑定须核对仓库身份，历史路径字符串不影响逻辑 ID。迁移配置不得静默同步不同工作树代码。

## 12. 实施顺序

A. 保存本方案，核对迁移后的目录、未提交修改、测试基线。
B. 新合同、原生工作包/适配器、阶段交接；旧暂停任务保留。
C. 原始执行事实、批次指纹、交付导入与终局批量核验。
D. 进度、日志批量、资源默认值、停止/恢复及路径迁移。
E. 更新规划/执行技能和使用文档，完成原生接入、报告、状态与 UI 测试。
F. 完整 typecheck、unit/integration、生产构建、Playwright E2E、真实原生执行 smoke；记录真实结果和外部限制。

## 13. 验收

- 原生终端和编辑工具可用，无逐工具额外权限进程。
- 可跨模块连续实现，不调用细项工具也可交付。
- 已有测试结果导入时程序启动测试次数为零。
- 缺报告、伪报退出码、错误轮次、过期指纹、失败和必需跳过均不能通过。
- 报告名称可与规划业务编号不同，映射完整则通过。
- 一次返回全部缺项；未变化证据可复用。
- 页面读取不触发文件哈希或 Git 写。
- 日志不逐块重复持久化；资源默认值生效。
- 暂停、重启、同会话续接、旧合同与人工验收/复核门禁回归通过。
- 以真实工具次数、额外进程、快照/写入次数和宿主 Token 统计验证改进；不把静态测试冒充真实模型验证。

## 程序调度的正式计划逐项复核

native-v2 每轮初始开发、正式整改或用户反馈修复完成后，执行顺序固定为：开发与自测 → 交付核验及执行成功退出 → 程序再次调起执行模型对照正式计划逐项复核 → 修复遗漏/偏离并重新自测、交付核验及成功退出 → 规划模型独立代码质量审查。不得直接开放人工核验或把首次完成自述当成这次复核。人工核验前的质量审查通过后才交用户；人工核验后的整改也不能跳过执行复核。

复核必须重新读原始计划及当前正式批准的整改/修订全文，按原编号关联真实实现、测试和未完成项。使用 AUTHORITATIVE_PLANS.json、HANDOFF.md 与 handoff.json 中程序给出的版本及 self_check.check_ids；正式范围变更引用对应批准修订。禁止创建或使用 implementation_plan.md、客户端计划工件或其他局部计划替代原文。逐项报告属于执行事实记录，不是另一份实施计划。

当前复核轮次的交付清单必须包含 plan_self_check，并符合 plan-self-check.schema.json：绑定请求、源交付、当前 run_id、plan_revision、plan_hash、authority_hash；完整覆盖全部 check_ids，逐项提供代码/测试报告/用例定位，记录发现问题及实际修复证据。遗漏、重复编号、空证据、未解决问题、旧轮次/旧计划/旧输入报告、进程失败均阻断规划审查；代码改动后提交当前轮次有效测试与新交付。正常开发轮次不能自行填报告冒充程序调度。

程序校验报告及当前交付的绑定和完整性，不能保证模型判断语义正确；规划模型仍须独立检查实际代码、测试真实性与原计划覆盖。缺少本轮有效自查报告不得放行。自查不计入任何质量关卡的三次拒绝次数；暂停/停止后不得自行继续，不新增后台轮询，不改变既有界面布局。
