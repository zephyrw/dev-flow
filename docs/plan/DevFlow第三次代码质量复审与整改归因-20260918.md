## 4. 本轮全部确认问题及确定改法

### TR-01 / P1：外层明确不确定，仍可能被当成完成

关联：CQ-01、RR-01。位置：[round-intent.ts:98](C:/Code/system-handle/packages/core/src/round-intent.ts:98)、[round-intent.ts:119](C:/Code/system-handle/packages/core/src/round-intent.ts:119)。

触发一：`{status:"unclear", delivery:{status:"completed"}}`。recognizedExecutionIntent 没有识别 unclear，优先四级按“外层识别成功”决定，因此采用内层 completed。非空未知外层状态也会退到内层。

触发二：明确 unclear 或未知状态经 deliverySubmit 入口，且有非空 implementations/test_executions。normalizeDeliveredRound 又将 unclear 提升为 completed。

后果：应向模型澄清的结果仍写完成事件并进入代码审查。不是要求验证完成声明；问题是覆盖了模型当前给出的意图。

确定整改：

1. 归一化结果保留 `intent_source: outer|nested|legacy_submit|missing` 与“是否提供非空意图字段”。先判断字段是否存在，再识别含义。
2. 外层有 status/verdict 时，外层独占意图来源；明确 unclear 或未知值均为 unclear，不再读取内层意图。外层未给意图时才取内层。
3. 旧提交兼容推断只在外层和内层都没有显式意图、且调用上下文明示旧完成提交时生效；不能覆盖明确的 unclear、未知值或求助。空数组不推断完成。
4. ProfileRuntime、MCP、原生回执继续共用一个规范化入口，平台身份隔离保持在其前面。原始结果保留为资料。

行为目标：外层 completed/need_user/need_planner/unclear/未知值分别保持语义，附件内容不改意图；相同输入在所有入口一致。

归因：**上轮明确要求未全部落实**。RR-01 第 43 行已经写明“内层仅在外层未提供意图时补充”；无需新业务决策。

### TR-02 / P1：续接只传了会话 ID，最小补问和默认配置审查仍不完整

关联：CQ-01、CQ-02、CQ-09、RR-03。位置：[engine.ts:1367](C:/Code/system-handle/packages/core/src/engine.ts:1367)、[engine.ts:2639](C:/Code/system-handle/packages/core/src/engine.ts:2639)、[profile-runtime.ts:210](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:210)、[runtime.ts:1177](C:/Code/system-handle/packages/runtime/src/runtime.ts:1177)。

分支 A：unclear 已进入自动续问队列，但 takeContinuation 丢掉 intent/original_text，Run 仅传 continuation_conversation_id。运行时仍发送完整开发、自测或完整代码审查指令。结果是在旧会话重新布置整轮任务，而不是只补当前结论。

分支 B：没有 execution_spec_id 的默认配置任务，以及历史任务的新 lightweight 轮次，LocalRuntime.review 仍走旧分支；该分支固定 codex exec，无 resume，材料也没有用户反馈正文。审查 need_user 后，用户回答不能送达原审查，可能反复询问。

确定整改：

1. continuation 定义为完整运行输入：`kind: intent_clarification|user_answer|runtime_resume`、source_run_id、purpose、role、phase、conversation_id、original_text、questions、answer。会话归属使用来源运行，不混用执行和规划会话。
2. 等待记录转成目标 Run 的 continuation 与目标运行持久化在同一事务中完成，再关闭该等待记录；重试从 Run 读取，不依赖已删记录。
3. intent_clarification 仅发送“请补充刚才这轮的结果意图”及原始回复，继续原角色会话；不附带要求重新完成全部开发/测试/审查的主任务指令。need_user 的 answer 与原问题一起传入原审查/执行上下文。
4. LocalRuntime.review 的轻量分流与 execute 共用 isLegacyProtocol，不能只看 execution_spec_id。新轻量审查统一进入 ProfileRuntime；真正已运行的 legacy 会话保留原协议收尾，续接时也要传递用户回答。
5. 平常新一轮独立质量审查仍开新会话；只在明确 continuation 时续接。真实会话不可恢复保留运行故障原因，不改成代码质量拒绝或静默重开整轮工作。

行为目标：不明结论只补问结论；用户回答送达原角色；默认配置与显式 spec 路径行为一致；补问不创建新整改轮次、不计失败。

归因：**原要求明确，运行适配器与 prompt 构造的端到端实现未完成**。我前两轮也没有把默认配置分支查全；不能仅用“已有 resume 字段”认定关闭。

### TR-03 / P1：规划求助的问题没有传递，旧等待记录会污染后续恢复

关联：CQ-01 的 need_planner、RR-03 的来源续接。位置：[engine.ts:3516](C:/Code/system-handle/packages/core/src/engine.ts:3516)、[engine.ts:2305](C:/Code/system-handle/packages/core/src/engine.ts:2305)、[profile-runtime.ts:83](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:83)、[recovery.ts:171](C:/Code/system-handle/packages/runtime/src/recovery.ts:171)。

当前可达链：执行 need_planner → waiting_context 保存 planning 意图和执行会话，但没有问题正文 → runPlanning 清除唯一含摘要的 blocker，也不把求助结果放进规划材料 → 规划成功、用户批准、新执行启动 → 旧 waiting 因没有 continuation=true 仍未清除 → 新执行发生运行故障后恢复 → resumeApproved 读到旧 planning 等待记录，错误再次派发规划。

这是两个同源后果：首次规划拿不到它要回答的问题；未来与求助无关的执行恢复被旧上下文改派。

确定整改：

1. need_planner 使用独立 `planning_handoff` 记录，保存唯一 handoff_id、源执行 run/角色/会话、源计划版本、求助原文/summary/notes/questions、目标 planning 角色和处理状态。此记录不是用户等待记录。
2. runPlanning 在创建规划 Run 时绑定 handoff_id，把求助正文、当前正式计划及源执行背景作为规划输入。规划续接只使用规划角色自己的会话；执行会话仅作来源引用。
3. 交接记录由 pending → assigned(target_run_id) → resolved/superseded。开始派发只标记归属，不提前删除正文；失败恢复读取同一记录，规划成功或被新需求取代后关闭。消费与 Run 创建须原子化，禁止残留待恢复 continuation 到下一执行轮次。
4. 沿用现有 PLANNING 与正式计划修订/确认行为，不为传递问题新增平台阶段或测试关卡。用户审批语义按既有批准范围规则执行，不由执行模型自行批准。
5. resumeApproved 只处理属于当前被暂停/失败运行或其明确续接链的等待记录；过期记录归档为 superseded，不改变当前恢复角色。对现存 need_planner 遗留记录，仅在其源运行/交接仍是当前规划来源时兼容转换，不能只凭 purpose=planning 抢占后续恢复。

行为目标：规划能看到真实求助；规划结束后新执行的暂停、网络故障恢复仍回执行；规划重试不丢求助也不串会话。

归因：**主审前两轮设计和审查遗漏**。原计划说了“进入规划澄清”，却没有给出问题载荷、消费/失效规则；我也没有发现这条完整链。无法从现有未提交工作树准确断言它在哪轮首次引入，不能把责任推为执行模型能力不足。

### TR-04 / P1：审查计数先落库，整改任务与派发稍后落库，中断恢复会用错关联

关联：CQ-03、CQ-04、RR-04；保留 RR-06 已修的多次运行尝试。位置：[quality-coordinator.ts:328](C:/Code/system-handle/packages/core/src/quality-coordinator.ts:328)、[engine.ts:2975](C:/Code/system-handle/packages/core/src/engine.ts:2975)、[engine.ts:3012](C:/Code/system-handle/packages/core/src/engine.ts:3012)、[engine.ts:3044](C:/Code/system-handle/packages/core/src/engine.ts:3044)、[repair.ts:15](C:/Code/system-handle/packages/core/src/repair.ts:15)。

当前协调器先事务提交 gate/current_review_id/计数/quality_review/dedup。Engine 随后发布文档、可能 await submitValidatedPlan，再写新 assignment，最后另一个事务转状态和写 outbox。

若在两个持久化部分之间进程中断，数据库可留下“新 gate + 旧 assignment + 无下一派发”。重启后的 resumeApproved 直接恢复实现；非 planner 旧 assignment 被保留。后续完成整改再审查时，assignment.source_review_id 与 gate.current_review_id 不符，该完整整改不能正常计数，执行还可能拿到旧整改正文。

同源残留：Engine.prepareNativeRepairReview 每次显式传当前 gate.cycle，覆盖协调器已经修好的首次 canonical 默认值；尚未完整应用的旧结果重入仍可能被构造成不同周期。

确定整改：

1. 按 workflow_id + review_run_id 建立一次性的质量转移记录，包含规范化结果、运行创建时绑定的 phase/cycle、原完成事件、决定和 next_assignment_id。首次接收后不得从当前 gate 重建这些默认值。
2. 在任何 gate 修改前准备好整改正文和可选计划的内存数据。需要异步读取的准备工作先完成；把现有 submitValidatedPlan 中的必要记录写入抽成同步持久化步骤，不把 await 放进数据库事务。
3. 用同一个 Store.transaction 提交：规范化结果/去重、gate/计数、已消费完成事件、新 assignment、必要的计划记录及来源关联、当前工作流状态、下一角色 outbox。协调器可以返回计算结果，但不能先单独提交一半状态。next_assignment_id 在首次决定中固定。
4. 文档文件导出在事务成功后执行；失败仅影响文档导出状态，已持久化的整改正文仍能交给模型。调度器内存队列从提交后的 outbox 唤起，重启时以 outbox/质量转移记录接续，不凭旧 assignment 猜测要执行什么。
5. 已接受结果重投返回原决定，不增加计数、不创建第二个 assignment、不发意图补问。真实存储/内部状态异常保留原错误，不能由 engine.ts:2700 的全捕获分支伪装成“模型意图不明”。未识别模型输出才进入补问。
6. 对已有半写入记录，用其 quality_review/dedup 中的首次决定和源完成事件补齐缺少的派发关联；同一原决定最多补齐一次，不重评、不重新计数。无法确定来源时保留运行恢复问题，不从历史任挑一轮，也不清空已成立的三次接管。

### TR-08 / P2：补拉截断缓存后反复从最新页重扫，大积压仍迟迟不展示

关联：CQ-11、RR-10。位置：[event-catchup.ts:26](C:/Code/system-handle/apps/web/src/event-catchup.ts:26)、[event-catchup.ts:76](C:/Code/system-handle/apps/web/src/event-catchup.ts:76)、[use-event-catchup.ts:33](C:/Code/system-handle/apps/web/src/use-event-catchup.ts:33)、[server.ts:550](C:/Code/system-handle/apps/api/src/server.ts:550)。

当前 history 接口从新到旧分页。capPending 只保留最旧 4000 条，丢掉已读取的较新页；扫到缺口底部才交付前缀，然后清除 resumeBefore。下一批又从最新页重读刚截掉的记录。内存有界了，但补拉变成反复扫描，第一段仍要等整个缺口扫到底才可见。

静态推导例子：序号 1—10000、每页 200、批量 4000，分别扫描 50、30、10 页才投递完，共 90 次请求，而一次扫描只需 50 次。10 万条时约 6500 次而非 500 次。该数字是代码路径推导，没有运行压测；不把它描述为实际测得时延。

确定算法（须兼容旧控制器 before 接口）：

1. 游标只保存 `watermark`、本次 `targetUpper`、本次起点 `startWatermark`、`before`，不保存整批事件正文。没有追赶任务时读取最新页，首次页最大 seq 固定为 targetUpper；startWatermark 固定为旧 watermark。
2. 每页过滤到 `(startWatermark, targetUpper]`，立即投递 UI 按 seq 去重/排序。复用 [mergeEvents](C:/Code/system-handle/packages/presentation/src/activity.ts:20) 的有界展示；展示到最新页不代表历史已经全部补完。
3. 读取下一页时 before 取当前页最小 seq，单调向旧页推进；每轮至多 20 页/4000 条，预算耗尽保存 before，下轮从该位置继续。网络失败保留目标和已推进位置，不重新从最新页启动同一轮。
4. 到达 startWatermark 或该历史查询末尾后，才将 watermark 推至 targetUpper 并结束本轮。新到事件在下一轮的新目标中追赶；不能仅因投递了较新页就提前推进完成水位。
5. UI 不为追赶保存全历史正文；需要看被展示缓存淘汰的旧记录时继续使用历史分页。切换任务/卸载保留当前 stopped 隔离，丢弃旧请求响应。
6. 可选的新 after 接口不是本项依赖；必须让当前旧控制器兼容路径本身满足算法，不能只修新服务端。

行为目标：静态缺口每页至多读一次（失败重试除外），第一页即有内容，单批时间/内存有界，已完成水位不跨越尚未追赶的区间。

归因：**本次截断修复引入新的重复扫描问题，同时未落实已有分段展示要求**。原计划不是没写目标，但我此前没有给出上面的完整游标协议，具体算法设计也有可改进之处。
