## 4. 必须整改的问题

### C01 / P1：缓冲器篡改全局数组方法，且没有等待异步写入完成

**位置：** packages/core/src/buffered-sink.ts:84—123；tests/integration/native-rereview-regression.test.ts:469—493。

**证据：** R01、R02。

processQueue 在执行 onFlush 时覆盖全局 Array.prototype.push，抓取传入数组的函数；5ms 后若写入未完成，就调用捕获的函数，并让 Promise.race 结束。inFlightBytes 也在 onFlush 返回 Promise 时提前扣除。

结果包括：

- 慢磁盘写入或网络 sink 未完成，后续块已经开始，close 也可提前返回。
- 任意同步入队的业务回调都可能被提前调用。
- 在途字节统计不反映实际异步写入，maxMemoryBytes 仅触发更多排队，无法限制总积压。
- 同步异常被打印后继续，不能可靠向调用方传递持久化失败。

现有 S11 将释放函数放在 pending 数组中，产品代码恰好会捕获并调用它；这个测试不能证明真实 I/O 的串行性与排空正确性。

**整改：**

1. 删除覆盖 Array.prototype.push、捕获外部函数和 5ms Promise.race 的全部逻辑。
2. 队列仅 await onFlush 返回的真实 Promise。成功或失败结算后再更新在途字节。
3. 明确背压协议：达到上限让生产者等待或暂停读取；不能只把数据转移到无限 pendingQueue。
4. close/flush 必须等待排空，并把失败作为结构化错误传回；不得将失败写入认作成功。
5. 业务回调、测试释放器只能由其拥有者控制。测试使用独立控制的延迟写入、拒绝写入、突发日志和中文分块。

**验收：** 修复 R01/R02；并补充“写入拒绝导致 close 失败”“大于上限的持续输入确实受阻”“关闭后无在途任务”的断言。

### C02 / P1：仍不能证明报告对应当前代码；ctime 也不能代替测试时输入记录

**位置：** packages/evidence/src/delivery-importer.ts:66—101；packages/evidence/src/validator.ts:451—487。

**证据：** R03。代码变更后重新写入旧报告的原始字节，不篡改退出码、不恢复时间戳，交付仍通过。

InputManifest 和 VerificationBatch 都在 importDelivery 时生成。started_at 实际是交付时扫描时间，未记录测试开始前的输入。validator 比较源码与报告的 mtime/ctime，只能判断文件先后写入，无法判断报告究竟由哪一版代码产生。最后的 fingerprint 检查比较的也只是交付阶段先后两次扫描。

**整改：**

1. 由可信宿主适配层在模型自然调用测试工具时被动记录输入版本、调用 ID、仓库、开始/结束事件和报告摘要。程序只观察及核验，不重新调度或重复执行测试。
2. 同一验证批次关联完整代码、配置、依赖锁文件及测试输入；测试结束和交付时确认相关输入未变。
3. 报告绑定执行 ID 和字节摘要；复制/重写旧报告不能产生新测试事实。
4. 无法取得可信测试时版本时，明确返回证据不足。不要在交付时补建一个声称覆盖测试过程的批次。
5. 指纹读取错误必须失败并保留具体原因，不能以 unknown 或主仓指纹替代。

**验收：** R03 必须拒绝；测试后修改、删除、重命名源码或配置均能使对应证据失效；真实当前版本的报告可以通过。保留模型按需测试的自主权。

### C03 / P1：跨仓同名报告被合并，第二仓缺失或失败都可能判通过

**位置：** packages/evidence/src/delivery-importer.ts:116—140；packages/evidence/src/validator.ts:220—225、84—90、455。

**证据：** R04、R05。两仓都声明 .reports/unit.json，第二仓缺失或报告失败，UT01 和 UT02 仍全部通过。

archivedReports、reportHashes、归档路径和 parsedReports 仅以相对路径为键，第二份同名报告被 continue 跳过。后续“报告存在”查的是共享键。实现文件存在性及报告时间检查也仍使用首仓 workspaceRoot。

现有 S10 同时包含“第二仓范围外修改”和“报告缺失”。范围外修改让整单被拒绝，不能证明缺失报告自身被检出。

**整改：**

1. 使用明确的复合身份：repo_id、tool_call_id/执行 ID、report_path、报告摘要。各层键和归档目录保持一致。
2. 仓库 ID 必须存在且与工作目录、任务、场景一致。禁止未知仓库回退主仓。
3. 实现文件、报告读取和指纹都解析到对应仓库；同一仓库不同执行的同名报告也不能互相借用。
4. 验收映射必须从场景一路指向确定执行、该执行报告及确定案例。

**验收：** 拆开测试缺失报告、失败报告、越界修改；每个反例只含一个错误，断言具体 issue code 和仓库身份。补充主仓不存在但第二仓存在实现文件的合法场景。

### C04 / P1：提交前必需构建和检查被“任意有效交付”替代

**位置：** packages/core/src/engine.ts:1992—2043。

**证据：** R06、R07。必需命令配置为退出码 1 的命令，但未执行；宿主事实中只有 pnpm test。模拟合法验收及复核通过后，临时仓库实际进入 COMMITTED。

parser=none 或 id=build 时，代码以 hasBuild || activeRev 放行。其他必需命令若没有 matchingTests，则以 acceptances.length > 0 放行。已有交付证明了其他内容，不能证明这条命令成功。

**整改：**

1. 每条 required_before_commit / required_hooks 必须有对应的当前版本成功执行证据，不能靠任意交付或任意验收项兜底。
2. build/lint 等无案例报告的检查，也应关联真实宿主调用、退出码、代码版本和产物/日志摘要。
3. 缺少检查与验收项的映射时明确拒绝并返回缺项；不要自动视为通过。
4. getEvidence 的兼容投影保留真实执行身份与来源，不能把 delivery_id 充当真实 run_id、通过固定值伪装完整执行信息。
5. 仍由执行模型通过原生工具完成这些检查。DevFlow 仅核对现有事实，缺项集中反馈给模型。

**验收：** R06/R07 阻止提交；补充检查失败、旧代码检查、其他仓库检查，以及确有当前成功证据时可提交的正例。不得直接删除 required 标志来让回归通过。

### C05 / P1：Git 快照错误仍被吞掉，无法冻结代码也会标记交付通过

**位置：** packages/core/src/engine.ts:1311—1321、1353—1363；packages/git/src/git.ts:217—231。

**证据：** R08。git status 能执行，但快照检查返回 BRANCH_CHANGED；deliver 捕获后仍返回 accepted，snapshot_id 为空，任务被标记 verified=true。

捕获所有异常并注释“没有变动则沿用快照”，把真实分支、基线和索引错误混为无修改，前面的 status 检查无法替代这些约束。

**整改：**

1. 快照失败不得创建通过的 DeliveryRevision、TaskProof 或进入待验收状态。
2. 保留 BRANCH_CHANGED、BASELINE_CHANGED、索引异常及磁盘读写失败等原始错误。
3. 如允许无改动交付，显式识别该情况，并验证已有快照仍匹配全部仓库和计划。
4. 快照与通过状态的持久化保持一致，避免部分写入留下“已验证”标记。

**验收：** R08 拒绝；分别测 status 失败、分支变化、HEAD 变化、索引变化和合法无改动，不用一个 Git 故障代替全部异常路径。

### C06 / P1：把“不是 running”当成成功结束，失败执行也能进入人工验收后的复核

**位置：** packages/core/src/engine.ts:565—581、1338、1822—1832。

**证据：** R09。隔离设置 run.status=failed 后，交付得到 execution_finished=true，accept 后进入 REVIEW_QUEUED。

当前门禁只排除 running，未正向要求 completed。运行记录缺失也满足可选链的不等式。正常退出回调则批量标记所有未失效 revision，缺少对产生该交付的 run 的精确关联。

**整改：**

1. 成功结束必须正向验证当前 run 存在、status=completed、结束事件可信；failed/stopped/缺失均不满足。
2. DeliveryRevision 明确绑定 run_id、conversation_id 和版本；退出事件只更新所属修订。
3. 模型交付后仍在运行时，可以记录候选交付，但只有执行成功结束、最终输入仍匹配，才开放人工验收及最终勾选。
4. 保留失败原因和恢复入口，不把 failed 改写为 completed 来满足门禁。

**验收：** R09 拒绝；覆盖 running、completed、failed、stopped、缺失记录、旧 run 回调和交付后继续修改代码。

### C07 / P2：身份合同仍可省略，会话身份没有参与核验

**位置：** packages/contracts/src/index.ts:353—359；packages/evidence/src/validator.ts:108—140；packages/evidence/src/native-run-records.ts:250—261。

**证据：** R10。声明的 conversation_id 与实际传入宿主事实不同，交付仍通过。其他复现清单省略大部分身份字段也被接受。

现有“显式错误身份被拒绝”的 S04 没覆盖缺失字段和 conversation_id。readRecords(runId) 忽略 runId；verify 参数也不含会话或运行身份。这说明身份绑定尚未完成，不能声称能够可靠隔离历史回放的事实。

**整改：**

1. native-v2 合同明确要求 schema_version、workflow/run/conversation、plan_revision/hash 和 submission_id。legacy 兼容通过独立路径处理。
2. 核对服务端记录的当前会话和运行轮次，不能仅信清单自报。
3. 日志事实键包含会话、轮次、调用 ID；恢复回放与当前事件区分，防止相同 step_index 覆盖。
4. 保留异步 command_status 关联，增加多轮和跨会话冲突测试。

**验收：** R10 拒绝；缺失身份、旧轮次和重复 step ID 各自有明确断言；同会话正常恢复继续可用。

### C08 / P2：成功重试失败；失效后重试反而返回旧 accepted

**位置：** packages/core/src/engine.ts:1225—1254。

**证据：** R11、R12。

状态检查先于幂等查询，成功进入 HUMAN_PENDING 后原样重试得到 INVALID_STATE。失效并恢复执行后则命中旧 delivery.status=passed，未检查 revision 失效及当前输入，返回声称已进入 HUMAN_PENDING 的 accepted，但真实状态仍为 EXECUTING。

R12 不证明能够直接完成提交；它证明接口返回了已经失效的成功结果并错误描述状态，会误导模型和客户端停止必要的重新交付。

**整改：**

1. 幂等结果区分“此请求曾被处理”与“此结果目前仍有效”。
2. 成功响应丢失后的原样重试，返回相同结果及当前状态，不重复写入。
3. 旧结果失效后禁止返回可用的 accepted；返回过期原因及新交付要求。
4. submission_id 与清单摘要、运行轮次和交付修订绑定；同 ID 不同内容明确冲突。
5. 新交付解决旧问题时关闭对应 issue，恢复只发送仍未解决的差异。

**验收：** 修复 R11/R12；覆盖成功、失败、失效、计划变化、并发重复和内容冲突。现有 S12 只证明重复失败结果被复用，不能代表完整幂等。

## 5. 尚未完成的性能与合同收口

### C09 / P2：降低 IO 和 Token 的目标没有形成可验证闭环

**当前位置：**

- packages/runtime/src/runtime.ts:564—575 仍对每条模型事件调用 store.event 写 AgentEvent。
- packages/contracts/src/config.ts:34—37 默认 executors=3、live_environments=6；本机 yaml 降低值没有改变通用默认。
- packages/core/src/engine.ts:1504—1509 停止流程仍报告 services_retained=true。
- RunUsage 只有 packages/contracts/src/index.ts:520 的类型定义，packages/apps/scripts/tests 搜索没有发现采集和落库生产者。
- 单仓成功交付依次发生 importDelivery 扫描、validator 再扫描、snapshot 后再扫描，尚未建立批次内复用。
