## 2. 总体结论

六项问题归为三条根因主线：

1. **纯前端布局缺陷（问题 1、3）** —— 全局 `button` 样式强制 `justify-content: center`；模型下拉使用 `position:absolute` 位于 `overflow` 裁剪容器内，z-index 无法突破 overflow 裁剪。
2. **运行中的服务进程是旧构建（问题 2、4 的放大器，5/6 的触发条件）** —— 源码与 `dist/` 均已支持 `mimo-code`，但正在运行的服务进程早于 MiMo 接入与「目录 parserRevision / discoveryStatus」改造构建。表现为：前端新 UI 列出 MiMo Code，旧后端 `asAdapter("mimo-code")` 抛 `TOOL_NOT_FOUND`；旧后端把「仅含手工候补」的模型目录报告为 `fresh`，前端因此**从不触发自动发现**。
3. **手工候补目录条目没有 effort 元数据 + 默认模型指向 3.7（问题 5、6 的直接根因）** —— AGY 与 Codex 的模型目录从未跑过 CLI 发现，库里只有 `ensureManualCandidate` 写入的 `effort.status="unknown", values=[]` 手工条目；`buildModelChoices` 据此不产生思考强度选项；默认执行模型为 `gemini-3.7-flash-high`（问题 5 的「默认应为 3.8」部分）。

## 3. 逐项排查结论

### 3.1 问题 1：侧栏三个菜单居中

**结论：全局 `button` 样式强制 flex 内容居中，`.nav` 只写了 `text-align:left`（对 flex 子项无效），未覆盖 `justify-content`。**

- `apps/web/src/style.css:129-145` —— 全局 `button` 规则含 `display:inline-flex; align-items:center; justify-content:center`（第 133 行是居中来源）。
- `apps/web/src/style.css:375-394` —— `.nav, .flow-nav` 设 `display:flex; text-align:left`，**没有 `justify-content`**，继承全局 `button` 的 `justify-content:center`。
- `apps/web/src/main.tsx:2347-2377` —— 「AGY 账号 / 使用指南 / 设置」三个按钮均为 `className="nav"`，内容（emoji span + 文本）在 flex 中被居中。顶部「工作流总览」同样受影响，因文案较长观感不明显。

### 3.2 问题 2：MiMo Code「未知工具: mimo-code (TOOL_NOT_FOUND)」

**结论：正在运行的服务进程是旧构建，其 `SupportedAdapters` 不含 `mimo-code`，`asAdapter()` 直接拒绝；前端静态资源是新构建（工具下拉来自打包进 web 的 `TOOL_DISPLAY_ORDER`），于是出现「UI 有 MiMo、API 报未知工具」的组合症状。**

- 错误文案唯一来源：`packages/core/src/model-catalog-service.ts:500-506` `asAdapter()` → `FlowError("TOOL_NOT_FOUND", "未知工具：" + value, 422)`；前端 `formatApiError`（`apps/web/src/components/model-api.ts:804-816`）渲染为「未知工具: mimo-code (TOOL_NOT_FOUND)」。
- 当前源码与构建产物**都已支持** mimo-code：
  - `packages/contracts/src/execution-spec.ts:13` `SupportedAdapters` 含 `"mimo-code"`；
  - `packages/contracts/src/model-catalog.ts:177` `TOOL_DISPLAY_ORDER` 含 MiMo Code；
  - `dist/packages/contracts/src/execution-spec.js:12`、`dist/packages/core/src/model-catalog-service.js` 均含 mimo-code 处理分支。
- 运行库无任何 mimo 记录；今日写库记录缺 `parserRevision`/`discoveryStatus`（见 §2.1）⇒ 运行进程 = 旧构建。启动链路 `打开 DevFlow.vbs` → `scripts/open-devflow.ps1` → `node dist\packages\service\src\open.js` 直接运行编译产物，**进程启动后不随 dist 重建而更新**。
- 重启到新构建后的次级检查点（否则会出现新的失败形态「未找到指定 CLI (TOOL_NOT_FOUND)」）：
  - 可执行名是 `mimo`（`packages/adapters/sdk/src/registry.ts:115`），npm 包 `@mimo-ai/cli`（`packages/adapters/sdk/src/launch.ts:21`），需在 PATH 可解析；
  - `mimo models --verbose` 输出应含 `xiaomi/mimo-v2.6-pro`、`xiaomi/mimo-v2.6-flash`、`xiaomi/mimo-v2.5`（`tests/fixtures/model-catalog/mimo-code/expected.json` 已覆盖这三条，`parseMimoRows` 解析已就绪）；
  - `packages/adapters/mimo/src/model-configuration.ts:18-21` `LOGICAL_MODEL_LABELS` 只映射了 `mimo-v2.6-pro/flash`，**缺 2.5 系列显示名**（不影响可用性，只影响展示名回退为原始 ID）。

### 3.3 问题 3：模型下拉被对话框截断

**结论：下拉列表是 `position:absolute` 的对话框内子元素，被祖先 `overflow` 裁剪；z-index 再高也无法绘制到裁剪区域之外。**

- `apps/web/src/components/model-settings.css:181-196` —— `.ms-model-list` 为 `position:absolute; top:calc(100%+4px); z-index:1050; max-height:240px`。
- `apps/web/src/components/app-dialog.css:80-85` —— `.app-dialog-body` 为 `overflow-y:auto; overflow-x:hidden`（裁剪祖先，负责滚动区域截断）。
- `apps/web/src/components/app-dialog.css:19-30` —— `.app-dialog-container` 为 `overflow:hidden`（第二层裁剪，负责对话框圆角外截断）。
- 渲染位置：`apps/web/src/components/ModelProfileEditor.tsx:343-405`，列表内联于 `.ms-combobox-container` 中，未做 portal。

### 3.4 问题 4：「正在读取目录」含义与低效原因

**结论：文案的「目录」指模型目录（model catalog，即该工具可选模型列表），不是读文件系统目录。措辞误导 + 等待真实的多进程 CLI 发现链路 + 每次改动配置还触发真实模型探测，三者叠加导致体感很慢。**

- 文案来源：`apps/web/src/components/ModelProfileEditor.tsx:354` `loading ? "正在读取目录…" : …`。
- 「选工具为什么还要读目录」：每个工具的模型列表必须从对应 CLI 实时发现（`agy models`、`mimo models --verbose`、codex 模型缓存等），前端进入工具页 `loadCatalog`（`ModelProfileEditor.tsx:87-129`）→ `GET /api/model-tools/:adapter/models`；目录缺失时自动 `POST …/models/refresh`，再以 1 秒间隔轮询操作直至完成（`model-api.ts:426-460`，上限 180 秒）。
- 服务端一次发现要**串/多次拉起 CLI**（`packages/core/src/model-catalog-service.ts:1274-1315`）：
  1. `readVersionHelp`：`--version` / `--help`（超时 10s）；
  2. `loadCatalog`：`models` / `models --verbose` 等（`catalogArgs`，超时 30s，`CATALOG_READ_TIMEOUT_MS`）；
  3. `readInvocationCapability`：mimo-code / opencode 还要跑 `run --help` 探测参数能力。
- **每次修改工具/模型/强度还触发 `verifyModelAccess`**（`ModelProfileEditor.tsx:164-175`）：服务端真实拉起一次模型调用探测（如 `buildMimoProbe` 的 `mimo run …`），实测 20–60 秒/次（§2.1 verification_job）。这是「选个模型怎么这么慢」的最大单点。
- 旧服务进程加重问题：目录状态判断逻辑缺失（不报 missing → 该刷新时不刷新、或在错误路径上空转），且 mimo 路径直接报未知工具。

### 3.5 问题 5：AGY 模型列表 / 思考强度 / 默认 3.7

**结论：AGY 目录从未做过 CLI 发现，库里只有预填默认模型生成的手工候补条目；手工候补没有 effort 元数据，故只有一个「Gemini 3.7 Flash」选项且无思考强度。解析器与夹具早已支持完整四家族列表——是「发现没跑 + 候补无元数据」，不是解析缺陷。默认 3.7 来自预填常量与配置默认值。**

证据链：

1. **只显示 Gemini 3.7 Flash**：agy 目录唯一条目 `gemini-3.7-flash-high[manual][unknown]`（§2.1）。`formatModelName` 把变体 ID 映射为家族名（`packages/presentation/src/model-display.ts:67-76` → "Gemini 3.7 Flash"），所以 UI 恰好显示用户看到的那一个选项。
2. **无思考强度**：`manualCandidateEntry`（`packages/core/src/model-catalog-service.ts:719-742`）固定写 `effort:{status:"unknown", transport:"none", values:[]}`；`buildModelChoices`（`packages/presentation/src/model-display.ts:125-204`）仅当 `effort.status==="supported"` 且存在可信 `fixedEffort` 才聚合家族并给出 `effortValues`；`ModelProfileEditor` 的思考强度 `<select>` 由 `availableEfforts = currentChoice?.effortValues ?? []` 控制（≥2 个值才渲染下拉）⇒ 一律隐藏。对照 Claude Code / Kimi 的条目带 `supported:low|medium|…`，所以「其他工具就能选」。
3. **为什么自动发现没有跑**：前端仅在 `discoveryStatus === "missing" || status === "missing"` 时自动刷新（`ModelProfileEditor.tsx:102-108`）。旧服务把仅含手工条目的目录报告为 `fresh`（现库行即如此），不触发；运行库也没有任何 agy 的 refresh 操作记录。另有一个现行代码隐患：`withFreshness`（`packages/core/src/model-catalog-service.ts:626-646`）把缺失的 `parserRevision` **回填为当前值**（第 629 行 `catalog.parserRevision ?? PARSER_REVISION`），掩盖「旧解析器产物需要重发现」。
4. **设计上早就能出全量列表**：`AGY_VARIANTS`（`packages/adapters/agy/src/model-configuration.ts:34-39`）定义 gemini-3.8/3.7/3.6-flash 的 high/medium、gemini-3.1-pro 的 high；`tests/fixtures/model-catalog/agy/expected.json` 期望可见 ID 恰为四家族 7 个变体。一次成功的 `agy models` 发现即可恢复「3.8/3.7/3.6 Flash + 3.1 Pro + 思考强度 high/medium」。
5. **默认 3.7**：`PREFILL_EXECUTOR_MODEL = "gemini-3.7-flash-high"`（`packages/core/src/model-defaults-service.ts:21`）；`packages/contracts/src/config.ts:100` zod 默认值同为 3.7；`devflow.yaml` / `examples/devflow.yaml` / `examples/schemas/config.schema.json` 同步写 3.7。预填结果已固化进 `model_defaults` 实体（executorProfile.modelId）。

### 3.6 问题 6：GPT-6 Astra 无思考强度

**结论：与问题 5 同机制。codex 目录只有手工候补 `gpt-6-astra[manual][unknown]`，effort 元数据为空 ⇒ 思考强度选择器被隐藏。codex 解析器与夹具已定义 GPT-6 Astra 的完整档位。**

- 实态：codex 目录唯一条目 `gpt-6-astra[manual][unknown]`（§2.1），无任何 codex refresh 操作记录。
- 设计值：`packages/adapters/codex/src/model-configuration.ts:124-141,237-274` 从 `supportedReasoningLevels` / `supportedReasoningEfforts` 生成 `effort:{status:"supported", transport:"config", values:[…]}`；`tests/fixtures/model-catalog/codex/expected.json` 期望 GPT-6 Astra 为 `low/medium/high/xhigh/max/ultra`（默认 `medium`）。
- 附带风险（需一并修）：预填 reasoning 为 `explicit: high`，而 `assertExplicitEffortAllowed`（`packages/adapters/sdk/src/model-selection.ts:94-128`）在 `effort.status === "unknown"` 时直接 `fail("EFFORT_METADATA_UNKNOWN", …)`（111-114 行）。当前手工候补状态下，**实际拉起执行/规划会话也可能被拒**——补全 effort 元数据同时消除该风险。

## 4. 修复计划

### P0 —— 立即恢复（运维操作，不改代码）

### P1 —— 代码修复（按问题）

**P1-1（问题 1）侧栏左对齐 —— 一行修复**

- `apps/web/src/style.css`：在 `.nav, .flow-nav` 规则（375 行起）增加 `justify-content: flex-start;`。
- 备选：把全局 `button` 的 `justify-content: center` 限制到 `.btn`/按钮变体类；影响面更大，不首选。
- 回归：目测侧栏三项 + 顶部「工作流总览」均靠左；其它按钮（primary/danger 等）保持居中。

**P1-2（问题 3）下拉浮层不再被裁剪**

- `apps/web/src/components/ModelProfileEditor.tsx`：`.ms-model-list` 改为 `position: fixed`，用输入框 `getBoundingClientRect()` 计算锚点与展开方向（下方空间不足时上翻），或 `createPortal(document.body)` 渲染列表；监听 scroll/resize 更新位置，Esc/外部点击关闭。
- `apps/web/src/components/model-settings.css:181-196` 同步改定位样式。
- 不采用「放宽 `.app-dialog-body` 的 overflow」方案：会破坏对话框滚动与圆角裁剪。
- 回归：e2e——打开「工具与模型」对话框展开模型下拉，断言列表完整可见（不被对话框矩形裁切）、可滚动、可选中。

**P1-3（问题 2）MiMo 健壮性与 UI/API 一致性护栏**

- `packages/adapters/mimo/src/model-configuration.ts`：`LOGICAL_MODEL_LABELS` 补 2.5 系列显示名（如 `"mimo-v2.5": "MiMo 2.5"`，按 CLI 实际 ID 调整）。
- 新增单测：`TOOL_DISPLAY_ORDER` 全部 `adapterId` 必须存在于 `SupportedAdapters` 且能通过 `asAdapter()`（防止「UI 列出、服务不认」再次发生）。
- 建议（可选加固）：API 暴露服务构建版本/SupportedAdapters；前端发现不一致时提示「请重启 DevFlow 服务」，替代裸露的 TOOL_NOT_FOUND。

**P1-4（问题 5/6 核心）为手工候补补全 effort 元数据 + 修正目录新鲜度判定**

1. **候补元数据合成**（`packages/core/src/model-catalog-service.ts` `manualCandidateEntry` / `ensureManualCandidate`）：
   - AGY：命中 `AGY_VARIANTS` 家族的 ID（如 `gemini-3.8-flash-high`）写入 `effort:{status:"supported", transport:"none", fixedValue:"high"|"medium", values:[…variants], variants:AGY_VARIANTS[family], familyId}` —— 与 `toAgyEntry` 同构，使 `buildModelChoices` 立即聚合家族并给出思考强度；
   - codex：为已知模型（至少 `gpt-6-astra` → `low/medium/high/xhigh/max/ultra`，默认 `medium`）提供官方种子级兜底档位（复用 `OfficialSeed`/常量表），使思考强度立即可选；
   - 同步消除 `assertExplicitEffortAllowed` 的 `EFFORT_METADATA_UNKNOWN` 运行风险（§3.6）。
2. **新鲜度修正**（`model-catalog-service.ts:626-646`）：`withFreshness` 不得把缺失/过期的 `parserRevision` 回填为当前值；缺失或 `!== PARSER_REVISION` 应视为需重发现（`discoveryStatus:"missing"` 或新增 `parserStale` 标记），让前端自动刷新真正生效。
3. **前端兜底**（`ModelProfileEditor.tsx:102-108`）：除 missing 外，`entries.every(e => e.source === "manual")` 也触发一次后台刷新（防旧数据/旧服务残留）。
4. **`ensureManualCandidate` 合并路径**（913-918 行）：当已有目录全部为 manual 时同时写 `status:"missing"`，不要保留 `previous.status = "fresh"`。
5. 单测：manual 候补的 AGY 变体 / gpt-6-astra 合成结果快照；`withFreshness` 对缺 parserRevision 输入的判定；全 manual 目录触发刷新。

**P1-5（问题 5）默认模型 3.7 → 3.8 及存量迁移**

- `packages/core/src/model-defaults-service.ts:21`：`PREFILL_EXECUTOR_MODEL = "gemini-3.8-flash-high"`。
