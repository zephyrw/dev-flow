## RR-01 / P1：嵌套交付材料仍会把求助结果变成完成

位置：[profile-runtime.ts:246](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:246)、[round-intent.ts:91](C:/Code/system-handle/packages/core/src/round-intent.ts:91)。对应 CQ-01。

触发：合法结果包含外层状态和可选 delivery，例如：

```json
{"status":"need_user","summary":"需要补充配置","delivery":{"summary":"已完成部分实现"}}
```

`ProfileRuntime.execute` 先取 `parsed.data.delivery ?? parsed.data`，外层 `need_user` 被丢弃。Delivery schema 会补上空的 implementations/test_executions 数组；`normalizeDeliveredRound` 又把“存在数组但没有 status”解释为完成。实际调用当前方法确认，上述输入最终归一化为 `completed`。

影响：本应等待用户的任务仍会交代码审查；`need_planner` 携带相同材料也有此问题。

整改：保留完整结果信封，先从外层/内层统一解析意图，再提取附件；明确外层意图优先，内层仅在外层未提供意图时补充。禁止以 schema 自动补出的空数组推断完成。旧交付接口若本身表达“提交完成”，由该兼容入口提供明确来源语义，不将同一推断用于任意模型结果。

行为目标：相同意图经 ProfileRuntime、MCP 和原生回执进入同一路由；携带部分材料不能覆盖求助状态。

## RR-02 / P1：结果接收未绑定当前运行，旧运行可改变新运行状态

位置：[engine.ts:1339](C:/Code/system-handle/packages/core/src/engine.ts:1339)、[engine.ts:1443](C:/Code/system-handle/packages/core/src/engine.ts:1443)、[engine.ts:3338](C:/Code/system-handle/packages/core/src/engine.ts:3338)。属于 CQ-01 修复后的运行关联遗漏。

触发：旧执行结果延迟到达、停止后重投，或进入串行接收队列时当前运行已经切换。

`applyRoundResult` 在核对运行之前就调用 `routeExecutionIntent`；该方法没有检查 `w.run_id === runId`、run 的 workflow、角色和停止记录。完成分支也只有工作流阶段及 run 状态检查，旧 `planSelfCheck.validateDelivery` 已是空方法，不能提供身份保护。

实际调用确认：当前为 `new-run/EXECUTING`，传入已标记停止的 `old-stopped` 的 `need_user`，当前任务变为 `WAITING_INPUT`，同时仍挂着 `new-run`。

整改：在独占接收区内、任何分流和落库之前，统一检查任务归属、当前运行、允许角色/阶段及停止记录；终态重复消息走已持久化结果的幂等返回。过期回执只记录为过期，不修改当前运行、等待上下文、完成事件或队列。身份由调用上下文提供，不相信模型回填的字段。所有入口共用这一层，不能只靠调用方的提前检查。

行为目标：停止或被替换的运行，无论返回完成、求助还是规划冲突，都不能干扰新运行。该检查是调度归属检查，不涉及测试证明。

## RR-03 / P2：等待上下文保存了会话，却没有用于继续该会话

位置：[engine.ts:3024](C:/Code/system-handle/packages/core/src/engine.ts:3024)、[engine.ts:3338](C:/Code/system-handle/packages/core/src/engine.ts:3338)、[engine.ts:3385](C:/Code/system-handle/packages/core/src/engine.ts:3385)、[profile-runtime.ts:424](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:424)。对应 CQ-02。

触发：审查模型需要用户回答，或者执行/审查输出没有可辨认意图。

等待记录保存了 `conversation_id`，恢复时却先删除记录，然后只按 purpose 重新排队；`ProfileRuntime.invoke` 对 `quality_review` 固定不读取已有会话，因此实际使用 `adapter.prepare` 开新会话。与此同时，`unclear` 和真正的 `need_user` 都进入 `WAITING_INPUT`，没有向原模型补问最小状态的派发。

影响：不明输出需要用户介入才能推进；用户回答后重新启动一次完整审查，而非继续原问题，丢失原会话调查上下文并增加重复工作。

整改：区分模型意图澄清和真正等待用户。`unclear` 记录原文，在原角色/会话发一条最小补问，不触发整改和计数；`need_user` 才等待用户。恢复时将 continuation 信息交给新运行，再清除等待记录；运行适配器按明确 continuation 调用 resume。平常新的独立审查仍开独立会话，只有同一审查的续问继续原会话。会话确实不可恢复时按运行故障处理，保留原因和上下文。

行为目标：来源角色、阶段、会话和未决问题完整续接；不能要求用户替模型填写“质量通过/需要修改”。

## RR-06 / P1：整改第一次尝试失败后，成功重试不再计入三次整改

位置：[engine.ts:2490](C:/Code/system-handle/packages/core/src/engine.ts:2490)、[quality-coordinator.ts:144](C:/Code/system-handle/packages/core/src/quality-coordinator.ts:144)。对应 CQ-04。

触发：某次质量整改的实现运行先因连接、超时、停止或等待输入未完成，随后新运行恢复并完成；之后质量审查仍拒绝。

派发只在 assignment 没有 `repair_run_id` 时赋值，因此该字段一直指向第一次失败/停止/等待的运行。计数只检查此运行的 completed/exit_code，后续成功运行不会被选中。正常运行故障本应不计数，但恢复后真正完成的整改仍应有计数资格。

整改：区分逻辑整改轮次和运行尝试。assignment 具有稳定轮次 ID，每个尝试关联该 ID；只有有效的明确完成事件被记录后，才固定本轮被审查的完成运行。重试可更新当前尝试，但不能覆盖已被审查消费的完成记录。审查请求直接引用该完成事件，事务内只消费一次。暂停、求助、网络失败不增加次数，也不永久取消后来完成的轮次资格。

行为目标：同一轮经历多次运行重试后完成，随后被拒绝只计一次；三轮这样的完整整改仍能正常触发规划接管。

## RR-07 / P1：冲突处理先删人工确认，外层再读取，导致后续提交被阻塞

位置：[delivery-coordinator.ts:715](C:/Code/system-handle/packages/git/src/delivery-coordinator.ts:715)、[engine.ts:2073](C:/Code/system-handle/packages/core/src/engine.ts:2073)、[engine.ts:2093](C:/Code/system-handle/packages/core/src/engine.ts:2093)、[engine.ts:3128](C:/Code/system-handle/packages/core/src/engine.ts:3128)。对应 CQ-08 的恢复链路。

触发：人工确认与终审通过后提交发生冲突，责任模型解决冲突，代码质量审查再通过。

`GitDeliveryCoordinator.handleConflictResolution` 先删除 acceptance；返回后 `Engine.handleMergeConflictResult` 才读取 acceptance，因而拿不到原记录，无法生成 acceptance_carry。后续审查通过后又要求存在 acceptance，最终抛 `ACCEPTANCE_STALE`。外围 catch 还可能将这个内部恢复错误归类为“审查意图不明”。

整改：在冲突处理前保存原人工确认，或让协调器以结构化结果返回确认承接信息；冲突请求/候选更新与承接记录持久化要具备可恢复顺序，不能先删唯一副本。保留原人工确认的原文和身份。模型报告功能影响时交人工复测；没有功能影响时按既有承接流程继续，不伪造新的人工确认。内部状态错误保留真实原因，不改写成模型未给结论。

行为目标：冲突解决后沿原阶段审查，按功能影响决定是否人工复测，然后可正常提交；服务重启或重复回执不丢确认记录。

## RR-09 / P2：来源完成记录在阶段转换中丢失或沿用错误

位置：[engine.ts:1009](C:/Code/system-handle/packages/core/src/engine.ts:1009)、[engine.ts:703](C:/Code/system-handle/packages/core/src/engine.ts:703)、[engine.ts:3393](C:/Code/system-handle/packages/core/src/engine.ts:3393)。对应 CQ-10。

2. 用户确认后把 intent 覆盖成仅 `{phase:"after_human"}`，来源执行 ID 被删。人工后审查期间没有 completion，任务反而显示开发中。

## RR-10 / P2：大积压补拉没有缓存上限，达到阈值后每次只推进一页

位置：[event-catchup.ts:28](C:/Code/system-handle/apps/web/src/event-catchup.ts:28)、[event-catchup.ts:47](C:/Code/system-handle/apps/web/src/event-catchup.ts:47)、[use-event-catchup.ts:25](C:/Code/system-handle/apps/web/src/use-event-catchup.ts:25)。对应 CQ-11。

触发：补拉缺口超过 4000 条事件。

`unique.slice(0, Math.max(unique.length, batchLimit))` 永远保留全部 unique，不形成上限。hook 使用累计 collected.length 决定本次是否继续，首次达到 4000 后，每次 5 秒轮询只能再取一页；旧缺口补齐之前，所有事件一直留在内存，每页还重新复制、去重、排序全部积压。

影响：原死循环虽已修复，但大积压仍长时间不展示，并产生随积压增长的内存和重复计算开销。例如约 10 万条、每页 200 条时，越过首批后仅余页的轮询间隔就约需 40 分钟，不含请求耗时。

整改：本次处理预算与历史累计量分开；用固定目标上界和 continuation 持续追赶。增量按 event_seq 合并可分段展示，另维护连续完成游标；若需要暂存，使用受限缓冲或按需历史加载。不能简单截掉事件造成缺口；也不能把整个缺口保存在 React effect 内直到最后一页才投递。切换任务保持请求结果隔离。

行为目标：每批请求和内存开销有界，大积压逐批可见并持续推进，事件不丢失、不重复。
