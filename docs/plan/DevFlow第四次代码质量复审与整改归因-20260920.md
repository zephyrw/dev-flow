## 3. 本轮全部确认问题及确定改法

### QR-01 / P1：审查续接已绑到 Run 后，失败或重启恢复被改派执行

关联：CQ-02、RR-03、TR-02。位置：[recovery.ts:181](C:/Code/system-handle/packages/runtime/src/recovery.ts:181)、[engine.ts:1486](C:/Code/system-handle/packages/core/src/engine.ts:1486)。

触发：审查 need_user/unclear 把 continuation 写入 Run 并清除 waiting → 审查运行故障或控制器把 REVIEWING 收成 RECOVERY_REQUIRED → `resumeApproved` 或范围内反馈。

`resumeWaitingIfCurrent` 在没有 waiting 时直接返回，随后固定 `QUEUED` + `execute`。不读当前失败 Run 上的 `continuation`。

后果：用户回答或意图补问已在 Run 上，恢复却新开执行轮，原审查会话丢失。

确定整改：

1. `resumeApproved` 与 `feedback` 的非 waiting 分支读取 `w.run_id` 对应 `Run.continuation`。
2. `purpose === "review"` 或该 Run 为质量审查：把该对象写回 workflow 级 `run_continuation`，转入 `REVIEW_QUEUED` 并入队审查，禁止 `QUEUED/execute`。
3. 不要重建 waiting 作为唯一来源。真实会话不可恢复仍保留运行故障原因。

归因：**明确要求未落实**。TR-02 已要求重试从 Run 读取。

### QR-02 / P1：规划 handoff 已 assigned 后，失败或重启恢复被改派执行

关联：CQ-01、TR-03。位置：[recovery.ts:181](C:/Code/system-handle/packages/runtime/src/recovery.ts:181)、[engine.ts:2444](C:/Code/system-handle/packages/core/src/engine.ts:2444)、[engine.ts:3788](C:/Code/system-handle/packages/core/src/engine.ts:3788)。

触发：need_planner 只写 `planning_handoff`，不写用户 waiting → assigned 并清 leftover waiting → `runtime.plan` 失败或重启把带 run_id 的 PLANNING 收成 RECOVERY_REQUIRED → `resumeApproved`。

`isCurrentPlanningSource` 只在已有 waiting 时运行。open 的 handoff（pending|assigned，`target_run_id === w.run_id`）不参与恢复路由。

后果：规划被跳过；handoff 停在 assigned，可能污染以后的规划。

确定整改：

1. 无 waiting 时仍读 `readPlanningHandoff`。
2. 仅当 handoff 为 pending|assigned 且是当前来源（target_run_id 匹配，或当前 Run 为 planning，或 blocker 为 NEED_PLANNER）时：转入 PLANNING，保留原文，入队 `dispatch_run purpose=planning`。
3. 当前 Run 是后续执行且 handoff 仍 open 时标 superseded，不得改派规划。

归因：**明确要求未落实**。与 QR-01 共因都是恢复只认 waiting。

### QR-03 / P1：新独立轮次会拾取历史失败 Run 的 continuation

关联：TR-02。位置：[engine.ts:1466](C:/Code/system-handle/packages/core/src/engine.ts:1466)。

触发：任一 intent_clarification/user_answer Run 失败，continuation 留在该 Run 上。之后出现没有 workflow 级 staged continuation 的同 purpose 新轮次。`openRunContinuation` 从新到旧扫描全部 Run，跳过 completed 且 exit_code===0，命中旧失败记录。

后果：整改或新轮次只收到补问指令，或错误续上旧会话。

确定整改：

1. 删除对 `store.list("run")` 的扫描。
2. `consumeContinuation` 只允许：当前 workflow 键上 purpose 匹配的 staged `run_continuation`；purpose 匹配的 waiting。
3. QR-01/QR-02 的恢复必须在更换 `w.run_id` 之前，把该失败 Run 的 continuation 写回 workflow 键。purpose 不匹配的 staged 记录不得清除。

归因：**修复新引入**。

### QR-04 / P1：冲突功能影响未进入质量审查材料

关联：CQ-08、RR-07、TR-05。位置：[profile-runtime.ts:411](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:411)、[quality-coordinator.ts:222](C:/Code/system-handle/packages/core/src/quality-coordinator.ts:222)。

触发：冲突回执 function_impact=changed|uncertain，协调器已写入 carry，随后转入 REVIEW_QUEUED。

schema、持久化、通过后人工复测路由已接通。`readConflictBackground` 没有任何调用方。审查 HANDOFF 没有 carry / reported_function_impact。

后果：质量模型在不知情下审冲突后的代码，可能给出简化 passed 或默认 none。平台提交路由已能拦住直接复用旧确认，但不能替代把变更背景交给质量模型。

确定整改：

1. `ProfileRuntime.reviewMaterials` 读取 `quality.readConflictBackground(w.id)`，写入 reported_function_impact、说明、requires_confirmation 及冲突摘要；无 carry 则不加。
2. 材料只作背景，禁止用质量简化 passed/none 回写覆盖 carry 的 changed/uncertain。
3. 通过后继续只以持久化 carry 决定是否人工复测。

归因：**明确要求未落实**，兼前次审查漏检（helper 已写，调用链未接）。

归因：**明确要求未落实**（消费者已实现，调度未接线）。
