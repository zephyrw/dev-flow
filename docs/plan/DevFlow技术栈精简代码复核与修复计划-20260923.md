## 3. 缺陷及逐项修复要求

### R01 — P1：修复 ESM 加载和实际 Windows 原生包装层

**证据。** [controller-lock.ts:30](C:/Code/system-handle/.claude/worktrees/devflow-node-migration/packages/process/src/controller-lock.ts:30) 在 ESM 中直接使用 `require`，POSIX 分支第 67 行同样有问题。[native/index.ts:45](C:/Code/system-handle/.claude/worktrees/devflow-node-migration/packages/process/src/native/index.ts:45) 捕获加载异常并缓存 `{}`，导致依赖方通过可选调用继续运行。[native/windows.ts:212](C:/Code/system-handle/.claude/worktrees/devflow-node-migration/packages/process/src/native/windows.ts:212) 用 QUERY/SYNCHRONIZE 权限获取句柄再绑定 Job，缺少 SET_QUOTA 和 TERMINATE。本次已复现启动异常和 assign=false。

修复动作：

1. 在 `native/index.ts` 提供唯一的异步初始化入口，使用 `import()` 选择平台模块；入口 await 初始化后才开放业务。去掉裸 `require` 和“失败缓存空对象”的降级。同步业务需要原生模块时只能拿到已成功初始化的实例。
2. 将 Windows 必需能力定义为明确方法，不通过 `method?.()` 表示成功。模块缺失、DLL 加载失败、查询失败均返回明确错误；让控制器拒绝启动、账号功能保持不可用。
3. `assignProcessToJob` 使用 `PROCESS_SET_QUOTA | PROCESS_TERMINATE`，额外查询权限按用途添加；捕获调用后的错误码再做清理，失败不得发送 start。统一 null/无效句柄判断和 try/finally 释放。
4. `createJob` 检查已有同名 Job，拒绝复用未知对象；名称使用每次启动的随机标识。补齐只读打开/查询既有 Job 所需 API，用于恢复确认；不能以 OpenProcess 成功与否代替 Job 成员查询。
5. 原生单元/集成测试必须导入这里的实际包装函数。当前 `node-native-primitives.test.ts` 自己声明了一份正确权限的 Win32 函数，不能覆盖本文件的错误；将底层原理 PoC 与生产包装测试明确分开。

验收：编译后的纯 Node ESM 入口在 Windows 正常初始化；模拟加载失败时拒绝运行；给测试自建子进程绑定 Job 成功、查询成员数准确；同名 Job 冲突被拒绝；错误路径不泄漏句柄。Linux/macOS 不加载 Windows DLL。

### R02 — P1：把 runner 和身份协议接到真正的进程启动链

**证据。** [manager.ts:146](C:/Code/system-handle/.claude/worktrees/devflow-node-migration/packages/process/src/manager.ts:146) 直接 spawn 业务命令；新增 runner 和 `process-protocol.ts` 没有被生产管理链使用。第 169–207 行按根进程 close/error 记录 `confirmed_exited`，未查询 Job/进程组；第 9–20 行 Windows taskkill/POSIX 单 PID SIGTERM 不具备控制器崩溃后的相同约束。实际生命周期缺少 started/PID/identity。

修复动作：

1. `ProcessManager.start` 只创建固定安装路径的 `runner-entry.js`，使用 `process.execPath`、空 execArgv、独立 IPC、独立三个数据流。启动器环境在创建子进程前清理 `NODE_OPTIONS/NODE_PATH/NODE_DEBUG*` 等注入项；Windows 环境变量名按不区分大小写处理。
2. 固定握手顺序：创建 attempt → runner ready → 父进程验证 ready/OS 创建身份 → Windows 绑定 kill-on-close Job → 写入已有 process_record → 发送 start → 收到 started 后补齐实际工具 PID/创建身份。任何前置失败都不得启动业务命令，已创建 runner 必须被收回。
3. 统一 `attempt_id` 为父进程生成的 UUID；不要保留当前 helper 的 `att_...` 与 runner 内部 UUID 两种格式。所有 ready/start/started/output/exit/stop 控制消息携带并校验 attempt；数据字节仍走标准流，不做 JSON/base64 包装。
4. 持久化沿用已有 process_record：`identity.backend=node-v1`、业务 id、attempt_id、launcher_pid、工具 pid、真实 OS creation_time、job_name 或 pgid；更新 lifecycle 回调和恢复读取。失败/未启动状态也记录阶段，不能给缺失身份填 Date.now 或猜测 PID。
5. Windows Job 由控制器持有不可继承句柄；runner 和工具不持有能延长 Job 生命周期的句柄。正常停止或控制器被终止后，均能终止整棵树。
6. POSIX 创建独立进程组，SIGTERM 后等待，再 SIGKILL；只有进程组确实消失才能完成。修复 runner 在根进程先 close 时清掉升级终止定时器、提前退出的行为，根退出但后代仍在时仍应完成组清理。
7. 按 attempt 隔离 active 和 stopHistory。同业务 id 重启时清掉旧完成缓存；迟到 exit/stop 不影响新 attempt。已有 API 必须保持有界超时，停止超时返回 unknown，不能一直挂起。
8. 删除手工维护的 `packages/process/src/runner-entry.js`，仅从 TS 编译产生 dist；开发测试先构建或走明确的开发编译入口，不再查找两份行为可能不同的 JS。

验收：经真实 `ProcessManager` 调用验证 ready 前不执行标记动作、绑定失败不执行工具、启动身份可恢复、控制器被终止后子孙全退、根先退而孙进程继续运行、同 id 连续两次 attempt、旧事件迟到、超时/取消并发、中文空格路径和二进制输出。断言 OS 状态与持久化状态一致，不只断言 mock 回调。

### R03 — P1：停止确认和恢复必须保留 unknown，不能把异常当退出

**证据。** [agy-account-processes.ts:49](C:/Code/system-handle/.claude/worktrees/devflow-node-migration/packages/process/src/agy-account-processes.ts:49) 缺记录/缺 PID 直接跳过，require/native 查询异常被 catch 后作为“Process gone”；[recovery.ts:248](C:/Code/system-handle/.claude/worktrees/devflow-node-migration/packages/runtime/src/recovery.ts:248) 也将异常设为 alive=false。实测查询自己的存活 PID 得到了 stopped=true。账号切换因此可能在旧进程仍使用凭据时继续写入。

修复动作：

1. 在 R02 的管理层建立唯一的身份查询/停止观测入口，供账号 ProcessHost、普通 runtime 和 recovery 复用；不再维护三种 PID 猜测实现。
2. 使用既定四态 `running / confirmed_exited / unknown / not_owned`。缺记录、身份缺失、权限拒绝、DLL/API 失败都是 unknown；创建时间不匹配是 not_owned；Windows 成员查询成功且为 0、POSIX 验证对应组已消失，才是 confirmed_exited。
3. 对现有只返回 boolean 的账号接口，只有明确 confirmed_exited 才返回 true；unknown 要阻止切换并给出稳定错误。删除无操作的 `assertCapabilities`，实际校验所依赖能力。
4. `reconcileProcesses` 不得在 unknown 时释放运行占用、确认恢复完成或推进账号切换。旧记录缺 node-v1 身份时维持待核对，由升级排空阶段处理，不能盲杀对应 PID，也不能一律视为停止。
5. 保留预期 PID 与 OS 创建时间、attempt、Job/pgid 的联合校验；停止一个任务不能误伤 PID 被复用后的无关进程。

验收：活进程返回非 stopped；模拟 AccessDenied/加载异常/记录缺失/无 PID 均阻止切换；PID 相同创建时间不同返回 not_owned；根进程消失但 Job 仍有成员不能确认；只有确认完成后才释放既有 permit/lease 和恢复流程。

### R05 — P1：恢复既有凭据目标、vault 格式和完整切换语义

**证据。** [credential-worker.ts:410](C:/Code/system-handle/.claude/worktrees/devflow-node-migration/packages/agy-accounts/src/credential-worker.ts:410) 按 realm 派生锁；第 452 行起把活动目标改成 `DevFlow.agy.<hash>`，旧目标是 `gemini:antigravity`。capture 写入 `.bak.`，activate 却读取 `.saved.`；引用改为 secret hash、revision 固定 1；activate/restore 忽略传入的引用；第 587–591 行 delete-saved 什么都没做却返回成功。

独立新增的 [credential-store.ts:85](C:/Code/system-handle/.claude/worktrees/devflow-node-migration/packages/agy-accounts/src/credential-store.ts:85) 尚未被 worker 使用，而且自己采用新的 16 位 hash 文件名、每文件 revision，读时直接 JSON.parse 密文。旧合同已经从共同基线的 Go 源码核对，不能以新注释自称“兼容”替代逐字段对齐。

固定合同：

| 内容 | 必须实现的唯一规则 |
|---|---|
| 活动系统凭据 | `gemini:antigravity`，不改目标名、不额外包一层自定义加密后写回官方目标 |
| 互斥域 | `Global\DevFlowAuth_` + SHA256(当前用户 SID + `:` + 固定目标)，完整 hex；所有 realm 共用 |
| vault 目录 | `%LOCALAPPDATA%\DevFlow\agy-accounts\<realm>\` |
| 引用 | 随机 `sec_`/`bak_` + 32 位小写 hex，保存为 `<ref>.bin`；不从 secret 派生引用 |
| 密文 | 当前用户 DPAPI、无额外 entropy、UI_FORBIDDEN；能够解开旧 Go 写出的文件 |
| envelope | `Version=2, RealmID, AccountID, Revision, Credential`；校验 realm/account/ref 一致 |
| 完整 Credential | `Exists, Flags, Username, Comment, Persist, TargetAlias, Attributes[], Secret`；Attributes 的 Keyword/Flags/Value 和 Secret 保持 Go base64 字节语义 |
| revision | realm 目录中的单个 `revision` 文件；持锁分配、持久化、单调递增且为安全整数；损坏或溢出即失败 |

修复动作：

1. worker 只编排操作，实际读写统一使用 `credential-store.ts` 和经 R06 修正的 `credential-windows.ts`；删除 inline native 和 `.saved./.bak.` Credential Manager 第二存储方案。
2. store 接受经过验证的 realm/ref 来定位旧文件，不再用 account hash 重新命名；加解密成对注入，只在 worker 进程使用。损坏、解密失败、权限失败和真正不存在必须区分，绝不当作新空账号重建。
3. 对 vault 目录链、目标和临时文件校验路径边界/reparse，设置当前用户与 SYSTEM 的限制 ACL；临时文件在相同安全目录创建、flush 后原子替换。先有可靠备份再动活动凭据，任何失败不能先删除唯一可恢复数据。
4. 在 worker 内部验证当前锁确已持有、请求 realm/lock_id 正确，再处理所有凭据动作；不能仅信任父进程布尔状态。锁获取/释放保持同一 OS 线程；争用立即返回 busy，不在主控制器线程同步等待 10 秒。
5. capture 产生可供 activate 使用的 sec 引用并真实保存 envelope；activate 必须按 secret_ref 读取和验证，再写官方目标并完整 readback；clear 必须 durable backup 成功后删除，再验证确已清除；restore 按 backup_ref 恢复包括“原来不存在”的状态；delete 必须删对应引用并报告真实结果。

## 6. 原生接口依据

R01 的 Job 绑定权限已对照 [Microsoft AssignProcessToJobObject 文档](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject)：进程句柄需要 PROCESS_SET_QUOTA 与 PROCESS_TERMINATE。

R06 的指针和输出参数修复应遵循 [Koffi 指针文档](https://koffi.dev/pointers)：指针以 BigInt 表达，结构输出和间接指针必须按其实际 ABI 处理，不能通过 TypeScript 类型断言改变原生内存含义。本次“符号绑定失败”和“assign=false”的结论同时具有前述本机复现结果。
