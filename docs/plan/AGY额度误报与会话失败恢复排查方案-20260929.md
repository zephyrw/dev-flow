# AGY 额度误报与会话失败恢复排查方案

调查日期：2026-09-29；时间均为北京时间。范围：只读检查本机 DevFlow 数据库、原始运行日志和当前源码/运行产物，提出实施方案。本轮未修改产品代码、运行状态、账号、凭据或已有任务。

## 1. 结论

这次不是已经证实的“账号额度用光但自动切换失效”。已确认两个 AGY 任务存在运行错误分类缺口：

1. **调控分析生产问题整改开发**：本轮 AGY 会话订阅连接中断，退出码 1；CLI 返回的会话结果仍带着早先的额度错误。DevFlow 未识别当前连接错误，采用了历史额度文本，把任务阻塞为 `MODEL_QUOTA`，因此也漏掉了自动重试。
2. **全域推商品详情生产问题整改开发与真实链路测试**：17:27 的本轮记录含 `INTERNAL (code 500)`，DevFlow 未识别这种 AGY 错误格式，阻塞为 `NATIVE_RUN_FAILED`。当前数据库不是 `MODEL_QUOTA`。用户看到两个额度提示与后台记录不一致，不能据界面文字把它归为账号耗尽。
3. 自动切号配置已开启，故障任务继承全局配置；17:21:41 的官方 CLI 用量探测显示当前账号 Gemini 周额度剩余 **76%**、五小时额度剩余 **74%**。这一数值是该次探测的快照，不代表未来额度。
4. 同日 16:40、16:52 存在已完成的 `workflow_quota` 自动切号审计；因此自动切换机制并非整体没有工作。此次没有切号的直接原因是核验得到 `quota_not_exhausted`。

应实施：**补齐 AGY 当前运行错误的识别和来源优先级，让断线/500 进入现有有限重试；保留真实额度耗尽才触发自动切号的约束。**

## 3. 根因与边界

[错误分类器](C:/Code/system-handle/packages/runtime/src/errors.ts:37) 和 [公共错误映射](C:/Code/system-handle/packages/contracts/src/runtime-failure.ts:206) 缺少以下两种 AGY 形式：

- `the connection to the agent was interrupted before the response finished` / `subscriber fell behind updates, stalled for ...`。
- 提供方错误记录中的 `INTERNAL (code 500)`。

[profile runtime](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:1310) 只有 stderr 被分类成已知错误时才优先采用它。当前连接中断未被识别，随后 `nativeFailureDiagnostic(result)` 采用旧额度字段。[账号桥接](C:/Code/system-handle/packages/runtime/src/agy-workflow-bridge.ts:478) 核验额度并正确拒绝切号后只返回 false，运行层继续保留先前的错误归因。

[旧 AGY 运行入口](C:/Code/system-handle/packages/adapters/agy/src/session.ts:229) 会拼接 footer 与 stderr 再分类，也必须覆盖“旧额度文本与当前连接错误同时出现”的顺序问题。

[现有调度逻辑](C:/Code/system-handle/packages/core/src/engine.ts:3714) 已支持 `MODEL_CONNECTION_FAILED` 的有限自动重试：最多 10 次、3 秒起步、1.5 倍退避、最大间隔 30 秒。两个失败未被正确归类，因此未进入这一路径。

`subscriber fell behind` 的更底层原因（CLI 内部订阅、服务端事件流、消费者处理速度等）目前没有足够证据。方案先修确定的分类与恢复缺陷；不能据这一行日志直接重写进程 I/O、数据库或改代理。

## 4. 一条可实施的修改路线

### 第一步：统一识别当前提供方通信失败

修改以下两个文件，复用一个共享识别函数，避免两份正则漂移：

- `packages/contracts/src/runtime-failure.ts`：补充上述两种有明确 AGY/提供方语义的模式，映射为已有 `MODEL_CONNECTION_FAILED`，公共映射与运行分类保持一致。
- `packages/runtime/src/errors.ts`：复用共享识别函数并返回 `retry=auto`。权限拒绝、用户停止、账号身份变更仍优先处理。

只接受当前进程诊断/提供方错误字段，不扫描模型正文、历史交付、业务 HTTP 日志中的任意 `500`、`quota` 或 `connection`。不要扩大为“出现数字 500 就自动重试”。

### 第二步：按来源决定最终原因，不让 footer 覆盖当前诊断

- `packages/runtime/src/profile-runtime.ts`：以本轮进程退出、停止原因、权限拒绝、stderr 诊断以及 CurrentTurn 为依据作最终判定；当前通信错误优先于未证实的额度 footer，最终保留 `MODEL_CONNECTION_FAILED`、原始脱敏诊断、退出码和来源。该情况下跳过额度切号候选，不执行多余的 `/usage` 核验。
- `packages/adapters/agy/src/session.ts`：先对当前 stderr 作独立判定，再处理会话 footer；覆盖旧入口的相同组合，避免字符串拼接后由关键词决定原因。
- `packages/runtime/src/runtime.ts`：确保旧入口传回的明确通信失败不会继续尝试用历史 quota 候选触发账号切换。
- `packages/adapters/agy/src/failure-fact.ts`：补齐当前通信诊断的冲突识别（特别是提供方 INTERNAL 500），保持 exit 3、当前轮、账号 epoch 等额度确认约束；不把 exit 1 改成额度耗尽。

修改 `packages/runtime/src/agy-workflow-bridge.ts` 的 `observeFailure()` 返回合同，区分 `waiting / quota_unconfirmed / not_applicable`，同时更新两个运行入口与直接调用该方法的测试，禁止以对象 truthiness 代替原 boolean。核验未证实耗尽时返回 `quota_unconfirmed`；调用方若已有明确当前通信错误则保留它，否则使用 `NATIVE_RUN_FAILED` 并说明额度未获确认。`not_applicable` 保留原始非额度原因。不得把当前执行判为成功，也不得仅凭未证实 footer 生成 MODEL_QUOTA。账号服务内部额度探测与候选选择算法保持不变。

### 第三步：复用原任务恢复，保持切号和工作流合同

本次优先复用现有 `engine.ts` 重试路径，不另建队列、切号器或恢复框架。必须验证恢复时保留：

- 原 Workflow、审批、plan revision/hash、工作树和未提交修改。
- 原 purpose、review phase、logical round、模型/推理配置、账号与原生会话绑定。
- 用户已投递指导的回执，避免将同一业务输入再次作为新要求重复投递。
- 停止/取消/修改计划后的失效检查；旧定时器不能唤醒新一轮。

真实本轮 quota 退出或可信额度零余额仍进入现有 `AGY_ACCOUNT_WAIT` 自动切号；普通 429 不能据此换号。两任务并发触发同一账号 epoch 的真实额度失败时仍合并为一个切号操作。

商品详情本轮的 error_message 不因后来出现 finish 而清零；先补齐 500 分类与重试，不顺便放松 `CurrentTurn` 的成功判定。

### 第四步：界面使用同一最终判定

沿用 [RuntimeFailureNotice](C:/Code/system-handle/apps/web/src/components/RuntimeFailureNotice.tsx:5) 和已有执行记录，不增加新设置或面板。通信故障进入重试时显示原因、次数及继续状态；达到上限时提示查看会话连接或服务错误。

页面只能在后端最终判定为额度问题时显示额度提示；未证实的 footer 只作为诊断背景，不能覆盖当前 blocker。对商品详情核对接口返回、任务 ID、当前 Run 与页面展示；只有确认前端使用旧 Run/旧诊断覆盖当前状态才修改相应投影，不能先假定是前端缓存问题。

### 第五步：部署后定向恢复这两个阻塞任务

1. 在隔离开发环境完成验证；修改 `profile-runtime.ts` 等前先核对其他正在进行的编辑，避免覆盖已有附件/指导输入修复。
2. 发布前核对控制器使用的构建目录及活跃 Run。等待其他任务进入可恢复边界后更新产物并受控重启，保存数据库一致性备份和上一版产物；不要直接在活跃控制器目录边编译边替换。
3. 无数据库结构迁移。保留旧失败 Run 与审计；本次不直接 SQL 清掉 blocker，不更改账号凭据，也不重置历史额度。
4. 使用已有 `/api/workflows/:id/recover` 对上述两个 Workflow 分别恢复。调用前确认仍为本报告对应失败 Run，且没有用户后续停止、换模型、改计划或新 Run；若已变化则重新读取后按新状态处理。
5. 观察新 Run 的真实 stdout、stderr、输入回执和后端/页面状态；调控任务发生相同断线时应进入有限通信重试，不能再显示旧额度倒计时。商品详情的当前 500 应显示提供方失败并走同一恢复路径。

## 6. 回滚与停止条件

- 若新逻辑将普通业务 500、旧 quota 或用户停止解释为可重试，停止发布。
- 若需要更换模型、丢弃会话、重建工作树或全量停掉其他任务才能继续，停止该扩大操作，保留证据重新确定范围。

- 有限重试后仍出现 subscriber stalled，则另行对该任务采集 CLI 版本、事件流和输出处理耗时，定位更底层中断；不得靠无限重试或盲目切号掩盖。
