## 2. 统一落地约束

### 2.1 一套真实执行链

继续使用现有 Store、Engine、Runtime 和 scheduler。所有新增入口经领域服务进入同一套状态机；生产链中不保留只改 entity 状态、实际不派发的第二套实现。新角色派发使用真实 SQL outbox，任务 kind 固定为 `dispatch_run`，消费者按冻结的 Run 加载适配器。旧 kind=dispatch 仅处理历史合同；新任务不得回退旧硬编码模型流程。

事务中同时写领域状态、版本、领域事件及唯一 outbox，事务提交后唤醒 worker。重启恢复扫描未完成 intent/outbox；无活动任务时不持续扫描源码、工作流或启动模型。

### 2.2 版本、幂等与权限

新增写操作统一校验：request_id、expected_version（创建除外）、身份和用途、当前 phase/epoch、计划/文档/交付版本及所需 feedback_cursor。存储 request_id 对应的规范化负载哈希与结果：同键同负载返回原结果，不重复事件；同键不同负载返回 409 IDEMPOTENCY_CONFLICT；旧版本返回 409 VERSION_CONFLICT。

服务端负责生成不可伪造的 run/phase/epoch/session/process 身份，不能接受 worker 自报人工确认或真实退出。序号在事务内递增，不能使用 Date.now 或 list.length+1。重复投递和并发 HTTP 请求都必须按一次操作处理。

保留冻结历史数据；旧合同走兼容读取，不能全库替换或把旧质量结果认作新关卡通过。执行配置修改创建新 ExecutionSpec revision，旧 Run 指向的 Profile 内容不可变。

### RQ-05【P1】生产流程仍从终局核验直接进入人工阶段

**证据**：Engine.deliver/finalizeNativeDelivery 的实际路径仍直接推进 HUMAN_PENDING；新 QualityCoordinator 无运行链调用方。仅新增状态枚举与 badges 不会改变调度顺序。

**唯一阶段顺序**：

`planning → plan approval → implementation+self-test → before_human review → human verification → after_human review → integration/commit → cleanup/completed`。

每道 review 的有效 changes_required：前两次派发执行整改，第三次派发规划接管；接管写入结束后用新的只读上下文自审。接管自审仍失败/无法完成则 WAITING_INPUT，不再自动无限重试。

**步骤**：

5. 任何阶段回调必须核对当前 epoch/purpose，不通过时不推进。暂停、停止、WAITING_INPUT 在恢复时保持，不因服务重启自动执行。
6. 按最新阶段暴露 MCP 权限；worker 不能调用人工确认或直接完成流程。

**确定提交算法**：

1. 取得仓库写 lease，冻结原 HEAD、symbolic ref、index bytes/hash、用户 staged/unstaged/untracked 基线和当前 diff；再次核验两道质量结论、功能确认、无未关闭问题和当前交付。

每份正式整改文档首先声明所审查的源码/交付版本和用户最新范围，再逐项使用以下固定栏目：

1. finding_id、repair_item_id、严重程度、需求与设计依据。
2. 证据级别（实际复现/静态确定/缺认证）、文件/函数/审查时行号、触发条件、最小复现、预期/实际、原始证据。
3. 根因与唯一修复设计，包含适用的算法、接口字段、状态、事务、幂等、并发、失败恢复。
4. 允许改动文件/符号、禁止改动项、必须保留行为。
5. 按依赖排序的具体实施步骤与各步产物。
6. 正向、负向、异常/并发/重启等适用验收、原缺陷回归及受影响旧功能回归，绑定稳定场景 ID。
7. 逐条关闭所需的代码/测试/原始报告、停止条件与事实冲突上报方式。

执行模型只能在这份确定设计内决定局部代码表达，不得重新选路线。若出现新事实，先由规划模型调查并更新完整文档；用户只决定不可推断的业务需求。文档完整性不能靠字数和“字段非空”证明，规划模型必须先核实根因和可实施性，复审必须基于修复后的实际代码与证据。

## 程序调度的正式计划逐项复核

native-v2 每轮初始开发、正式整改或用户反馈修复完成后，执行顺序固定为：开发与自测 → 交付核验及执行成功退出 → 程序再次调起执行模型对照正式计划逐项复核 → 修复遗漏/偏离并重新自测、交付核验及成功退出 → 规划模型独立代码质量审查。不得直接开放人工核验或把首次完成自述当成这次复核。人工核验前的质量审查通过后才交用户；人工核验后的整改也不能跳过执行复核。

复核必须重新读原始计划及当前正式批准的整改/修订全文，按原编号关联真实实现、测试和未完成项。使用 AUTHORITATIVE_PLANS.json、HANDOFF.md 与 handoff.json 中程序给出的版本及 self_check.check_ids；正式范围变更引用对应批准修订。禁止创建或使用 implementation_plan.md、客户端计划工件或其他局部计划替代原文。逐项报告属于执行事实记录，不是另一份实施计划。

当前复核轮次的交付清单必须包含 plan_self_check，并符合 plan-self-check.schema.json：绑定请求、源交付、当前 run_id、plan_revision、plan_hash、authority_hash；完整覆盖全部 check_ids，逐项提供代码/测试报告/用例定位，记录发现问题及实际修复证据。遗漏、重复编号、空证据、未解决问题、旧轮次/旧计划/旧输入报告、进程失败均阻断规划审查；代码改动后提交当前轮次有效测试与新交付。正常开发轮次不能自行填报告冒充程序调度。

程序校验报告及当前交付的绑定和完整性，不能保证模型判断语义正确；规划模型仍须独立检查实际代码、测试真实性与原计划覆盖。缺少本轮有效自查报告不得放行。自查不计入任何质量关卡的三次拒绝次数；暂停/停止后不得自行继续，不新增后台轮询，不改变既有界面布局。
