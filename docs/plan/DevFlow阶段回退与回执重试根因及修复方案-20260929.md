## 2. 根因与代码证据

### R1：工作流级提交标识与运行级结果混用，阻断正确的测试完成交接

[engine.ts:1790](/C:/Code/system-handle/packages/core/src/engine.ts:1790) 在整个工作流的所有 delivery 中查找 `submission_id`，随后比较整个规范化 manifest 的 hash。命中旧 ID、内容不同就抛出 DELIVERY_CONFLICT。

真实测试回执沿用了开发轮次的 `sub-wf-…`。当前回执的 run_id 已正确变为测试 Run，旧 delivery 属于开发 Run；即使只改 run_id，整个 manifest 的 hash 也必然变化。实际回执另有测试项等差异，均被这个工作流级去重键挡住。

[profile-runtime.ts:323](/C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:323) 已把结果交给当前 Run 的 `receiveRoundResult`，控制器知道正确的运行身份，却仍让可选的模型自填 submission_id 决定整个完成流程。这是边界错误；不能以“提醒模型下次换一个 ID”作为修复。

### R2：回执协议错误进入代码修复分支，生成错误职责并破坏记录

[engine.ts:3732](/C:/Code/system-handle/packages/core/src/engine.ts:3732) 对这一故障调用修复逻辑后：

1. 无条件调用 `invalidate("异常修复，将按原角色继续")`。
2. 用遗留的 `repair_assignment.planner` 决定排队 stage。规划修复已结束，assignment 仍保留 planner=true，于是测试重试却写入 `planner_takeover`。

[engine.ts:1063](/C:/Code/system-handle/packages/core/src/engine.ts:1063) 的 invalidate 会删除 acceptance、失效 delivery_revision，并将所有 review 标为 stale。截图“历史复核已失效”因此反复出现；这里无须发生代码修改。

实际下一 Run 的冻结 dispatch_context 仍保留 `executor_test`，所以“规划模型接手已排队”和“继续测试”会先后出现。不能据错误排队文案断言真的再次派发了规划模型。

当前恢复有执行失败次数上限：执行模型累计 6 次后 BLOCKED，规划模型 3 次。它不是字面上的无限循环；但把可处理的回执问题反复派给模型，最后阻塞任务，同样不能完成交付。

## 3. 唯一实施路线

### 3.1 将业务阶段与模型运行状态分开，阶段持久化且只向前

新增 `packages/contracts/src/workflow-progress.ts` 和 `packages/core/src/workflow-progress.ts`，使用现有 entities 表保存一个 `workflow_progress` 实体，不新建调度器、不引入数据库服务。

实体字段确定为：workflow_id、milestone、activity、source_run_id、plan_revision、updated_at、schema_version=1。milestone 使用有序枚举：planning、approval、development、testing、pre_acceptance_review、human_acceptance、post_acceptance_review、commit。

规则如下：

| 主流程位置 | 允许的内部活动 | 后续业务阶段 |
|---|---|---|
| 开发实施／初次自动测试 | 初次实现、自测、同范围修复 | 验收前质量审查 |
| 验收前质量审查 | 首次复核、一次执行整改及复核、规划整改、整改后测试 | 人工验收 |
| 人工验收 | 用户实操、指导、功能修复、相关复测 | 用户明确通过后进入验收后代码复核 |
| 验收后代码复核 | 最终复核、规划整改、整改后测试 | 本地提交 |
| 本地提交 | commit、整合、冲突处理、提交恢复 | 完成 |

验收前、验收后的整改均属于当前阶段内部活动，不能重开初次开发或初次自动测试。复核发现问题时保持当前阶段进行中，不画“已通过”勾；规划修复后的测试 completed 按现有质量策略 2 直接向前。

具体约束：

- 业务阶段只能由已接受的正式业务事件推进。QUEUED、EXECUTING、VERIFYING、STOPPED、BLOCKED、恢复、额度重试仅改变运行状态／activity。
- 更新 milestone 时校验新值不小于已保存值，并校验来源 Run、用途和所属业务阶段；不以简单 `max(index)` 掩盖错误派发。
- 审查通过、执行完成、用户验收通过、最终提交分别保留自己的事实。阶段位置向前不意味着人工验收自动通过，也不意味着失败的测试通过。
- 同一任务内正式批准范围更新仍保留主流程位置，显示“当前阶段处理批准变更”，按该阶段的修复活动落实；不得因计划 revision 变化自动删除业务进度。需要重新批准时仍须等待用户批准，内部活动显示“等待变更批准”，不能因阶段已前进而绕过批准。新建任务才从调研计划开始。
- 初次执行模型内的开发与自测仍由同一 Run 执行，沿用现有明确活动信息显示；没有明确测试开始事件时不伪造第 4 步开始或测试通过。完成交接进入第 5 步即可。
- detail API 返回 `business_progress`。页面直接消费该快照；刷新、事件只保留最近 500 条、断线、重新打开页面均不得丢失阶段。

### 3.2 原生结果以控制器绑定的 Run 去重，submission_id 降为附加信息

修改 engine.ts 的 applyRoundResult、staleRoundResult、finalizeNativeDelivery；保留现有可选测试说明和附件展示。

原生 lightweight/native-v2 路径使用 `(workflow_id, run_id)` 作为一轮正式完成回执的唯一键，plan_revision 和 purpose 从已保存 Run 读取。模型自填 submission_id 不再参与跨 Run 去重或阻止状态前进。旧 legacy 交付接口保留原兼容行为，明确分支隔离。

接收规则固定为：

1. 先验证该回执属于当前允许提交的 Run；旧 Run、已停止 Run、旧计划回执沿既有 stale 处理，不借修改 ID 冒充当前结果。
2. 同一 Run 首次合法 completed：保存规范化正式结果及 receipt；可选附件独立归档。不能因可选清单中的旧 ID 拒绝已经明确的完成意图。
3. 同一 Run、相同正式结果重复到达：返回原处理结果，不新建 delivery、不再次派发后继。
4. 同一 Run、不同正式结果：返回明确 ROUND_RESULT_CONFLICT，保留原结果，停止本轮结果处理；不覆盖原回执、不触发代码修复、不降低阶段。冲突记录供当前阶段恢复处理。
5. 不同 Run 使用相同 submission_id：分别接收各自本轮结果；不能把前一 Run 的成功回执当作当前 Run 已完成。
6. `need_user`、`need_planner` 和 unclear 保留现有语义，不按成功推进。

使用现有 Store.transaction、workflow exclusive 和 outbox，将首次完成 receipt、execution_completion、质量流下一动作、业务阶段、后继 outbox 一起落库；以 receipt 中的 `routing_applied` 标记防止重复推进。等待文件或模型操作必须在事务外完成；进程重启后恢复未完成的本地事务／待派发 outbox，不重新要求模型报告同一已接收结果。外部模型运行沿用现有派发去重和租约。

控制器提供身份字段，模型只负责 status、summary、必要说明及可选材料。调整 profile-runtime.ts 的结果归一化入口，外层及嵌套 delivery 的身份字段不得覆盖控制器绑定身份；显式不匹配的原始回执按过期／不匹配处理，不能静默包装成当前 Run。

### 3.3 协议、运行恢复与业务修复分流，保持冻结用途

修改 repair.ts 和 engine.ts 的异常处理分支：

- DELIVERY_CONFLICT 的跨 Run 情况由 3.2 消除。同一 Run 结果冲突是协议处理问题，直接记录本轮协议阻塞；不消耗代码整改次数、不重新派发开发、不调用 invalidate。
- 网络、账号、暂停恢复继续使用既有恢复机制，完整保留 purpose、review_phase、source_run_id、assignment_id、logical_round_id、冻结模型及会话绑定。
- 执行异常重试的 stage、角色和恢复文案一律来自失败 Run 的冻结上下文，不读取与当前用途无关的旧 repair_assignment 来判定所有者。
- repair_state 保存真实用途；executor_test 不得写 implementation。测试轮只给“继续当前测试及其必要修复”的职责，planner_takeover 只给规划修复且不跑测试，planner_commit 只处理提交。
- 只有真实源代码／批准范围／环境变化按既有影响规则更新结果适用性。普通重试不删除人工验收、不把全部历史复核作废。review 是历史事实，保留原结论及来源；代码修复后的旧报告可以注明适用版本变化，但不能据此强制开启新的复核。
- 执行失败次数仍有上限，按现有逻辑有界恢复；协议冲突直接停在当前阶段，不新增“不断换 Run 到成功”为止的策略。

### 3.4 封闭反馈、恢复和重复消息中的回开发入口

在 engine.ts 的 finalizeNativeDelivery 中，让策略 2 当前用途的完成路由先于通用 implement 回退逻辑生效。

- 普通待处理反馈绑定接收时的业务阶段和 Run 作用域：测试阶段继续 executor_test；人工验收阶段处理 functional_fix／既有验收指导；质量整改阶段保留对应整改角色；提交阶段的代码问题交阶段内规划修复。不能用一个非空 pending feedback 将所有阶段改成 implement。
- 反馈已被当前 Run 处理后标记已消费；迟到反馈继续按所属阶段处理，不重复消费。
- `executor_test + before_human + completed` 的唯一后继为 HUMAN_PENDING；`executor_test + after_human + completed` 的唯一后继为 planner_commit。
- 在现有 dispatch 和恢复入口验证待派发用途与持久业务阶段的对应关系。第 5 步之后允许带明确 quality assignment 的 implement 表示执行整改，禁止不带来源的初次 implement；不以用途名称 alone 判断回退。
- 被旧 Run 的迟到结果、旧 outbox 或断线恢复触发的非法后退不执行，记录上下文冲突并保留当前业务阶段。不会为了让进度条看起来向前而启动错误角色。

### 3.5 界面和记录一致

- activity.ts 的 workflowProgress 使用 business_progress；workflow-status.ts 使用相同阶段及 activity 生成标题和说明。
- 队列中的测试重试显示“整改后测试等待重试”；实际运行显示“验收前质量审查 · 整改后测试”，不出现“规划模型接手”或“自主开发与自测”。

- ReviewResults.tsx 接收当前整改进展：有问题的复核已由后继整改处理时显示“本次复核发现 5 项问题；规划整改已完成，正在整改后测试”。不再无条件提示“以新一轮结果为准”，因为策略 2 此处不会再产生新一轮复核。
- 工作包完成与交付状态继续显示各自事实；不因队列重试重新清空已完成的工作，不把阶段序号当工作包交付证明。

## 6. 当前受影响任务的恢复与历史数据处理

1. 发布前按现有暂停机制等待在途 Run 停止并确认退出，保存 SQLite 一致性备份、目标实体和事件游标。不得直接复制仍在写入中的主 sqlite 文件而遗漏 WAL，也不得为处理本任务终止其他任务。
2. 回填业务阶段时读取持久 Run、quality_flow、assignment、正式完成结果及完整 StateChanged 历史，不使用前端最近 500 条事件取最大值。按已记录正式业务事件重建，并排除技术状态和错误排队标签。本任务明确回填为 pre_acceptance_review／executor_test。
3. 不把旧 changes_required 复核改成 passed。保留报告原文、规划修复完成及其 source_run 关系；展示已完成整改、待测试交接。既有 stale 被多次覆盖原因时不批量恢复“有效”，用原事件和后继完成关系展示历史用途。
4. 部署修复后，先重新读取当前状态：若已经到 HUMAN_PENDING 或之后则保留前进结果，此次恢复不重复派发。
5. 若仍停在本次测试回执冲突，选择当前冻结测试逻辑轮次中最后一份由真实 CLI 正常结束产生的 completed 回执，恢复范围仅限失败原因恰为 DELIVERY_CONFLICT 的记录。使用其自身 Run 身份处理，不改写为别的 Run；等待中的后继技术重试先按现有机制撤销。
6. 增加受控结果恢复入口，绑定 workflow version、logical_round_id、原 Run、回执记录和当前阶段；在无活跃写入者、无后继成功结果的条件下重放原结果到新的运行级接收路径。同一事务写入恢复记录和后继状态；重复执行返回同一 receipt。不能直接把 workflow.state 手改成人工验收。
7. 没有符合上述条件的 completed 回执时，继续原 executor_test，仅完成尚未完成的测试及结果说明；不得派发初次 implement。该分支是确定的错误处理，不是待排查事项。
8. 只从“未来恢复材料”中排除可精确关联到本次回执错误的通用开发指令，原始事件和原用户反馈完整保留。不清空整段 workflow.feedback，不重写原开发计划。
9. 测试完成路由仍由既有策略 2 决定：此任务只进入 HUMAN_PENDING，人工功能验收和最终代码复核不被自动跳过。

回填用现有 entities 机制并保存 `workflow_progress_migration` 记录，包含迁移前值、workflow version、事件游标和迁移版本；迁移可重复执行。活跃 Run 不做事中修改，等当前安全边界再执行。多个角色、恢复入口共用同一解析函数，不能各自猜测阶段。

## 7. 发布、回滚和停止条件

实施顺序为：隔离实现与定向回归 → 构建 → 独立实例验证 A16 → 安全暂停受影响任务 → 备份／迁移 → 原子替换对应构建产物并重启控制器 → 核对实际加载版本 → 恢复本任务 → API／数据库／真实浏览器读回。

回滚同时处理程序与新增进度数据：暂停受影响任务，恢复上一构建；新增实体为兼容性附加数据，可由旧版忽略。需要撤销目标任务迁移时，必须验证 workflow version 仍等于迁移后的预期值；已有后续任务进展则不得用旧库覆盖。保留原始回执和迁移记录以便向前修复，不回滚用户代码、Git 分支、会话或其他任务数据库记录。

以下情况停止发布／恢复并保留现场：任一 A01—A16 未满足；目标 Run 尚未退出；版本检查冲突；回执身份不匹配；已存在更晚成功交接；恢复会覆盖用户新操作；构建或真实浏览器显示与数据库阶段不一致。停止的是对应操作，不将任务主流程降回开发，不把未验证写成通过。
