## 3. 确认的问题与具体改法

### CQ-01 / P1：执行结果的状态被忽略，求助或不明输出会变成完成

位置：[profile-runtime.ts:246](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:246)、[engine.ts:1273](C:/Code/system-handle/packages/core/src/engine.ts:1273)、[engine.ts:1406](C:/Code/system-handle/packages/core/src/engine.ts:1406)、[engine.ts:1580](C:/Code/system-handle/packages/core/src/engine.ts:1580)。关联原计划“最小交接”和 R1。

触发：执行模型返回约定允许的 `need_user`、`need_planner`，或未给出可辨认的完成意图。

根因：`ProfileRuntime.execute` 无论状态为何都调用 `deliver`；解析失败还会补成 `status: completed`。`Engine.deliver` 不按该状态分流，直接写入通过的交付并进入交接；无交付记录时 `finalizeNativeDelivery` 又会凭进程正常结束生成“本轮执行已完成”。进程正常结束与开发完成被混为一谈。

影响：需要用户输入的任务进入代码审查，需要规划澄清的任务被当成已开发完，界面也会显示错误的完成状态。

整改：

1. 在公共合同层定义唯一的执行结果归一化入口，识别 `completed / need_planner / need_user / unclear`；兼容旧字段，但禁止将未知状态或解析失败默认归为完成。
2. `ProfileRuntime`、原生 agy 结束处理、MCP 交付统一调用同一个结果接收方法。运行身份由平台补入，保留模型原文。
3. `completed` 才记录本轮完成并派发质量审查；`need_planner` 进入规划澄清；`need_user` 保留来源角色进入等待输入；`unclear` 在原会话只补问当前意图。
4. `finalizeNativeDelivery` 只消费已记录的明确完成事件，正常退出仅代表通信/进程结束。不得因没有详细清单而拒绝明确的完成声明。

预期：同一执行结果经三种接入方式都落到相同状态；求助不会生成完成记录，也不会使整改计数增加。

### CQ-02 / P1：不明审查结果被当成拒绝，等待输入后恢复到执行角色

位置：[engine.ts:2839](C:/Code/system-handle/packages/core/src/engine.ts:2839)、[engine.ts:2861](C:/Code/system-handle/packages/core/src/engine.ts:2861)、[profile-runtime.ts:782](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:782)、[recovery.ts:146](C:/Code/system-handle/packages/runtime/src/recovery.ts:146)、[engine.ts:730](C:/Code/system-handle/packages/core/src/engine.ts:730)。关联原计划 P13、R1、R3。

触发一：审查返回 `{summary: "稍后补充结论"}`，没有通过、修改或求助意图。当前可选字段合同接受它，随后 `!passed` 分支直接派发整改。文本解析失败时，普通审查还会使用旁路问答的兜底，生成 `{answer: ...}` 后落入同一路径。

触发二：审查明确返回 `need_user`，进入 `WAITING_INPUT`。用户补充回答或恢复后，`feedback(within_plan)`、`resumeApproved` 固定转 `QUEUED/execute`，没有恢复这次审查的路由。

影响：无具体质量问题也能启动空整改；用户回答审查问题却再次启动开发，原问题和审查阶段无法正确续接。

整改：

1. 归一化审查意图为 `passed / changes_required / need_user / unclear`，允许正文表达问题，只有明确修改意图才派发整改。未知输出不能等价于质量不通过。
2. 旁路问答的文本恢复只用于旁路问答；执行和审查的非结构化输出进入各自的意图归一化流程，不因未使用 JSON 而要求重做工作。
3. 等待时持久化来源 `purpose/role/session/phase/run` 和待回答问题。用户反馈、恢复 API 和调度器按该记录继续原角色。
4. 原会话仍可用时继续原会话；真实会话失效时沿运行恢复机制处理，不静默改派执行角色。补问本身不计质量失败。

预期：不明输出只触发一次针对意图的补问；审查求助收到回答后继续该阶段代码审查，不生成空整改轮次。

### CQ-03 / P1：审查重放不幂等，提交失败后无法可靠重试

位置：[quality-coordinator.ts:192](C:/Code/system-handle/packages/core/src/quality-coordinator.ts:192)、[engine.ts:2897](C:/Code/system-handle/packages/core/src/engine.ts:2897)、[engine.ts:3047](C:/Code/system-handle/packages/core/src/engine.ts:3047)、[engine.ts:3141](C:/Code/system-handle/packages/core/src/engine.ts:3141)。关联原计划 R2、R3 及提交恢复。

触发：同一轮简化审查结果重投，或代码质量通过后 Git 提交失败，用户选择重试提交。

根因有两处：

- `evaluateReviewResult` 每次为缺省的 `reviewed_at` 生成新时间，再将整个结果计算哈希。同一内容重投会得到不同哈希，报 `IDEMPOTENCY_CONFLICT`。
- 首次审查接受 `pass / passed / quality_pass` 以及 `status` 字段，`retryCommit` 却只接受 `review.verdict === "pass"`。即使是 `pass`，它仍重新调用 `receiveReview`，再次生成时间戳并重新评估已经通过的审查，受到前一个问题影响。

整改：

1. 在首次接收时统一状态别名并保存规范化结果；接收时间只生成一次。
2. 去重依据固定运行身份和规范化的实质结论。默认值从首次持久化结果取得，不能每次读取当前时间、当前轮次再拼出不同内容。
3. 将审查接收与 Git 交付拆成可分别调用的方法。提交重试直接恢复原提交意图和各仓库提交进度，不重新执行质量结果接收、阶段计数或人工状态迁移。
4. 保留对同一运行互相矛盾结果的冲突处理，以及停止/失效运行不能改变当前任务的限制。历史 `pass` 和新的 `passed` 都兼容。

预期：相同审查事件重复处理返回原决定；Git 短暂失败后可完成原提交，已提交的仓库不重复提交，也不要求模型再审或重测。

### CQ-04 / P1：历史实现轮次可能被误计为本次质量整改

位置：[quality-coordinator.ts:117](C:/Code/system-handle/packages/core/src/quality-coordinator.ts:117)、[quality-coordinator.ts:144](C:/Code/system-handle/packages/core/src/quality-coordinator.ts:144)、[quality-coordinator.ts:260](C:/Code/system-handle/packages/core/src/quality-coordinator.ts:260)。关联原计划 R2。

触发：同一计划存在初次开发和已计数的整改运行；没有新的整改运行完成，又收到一次新的审查拒绝。

根因：`completedExecutorRepair` 检查了 assignment 的来源，却从该计划所有成功实现运行中挑选“还没被计数的最后一个”。没有要求该运行属于当前 assignment/source review。因此排除已经计数的整改运行后，可能倒退选中初次开发或另一旧运行。

影响：没有新整改也能增加连续失败次数，使规划模型提前接管。内存调用已确认能选中 `initial-implementation`。

整改：

1. 派发整改运行时写入平台生成的整改 assignment 标识、来源审查和阶段；审查请求明确关联被审查的执行完成事件。
2. 计数只采用该关联链上的实现运行，核对任务、阶段、计划版本、完成状态及是否已消费。禁止从历史未消费运行中回退挑选。
3. 审查保存、计数更新、assignment 更新和下一次派发放入同一事务；重投返回原决定。
4. 历史计数保留。新轮次建立明确关联；旧记录能从现有派发/审查记录确定关联时兼容读取，关联不明时不能猜测并追加计数，也不能把合法接管清零。

预期：首次发现计 0；恰好三轮不同的已完成整改分别被拒绝后才接管；重复审查、无新整改、运行故障均不增加计数；两阶段互不影响。

### CQ-05 / P1：轻量完成路径允许没有快照，最终提交却强制读取快照

位置：[engine.ts:1415](C:/Code/system-handle/packages/core/src/engine.ts:1415)、[engine.ts:1580](C:/Code/system-handle/packages/core/src/engine.ts:1580)、[profile-runtime.ts:310](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:310)、[delivery-coordinator.ts:113](C:/Code/system-handle/packages/git/src/delivery-coordinator.ts:113)。关联原计划 R1、R3 和 Git 交付。

触发：原生执行完成但没有详细交付清单，或交付时技术快照生成失败且任务没有旧快照。

根因：轻量结束路径不创建快照；`deliver` 又吞掉快照异常。代码审查可继续，但原生 Git 交付仍调用 `store.must("snapshot", w.snapshot_id!)`，没有创建候选的兜底。若沿用旧快照，提交候选还可能与当前改动不一致。

影响：正常完成、自审查和人工确认都能经过，最后却在提交阶段进入 `COMMIT_PARTIAL`；恢复还受 CQ-03 影响。

整改：

1. 将提交所需快照作为 Git 事务的技术候选，在首次提交时、取得工作区写锁后创建并持久化；不能依赖可选交付附件替它生成。
2. 保存明确的提交意图与候选关联，重试复用同一候选和各仓库提交结果。候选创建失败按 Git 操作失败恢复，不倒退成开发/测试失败。
3. 代码审查读取当前仓库差异及原计划，不依赖测试证据快照。提交候选需对应这次审查后的同一组代码；若期间出现新的代码修改，保留变更事实并按当前任务意图处理，不能悄悄提交旧候选。
4. 保留分支、工作区归属、并发写入和 Git 冲突保护；不把技术快照重新变成执行到审查之间的证明关卡。

预期：只报告明确完成、无测试附件的新任务也能走到正常提交；创建候选或提交失败可恢复，不误用上一轮代码。

### CQ-06 / P2：可选报告导入仍处于交接必经路径，文件异常会阻塞完成

位置：[engine.ts:1392](C:/Code/system-handle/packages/core/src/engine.ts:1392)、[delivery-importer.ts:64](C:/Code/system-handle/packages/evidence/src/delivery-importer.ts:64)、[delivery-importer.ts:97](C:/Code/system-handle/packages/evidence/src/delivery-importer.ts:97)。关联原计划 R3、R6。

触发：附带报告在存在性检查后消失、读取受限，或者归档目录写入失败。

根因：完成状态落库之前同步执行 `DeliveryImporter.importDelivery`。该调用为所有工作区计算文件指纹，并执行报告 `stat/read/hash/write`；除路径解析外，这些 I/O 异常没有隔离。

影响：可选资料问题使真实模型完成无法交接，且每次交接承担全工作区扫描成本。此项是异常处理与职责耦合缺陷，与报告是否真实无关。

整改：先事务化保存模型完成意图及下一角色派发，再把附件索引/归档交给独立的可选资料处理；每个附件分别限制路径、大小、读取和归档错误。资料失败只影响该附件展示，不撤销完成、不增加模型重试次数。取消角色交接前强制计算测试输入指纹；Git 候选按 CQ-05 单独处理。

预期：附件不存在或不可读时仍正常交接，界面能显示附件读取状态，调度不等待全仓扫描。

### CQ-07 / P1：人工反馈的功能修复在质量审查之前直接交人工复测

位置：[engine.ts:1636](C:/Code/system-handle/packages/core/src/engine.ts:1636)。关联原计划第 5 节功能修复路径及 R8。

触发：已有 `functional_fix_intent` 的执行轮次完成。

根因：`finalizeNativeDelivery` 将问题标记待复测后，直接转 `HUMAN_PENDING/functional_retest` 并返回，跳过下方 `REVIEW_QUEUED` 分支。

影响：这一轮新修复代码在代码质量审查之前交给用户。人工确认后的终审仍可能执行，但不能替代原计划规定的“修复完成 → 代码审查 → 人工复测”顺序。

整改：功能修复完成也先按来源阶段派发代码质量审查；问题可记录“修复已交接”，人工复测入口在质量通过后开放。将功能问题 ID、完成事件和来源阶段一起传递，审查修改后仍保留问题关联。人工确认之后继续既有人工后审查，不伪造人工通过或清除另一阶段计数。

预期：首次交付和功能反馈修复都先审代码，再交人工；质量拒绝时继续本轮整改，人工入口不会提前进入待验收状态。

### CQ-08 / P2：提交冲突修复完成后硬切人工前阶段，并注入已删除的程序自查步骤

位置：[engine.ts:1973](C:/Code/system-handle/packages/core/src/engine.ts:1973)。关联原计划 R2、R3、R8。

触发：人工确认、人工后代码审查通过，提交整合产生冲突，责任模型完成冲突处理。

根因：`handleMergeConflictResult` 不读取原阶段，固定写入 `before_human`，同时向执行模型发送“完整补测”“完成程序计划自查”的旧指令。另一个提交恢复分支却使用 `after_human`，两条恢复路径语义不一致。

影响：提交后的恢复跳回错误阶段，后续计数、人工确认承接与正常终审恢复不一致；执行模型还会被引导寻找已取消的自查步骤。

整改：冲突请求保存来源阶段、提交候选和原人工确认关联；处理回执后继续该来源阶段。需要落实冲突后的代码调整时，把具体冲突与变更交给责任模型，由其完成整批修改和必要自测后交代码审查。删除程序自查指令；是否影响功能由模型说明，影响功能则按已有人工复测安排处理。

预期：人工后提交冲突恢复仍使用人工后阶段；保持合法计数和人工确认历史，不凭冲突事件自动倒退到人工前完整流程。

### CQ-09 / P1：旧任务的新轮次仍走旧受控执行路径，与新交接协议不兼容

位置：[runtime.ts:444](C:/Code/system-handle/packages/runtime/src/runtime.ts:444)、[runtime.ts:470](C:/Code/system-handle/packages/runtime/src/runtime.ts:470)、[runtime.ts:570](C:/Code/system-handle/packages/runtime/src/runtime.ts:570)、[tools.ts:674](C:/Code/system-handle/packages/mcp/src/tools.ts:674)、[engine.ts:1267](C:/Code/system-handle/packages/core/src/engine.ts:1267)、[engine.ts:2430](C:/Code/system-handle/packages/core/src/engine.ts:2430)。关联原计划 L01/L02、R7。

触发：恢复或继续历史 `legacy/leaf-v1` 任务，保留原计划数据。

根因：运行模式仍由历史 `task_model` 决定。旧 agy 分支安装旧 hook，提示只能使用 worker 工具，并要求 freeze/run_check/finish；MCP 也仍按旧模式暴露这些工具。若该任务走新的 ProfileRuntime 完成接口，`Engine.deliver` 又只接受 `native-v2`。旧 VERIFYING 成功分支则直接转人工确认。

影响：旧任务继续执行时仍受平台逐项测试控制；遵循新 Skill 的模型可能找不到兼容的完成接口，走旧接口又绕过新人工前质量审查。这是运行时兼容遗漏，不是要求重新证明旧任务测试情况。

整改：

1. 将历史计划格式与当前运行交接协议分开表示。历史任务保留原计划、版本、任务编号及批准记录，新派发轮次统一使用轻量协议。
2. 在调度入口、运行配置生成、MCP 注册、结果接收和恢复入口集中解析该协议，避免每层自行判断 `task_model`。
3. 新轮次停止注入旧 hook 和 freeze/run_check/finish 指令；旧资料继续可读，历史接口只作兼容读取或明确的旧运行收尾适配，不成为新运行前置步骤。
4. 新完成接口覆盖历史计划格式，并统一进入两阶段代码质量流程。
5. 已运行会话按其当前协议平稳收尾；STOPPED、WAITING_INPUT、WAITING_AUTHORIZATION 保持状态，不自动重启、不迁移到新任务。

预期：继续旧任务与新建任务使用相同职责边界；历史记录完整，已有接管和暂停行为不变。

### CQ-10 / P2：整改执行中仍因上一轮交付显示全部任务完成

位置：[engine.ts:977](C:/Code/system-handle/packages/core/src/engine.ts:977)。关联原计划 R6。

触发：同一计划已有一次完成交付，质量整改或功能修复开始新的执行轮次。

根因：`taskStatus` 通过“同 run 或同 plan_revision”匹配交付，匹配到上一轮 `passed` 就把所有任务标成完成；它没有区分当前实施轮次与历史完成事实。

影响：任务处于排队或执行整改时，界面仍显示全部开发完成，摘要和完成时间来自旧轮次。

整改：状态投影使用当前实施轮次/完成事件的显式关联，并区分历史开发完成和本轮整改进展。质量审查期间应关联它正在审查的执行完成事件，不能简单要求当前审查 run 等于执行 run。整轮完成仍接受模型声明，不重新引入测试证明或逐项 claim；历史摘要保留为历史。

预期：新整改运行显示正在整改；该轮明确完成后更新当前状态；历史完成信息可查看，但不覆盖当前轮次。

### CQ-11 / P2：兼容事件补拉超过 4000 条积压后无法继续推进

位置：[use-event-catchup.ts:21](C:/Code/system-handle/apps/web/src/use-event-catchup.ts:21)、[main.tsx:1928](C:/Code/system-handle/apps/web/src/main.tsx:1928)。关联原计划 R6；仅影响启用旧控制器兼容补拉的界面。

触发：已有非零游标，标签页后台停留或连接中断期间新增超过 4000 条事件。

根因：单次补拉达到上限且还有前页时直接返回，不接收事件，也不保存分页位置。下一次轮询重新从最新页开始，重复读取同一批 4000 条，无法填平缺口。

影响：连接恢复后活动记录持续停留在旧状态；不是一次性延迟，而是没有后续推进条件。

整改：将一次补拉的目标上界、分页位置、已收集事件与完成游标分开保存。达到批次上限后下次从保存的分页位置继续；缺口补齐后按序去重投递并推进游标，随后追赶新的上界。积压较大时分段投递并维护连续区间，避免无界内存。切换任务或卸载时丢弃该任务未完成请求的回调。

预期：超过 4000 条的积压能在多个有限批次中持续推进，最终补齐；切换任务不混入前一任务事件。

## 5. 执行模型的回归责任

以下是修复后的行为目标，供执行模型在全部开发完成后统一验证；不是要求复核模型追查既有测试声明。

| 层次 | 应覆盖的行为 |
|---|---|
| 单元 | 执行/审查意图归一化；未知结果不伪造完成或拒绝；相同结果重投稳定；历史运行不充当新整改；三次计数和双阶段隔离；进度投影；跨批次事件游标。 |
| 集成 | 各适配器完成接口到派发的全链路；审查求助与回答后恢复；执行求助/规划澄清；重复 outbox 消息；附件读写失败不影响交接；无快照首次提交；部分仓库提交后重试；冲突恢复；旧计划格式的新轮次。 |
| E2E | 真实工作台中的初次交付→人工前审查→人工确认→人工后审查；两阶段各自三次整改接管；功能反馈修复先审查后复测；审查求助后继续；暂停/恢复；提交失败后重试；历史任务继续；整改进度与大量事件补拉。 |

不把异常处理改为静默忽略：Git 真失败应保留可恢复原因；会话真失效仍走运行恢复；附件失败只影响附件；未知模型意图只补问意图。普通独立开发任务继续使用项目原生命令，不因读取 DevFlow Skill 就创建或恢复工作流。
