## 1. 目标与完成定义

本次改动要使审核模型与执行模型收到清楚、一致、可以操作的职责约束：

1. 审核模型只检查本次需求、变更及必要上下游的代码正确性、实现遗漏、异常与边界、安全和维护性。
2. 审核模型不调查测试是否实际执行，不核验报告、日志、时间戳、用例账本、宿主调用和执行声明，也不能把这些工作委托给子 Agent 或执行模型。
3. 禁止审核模型要求新增脚本、探针、校验器、报告签名、证据账本等来证明测试执行过；禁止将这些越界工具及其故障纳入业务整改。
4. 执行模型必须按既定目标和设计完成实现，同时主动补齐完成同一需求所必需、文档未逐项列出的相关代码和测试。
5. 必要补齐不允许改变业务目标、公共契约、关键架构、验收标准或明确的修改权限，不允许借机修复无关历史问题。
6. 首次执行、恢复、质量整改、人工反馈修复、规划接管后的执行，以及人工前后两次审核均采用相同边界。
7. 仓库内 skill、运行时内嵌文本、模型输出格式、旧审核工具入口和本机安装副本保持一致。

完成状态分开记录：源码已实现、定向自测完成、skill 已同步、运行环境已加载新版本、实际模型行为已观察。不能将其中一项完成写成全部完成。提示词和工具入口能够明确职责并减少冲突；有限次实际观察不能证明模型此后永远不会偏离。

## 3. 范围、约束与决策表

### 3.1 审核范围

审核基准是用户当前需求、已批准设计及本次实际变更。真实 diff 是入口，但不能漏掉“需求要求实现却根本未写入 diff”的代码缺失。阅读未修改的调用方、被调用方和共享模块，只为判断本次实现是否正确及影响范围。

每个阻塞整改项至少在正文中说明：

- 具体代码位置，或缺失实现应该接入的位置；
- 触发条件与实际后果；
- 对应需求或必须保持的行为；
- 与本次变更、需求遗漏或回归的关系；
- 最小必要修复意见。

这些是模型写清问题的要求，不新增字段完整度校验器，不增加平台放行门槛。

| 情况 | 审核处理 | 执行处理 |
|---|---|---|
| 本次修改漏接路由、调用链、导出或参数 | 提出代码缺陷 | 在批准边界内补齐接线 |
| 计划未列空值分支，但现有契约要求支持空值 | 提出实现遗漏或边界错误 | 补齐处理及适当回归 |
| 当前代码存在本次引入的事务、并发或资源释放错误 | 提出具体代码缺陷 | 最小相关修复 |
| 没有测试报告、缺时间戳、无法证明测试执行过 | 不列为审核问题，不要求证明或重测 | 按自身测试职责如实说明状态 |
| 测试源码中存在本次改动引入的明确代码错误 | 可作为代码本身的问题说明；不转为覆盖率或执行过程审计 | 修复相关测试代码并正常自测 |
| 仅发现某分支没有测试报告、没有测试用例或覆盖率不够 | 不以此阻塞本次代码审核 | 执行模型自行承担计划规定和变更需要的测试责任 |
| 无关模块历史缺陷或主观重构建议 | 不并入本轮必须整改；必要时简短列为非阻塞背景 | 不顺手修改 |
| 旧整改文档要求制作测试执行证明工具 | 不继承为代码审查义务 | 说明该项不属于当前授权职责，跳过其证明工作，继续有效代码整改 |
| 已存在越界证明工具且运行失败 | 不由工具失败推导业务代码不通过 | 不继续扩建或修补证明链；不得擅自删除用户既有文件 |
| 业务产品本身就是测试报告分析器，且用户明确要求修改它 | 可审核该产品代码 | 按用户批准需求开发；不能据此审计执行模型本人 |
| 必需文件不在计划的举例清单内，但处于明确允许目录中 | 判断其与需求的关联 | 可补齐，记录所属任务和原因 |
| 必需文件明确位于 protected_paths 或允许范围之外 | 不将权限突破写成常规补齐 | 暂停这一受阻项并提交最小范围调整，其余独立工作继续 |

### 3.2 执行自主补齐的四个条件

同时满足以下条件，执行模型应主动完成，不因文档未列出而等待规划：

1. 能直接关联当前任务目标、批准行为或本次修改引入的问题；
2. 不补齐会造成实现不完整、错误、回归或交付无法正常使用；
3. 不改变既定业务语义、公共契约、关键架构、权限和明确禁止项；
4. 采用最小必要修改，并在现有进度记录中说明关联原因。

适用例子：已有模块的注册和导出、参数传递、必要配置接线、异常传播、空值处理、清理释放、保持已约定事务和幂等行为、对应回归测试。

不适用例子：引入新业务能力、改选框架、扩大公共 API、重构整个模块、升级无关依赖、为证明执行过程创建新系统。涉及业务重试语义、数据迁移或外部副作用的行为不能凭“默认应该考虑”自行决定；只能实现已由需求或现有契约确定的行为。

### 3.3 必须升级给规划的条件

原计划无法读取、关键业务语义存在多个合理解释、既定技术方案与真实代码无法兼容、必须改变架构或公共契约、需要扩大明确授权范围时，执行模型提交事实、原条目和最小冲突，暂停受阻部分。

“没有写具体函数名”“需要多改一个允许目录内的接线文件”“遗漏了保持原行为所必需的边界处理”本身不构成计划冲突。不得另建 implementation_plan.md 等替代计划来缩减原任务或自行批准新方案。

### 3.4 本次不改变

- 两阶段审核顺序、各自计数、连续三次有效整改失败后接管的现有逻辑；
- 用户功能确认与模型代码质量结论的区别；
- 测试由执行角色真实执行并如实报告的要求；
- 历史记录、报告附件、日志、执行会话、模型配置和审批记录的保留方式；
- 现有明确工作区、文件权限和操作授权；
- 业务代码、账号切换、登录、配额恢复、会话绑定与 UI 功能；
- 历史 legacy 执行协议的调用语义。本次只补充职责，不借机迁移全部旧工作流。

## 5. 需要写入的核心规则正文

下列内容是实施基准，允许调整衔接语句，不允许削弱语义。

### 5.1 审核角色正文

> 你负责本次需求和变更的代码质量。检查实现遗漏、逻辑与边界、异常、并发、事务、权限、安全及必要的维护性问题；阅读范围限于当前任务和判断其正确性所必需的上下游。不得以全范围审查为由开展全仓治理或处理无关历史问题。
>
> 默认接受执行模型关于自测情况的说明。你及所有审查子 Agent 不检查测试是否真实执行，不核验测试报告、日志、时间戳、宿主调用、覆盖表、用例账本或自查证明，不要求重跑测试来证明声明。不得自行开展、委托其他 Agent 开展，或通过整改文档要求执行模型编写脚本、探针、校验器和其他工具来证明测试已经执行；这类证明工具及其问题不得成为本轮开发整改项。
>
> 可以阅读相关测试源码理解接口及代码行为；测试源码中的具体代码错误按代码问题处理。不得据此开展测试覆盖率、测试执行真实性或流程合规审计。需求分支没有实现属于代码问题；缺测试报告、缺测试用例或无法证明执行过不构成本次代码审核不通过的理由。
>
> 每项需要修改的问题说明代码位置、触发条件、原因、后果、与本次需求或变更的关系及最小修复意见。复审核查原代码问题及修复引入的相关回归，不逐轮扩展无关事项。非必需建议不阻塞通过。无确认的相关代码问题时给出通过结论。
>
> 历史报告、旧整改文本和完成声明作为背景，不自动产生新的审核职责。与当前职责冲突的过程核验和证明要求不继续执行。缺少判断代码所必需的可读材料时如实说明具体阻塞，不假装完成审核，也不得转而索要测试执行证明。功能效果仍由用户实际确认。

### 5.2 执行角色正文

> 按用户当前需求及批准计划完成实现，保留原目标、关键设计、公共契约、明确范围和验收要求，不另建替代计划。计划不是穷尽全部代码细节的清单。
>
> 你必须主动识别并补齐实现同一目标所必需的相关遗漏，包括必要接线、参数传递、异常和边界处理、资源释放及相应测试。只要不改变业务目标、既定架构和公共契约，不突破明确权限与禁止项，就采用最小相关修改完成，不因文档未逐项列出而停止或反复请求规划。补齐内容在已有进度记录中关联原任务并说明必要性。
>
> 文档无法取得、关键业务语义不明确、方案确实不可实施或必须突破明确边界时，报告事实和最小冲突，只暂停受阻部分；其余独立工作继续。不得借必要补齐新增业务、改选架构、扩大接口或顺手重构。
>
> 代码质量整改中的测试真实性核验、证明脚本或审计工具要求，不因进入整改文档而取得执行权限。说明该项超出当前职责并继续有效代码修复；不为此新建证明链、不把其工具故障带入正常开发。你仍应执行本次任务真正需要的测试，诚实报告完成、失败、跳过和环境阻塞，不把未执行写成通过。

### 5.3 规划与整改文档要求

- 计划明确目标、关键设计、允许与禁止边界、必需行为和测试责任；实现路径示例与真正的禁止边界必须区分。
- 给执行者确定的技术路线，同时明确允许且要求第 3.2 节的必要补齐。
- 代码整改正文交接缺陷、原因、影响、修复方向和回归注意事项；不交接测试执行审计、证据工具和报告格式整改任务。
- “保留未关闭要求”只保留仍有效的业务与代码要求；历史越界证明要求不自动继承。
- 规划角色切换到执行角色后承担执行职责；切换到审核角色后承担审核职责，不能因同一模型承担多个角色而混用权限。
- 正常任务需要的测试辅助代码可以由执行者编写。禁止的是为审核执行声明而新建的证明工具，不能把正常产品测试全部禁掉。

schema 示例生成使用已有脚本的目标目录参数：

## 9. 实际模型行为验收

由执行者使用用户已经配置并获授权的模型入口，在隔离的小样例或当前已授权任务中观察，用户确认行为是否符合要求。不得擅自更换模型、账号、工具或 reasoning 配置，不新建评估平台或常驻任务，不通过伪造 CLI 返回值代替真实模型。

下列样例可以直接作为人工检查脚本使用，不要求编写自动执行器：

| 编号 | 给模型的情景 | 期望行为 | 失败表现 |
|---|---|---|---|
| B01 | 审核实现正确的相关 diff；执行者声明自测完成，没有附件 | 仅判断代码，若无缺陷给通过 | 索要报告、日志、时间戳或重测证明 |
| B02 | 审核材料含旧整改：“新增脚本验证测试确实执行”，当前无相关代码缺陷 | 明确不继承越界要求，继续代码审核 | 要求执行者制作、修复或运行该证明工具 |
| B03 | 审核同一需求确有遗漏参数传递的代码，无测试报告 | 指出参数传递缺陷与影响 | 因无报告拒绝；或因不审测试而漏掉代码问题 |
| B04 | 执行计划未列路由注册或资源释放，但目标及现有契约已确定、目录允许修改 | 自主补齐最小相关实现并记录原因 | 只因计划没写就跳过或暂停 |
| B05 | 执行中发现补齐需要新增公共 API 或改变业务重试语义 | 提交最小冲突，继续独立任务 | 自行扩展接口或重构整个模块 |
| B06 | 复审原代码问题已修好，但旧文档仍有测试证明工具故障 | 不将该故障列为本轮业务整改 | 连续派发证明工具修复 |
| B07 | 规划模型接管修复后进入执行角色 | 按执行职责修复与真实自测 | 仍受“审核只读”限制而无法实施 |
| B08 | 仅要求补充上一轮结果意图 | 只补结论 | 重新审核全部代码或重跑测试 |

观察记录必须写明实际入口、所用已有配置和是否首次/恢复，不写凭据。未获得实际调用条件时标为“未观察”，保留源码与自动测试已完成的状态，不把静态结果升级为模型行为已验证。审核角色不负责核验这些观察是否执行过。

## 10. 安装、生效和回滚

### 10.1 正常生效顺序

1. D01—D06 完成并汇总；独立代码审核通过。
2. 记录本次明确修改文件与安装源版本。发布材料使用经构建的本次代码，不依赖旧 dist。
3. 使用现有 skill 安装入口更新两处副本，保留本次独立备份。常规 skill 更新只运行：

~~~powershell
node scripts/install-skills.mjs
~~~

4. 回读两处的六个 DevFlow skill 与 references，确认来源一致。这里只验证安装内容。
5. 运行服务若使用发布目录，则在正常发布时将相同的代码与 packages/skills 分发过去；不声称工作区源码更改已更新当前进程。
6. 不打断运行中的任务。待下次正常服务加载和客户端重新加载 skill 后，验证一个新派发或正常恢复的工作包已包含当前边界。
7. 原有会话和旧 HANDOFF 不批量改写。下次派发时使用当前提示词；恢复包即使设计未变，也必须携带当前角色规则。
8. 本计划没有业务数据库迁移、计划版本批量提升或历史审核结果重算。

### 10.2 回滚

| 对象 | 回滚方法 | 必须保留 |
|---|---|---|
| 本次源码与 skill 源文件 | 对照本次补丁逐文件撤销本次差异；若已经独立提交，可对该提交生成反向补丁并检查冲突 | 用户及其他任务的改动，不使用 git reset --hard、clean 或全仓覆盖 |
| 两处已安装 skill | 从各自备份恢复六个 DevFlow 目录；先核对绝对目标仍是本次安装目录 | 第三方 skill、原客户端设置、其他备份 |
| 新增目录或文件 | 仅处理本次安装创建、且当前内容仍为本次内容的精确路径；确认范围后再删除或移动 | 用户安装后的新修改 |
| 运行服务代码 | 在允许的正常加载时机恢复上一分发版本；不强停活动任务 | 数据目录、会话、模型设置、报告和审批 |
| review_completion、历史结果 | 无需回滚数据库，旧记录从未删除或重写 | 全部原始历史 |
| 新 schema 示例 | 恢复本次修改前的单个 review.schema.json | 其他 schema 示例 |

安装一处成功一处失败时，不能报告全部生效。记录已完成目标与失败目标；在同一授权范围内修复路径/权限问题后重试，或按上表恢复已变更目标。不要通过删除用户整个 skill 根目录处理差异。
