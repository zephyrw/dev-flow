## 2. CQ01：安装前没有覆盖链接与双目标路径关系

### 2.1 代码位置

- [scripts/install-skills.mjs:21](C:/Code/system-handle/scripts/install-skills.mjs:21)：单目标预检仅对字符串形式的 resolve 路径做 contains。
- [scripts/install-skills.mjs:40](C:/Code/system-handle/scripts/install-skills.mjs:40)：随后直接 mkdirSync 与 cpSync，没有链接检查。
- [scripts/install-skills.mjs:61](C:/Code/system-handle/scripts/install-skills.mjs:61)：两个目标先构造，但没有作为一个整体完成预检。
- [packages/clients/src/installer.ts:41](C:/Code/system-handle/packages/clients/src/installer.ts:41)：copyVerified 检查当前 src/dest 和子项的链接，不检查已存在父路径。
- [packages/clients/src/installer.ts:110](C:/Code/system-handle/packages/clients/src/installer.ts:110)：主目标与共享目标直接组成数组，没有规范化去重或关系检查。
- [packages/clients/src/installer.ts:208](C:/Code/system-handle/packages/clients/src/installer.ts:208)：源文件存在后即进入写入循环。

### 2.2 触发条件及后果

场景 A：userHome/.agents 或 userHome/.agents/skills 是指向其他目录的 Windows junction / 符号链接。

- scripts 入口的 resolve 不解析链接，contains 也不能发现物理路径偏离。
- ClientInstaller 从目标 skill 子目录开始 lstat；当链接位于父路径时，子目录自身可以是普通目录，检查仍通过。
- 后续 mkdir、备份和复制会沿父路径进入链接目标，在声明目标以外的位置写入。
- 原计划明确要求“不通过链接写入其他位置”，当前实现没有达到这一代码边界。

场景 B：自定义 CODEX_HOME 指向 userHome/.agents，主目标与共享目标变成同一个物理目录。

- 当前实现将同一位置按两次独立目标处理。
- 第二份备份可能记录第一轮已经更新后的内容，而不是另一处独立旧状态；回滚时容易把新内容重新覆盖回去。
- 这不是两个独立安装位置，结果必须去重，不能报告两处独立同步。

场景 C：自定义 backupRoot 与另一目标重叠，或后一个目标存在可预先发现的冲突。

- 当前只在各次 installSkills 进入时分别检查三条路径；没有在第一次写入前检查两个目标、两个备份和源之间的完整关系。
- 第一目标可能已经写入，然后才发现第二目标或备份不合法，留下可预先避免的半完成状态。

上述均由路径计算和文件调用链静态确认；没有在真实用户目录创建链接或运行安装探针。

### 2.3 确定修复方案

保留现有安装入口，不引入安装管理框架或外部验证工具。在两个已有安装实现中补齐有限的路径预检：

1. 先生成完整安装清单：源目录、主目标、共享目标以及本次六个 skill 的精确子路径。scripts 入口同时列出两个备份目录；ClientInstaller 保留原有同目录文件备份方式，预检其实际备份文件及父路径，不另建备份体系。
2. 路径用绝对形式规范化；处理 Windows 大小写等价。对目标完全相同的情况去重，只保留一个物理目标和一份原始备份，结果可同时标明其承担 codex/shared-agent 两个逻辑别名。
3. 源与目标、两个不同目标不得互为父子。scripts 入口的任一备份目录不得与源或任一目标重叠；ClientInstaller 既有同目录文件备份不适用目录互斥规则，但备份文件不得覆盖源文件、另一待安装文件或已有备份。
4. 在创建或写入任何目标前检查源、目标、备份路径的已存在组件。使用 lstat 识别 junction / 符号链接，不使用会跟随链接的 existsSync 作为唯一判断。
5. 路径含尚未创建的尾部时，逐级检查最近已存在的祖先，再处理未存在部分；识别悬空链接，不能把它视为普通不存在路径。
6. 预检六个源 skill 的目录及复制树；预检将覆盖的目标项及其父目录。发现链接即返回包含精确路径的错误，不跟随链接复制、备份或自动修复链接。
7. 完成整个安装清单的静态预检后，才开始备份和复制。复制前对当前即将使用的路径保留局部复查，发现路径已变成链接即停止。该检查用于处理普通路径变化，不声称实现对恶意并发替换的无竞态防护。
8. scripts 与 ClientInstaller 使用相同的拒绝/去重规则；保留各自现有单目标 API 和其他客户端的目标选择行为。
9. 不修改权限、解析链接后继续写到外部位置，不移动或删除用户链接；是否调整这些链接由用户决定。

必要实现细节由执行者在这两个现有文件内完成。不要为复用几十行检查代码新建通用文件系统服务；允许普通本地 helper 函数。

### 2.4 完成条件

- 链接位于 .agents、skills、某个 skill 或被复制文件层级时均会在写入前拒绝。
- 两个相同目标只安装一次，不生成互相矛盾的备份。
- 目标/备份跨目标冲突在任何目标写入前被发现。
- 被拒绝场景中用户已有文件与源文件不变。
- 允许的普通两目录安装仍保持六个 skill 和完整 references 同步。

## 3. CQ02：部分失败时安装回执丢失

### 3.1 代码位置

- [scripts/install-skills.mjs:74](C:/Code/system-handle/scripts/install-skills.mjs:74)：results 在循环中积累。
- [scripts/install-skills.mjs:79](C:/Code/system-handle/scripts/install-skills.mjs:79)：失败时先 push，随后默认直接 throw 原始错误。
- [scripts/install-skills.mjs:87](C:/Code/system-handle/scripts/install-skills.mjs:87)：CLI 的所有结果与 backupRoot 输出都在调用成功返回之后。
- [scripts/setup.mjs:75](C:/Code/system-handle/scripts/setup.mjs:75)：setup 同样使用默认抛出路径。

### 3.2 触发条件及后果

当 Codex 主目录完成更新，但共享 Agent 目录因只读、文件占用或复制中途 IO 错误失败时：

1. 第一目标已经是新内容，第二目标可能是旧内容或部分更新。
2. 内部 results 记录会随函数抛出而无法作为返回值取得。
3. 原始异常没有携带前面目标的完成情况和本次备份根目录。
4. CLI 的逐目标打印分支无法到达；调用者只得到错误堆栈，无法按本次 API 回执判断哪些目录已经改变、哪些备份可恢复。

程序确实会失败退出，因此本项不是“错误地宣称成功”；问题是多目标变更已经发生，却缺少完整的部分失败结果。原计划要求分别报告目标结果和备份，以免两处长期留在不同版本。

### 3.3 确定修复方案

1. 保留 throwOnError 兼容语义，但抛出的错误必须携带完整 report：backupRoot、逐目标状态、成功/失败 skill、失败位置、错误原因和是否可能发生部分写入。
2. 在现有脚本中定义轻量 InstallSkillsError 或同等本地错误对象。它仅承载结果，不负责自动回滚或验证测试。
3. 目标状态至少区分 completed、failed、not_started；复制中途失败的 failed 标注 partial=true，且列出实际已经完成的子项。
4. 默认遇到失败停止后续写入，将尚未处理目标标为 not_started；throwOnError=false 的显式调用可以继续其他独立目标，最终也返回同样结构。
5. CLI 捕获带 report 的异常，先逐目标打印状态与备份位置，再以非零退出码结束。只有全部实际目标完成才打印全部更新成功。
6. setup 捕获并输出相同部分失败摘要，停止后续依赖完整 skill 安装的配置步骤，不吞掉错误继续宣称配置完成。
7. 不自动撤回用户可能已经使用或再次修改的目标。恢复按已有备份逐目标执行；执行模型报告修复/重试范围。
8. 单目标 installSkills 的调用者继续能捕获失败；新增细粒度结果不能改变六个 skill 的白名单。

### 3.4 完成条件

第二目标写入失败时，调用方和 CLI 都能确定第一目标已完成、第二目标的失败/部分状态及备份位置；退出码失败。预检失败时所有目标标为未开始或拒绝，不出现虚构的成功结果。

## 4. CQ03：外层启动提示词仍要求读取全部引用文件

### 4.1 代码位置

- [packages/runtime/src/profile-runtime.ts:936](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:936)：invokePrompt。
- [packages/runtime/src/profile-runtime.ts:955](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:955)：普通分支仍写“必须先阅读全部材料和引用文件”。
- [packages/runtime/src/profile-runtime.ts:547](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:547)：该文本作为实际 adapter 启动/恢复 prompt 发送。
- [packages/runtime/src/profile-runtime.ts:424](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:424)：审核材料包含计划、历史交付和关联材料。

### 4.2 触发条件及后果

计划或历史交付引用测试报告、证明脚本、旧整改附件时，普通审核仍收到一条无范围限制的外层指令，要求把全部引用文件读完。

共享审核指导已经规定只读取代码判断所必需的内容，但外层启动文本没有同步。模型因而同时收到两种相互冲突的要求；“不核验测试”不能自动解释掉“先读取所有报告引用”的命令。这会继续引导无必要的材料读取，并可能把旧证明材料带回本轮审核。

这里确认的是实际发送文本的冲突，不是声称已经观察到某次模型因此越界。

### 4.3 确定修复方案

1. 修改 invokePrompt 的普通分支，要求先读取当前 handoff 的角色规则与任务正文，引用文件仅按当前任务和角色判断所需读取。
2. 审核目的明确补一句：不要求遍历测试报告、执行日志、证明附件；这些缺失不触发代码整改。
3. 执行目的保留完整读取计划及正式设计，必要实现材料按当前需求读取，不将历史证明要求自动继承为新待办。
4. 若使用 purpose 分支，必须基于现有 RunPurpose 的真实枚举，不猜测不存在的字符串；不改 adapter 选择、会话绑定或权限类别。
5. aside 和 intent_clarification 保持原有前置分支，尤其后者只补结果意图，不因增加读取规则重做全部任务。
6. 当前传入的 schemaPath、handoff 路径和结果对象格式保持不变；不新增引用文件扫描器，不按关键词自动删用户文档。

建议普通分支基础措辞：

> 先读取当前工作包中的角色职责、任务正文与批准设计；引用材料仅按本次任务及当前角色判断所必需的范围读取。历史材料只作为背景，不自动产生新的流程或证明任务。按指定输出格式返回本轮结论。

审核分支附加明确的代码范围限制即可，不必在外层再次重复整份长版 skill。

### 4.4 完成条件

实际交给 adapter 的普通审核 prompt 不再包含“全部引用文件必读”的要求；首次和正常恢复一致。代码相关设计与必要上下游仍可读取，意图续问不重新启动审核。

## 5. CQ04：冲突修复入口未接入共享执行边界

### 5.1 代码位置

- [packages/runtime/src/profile-runtime.ts:249](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:249)：resolveMergeConflict。
- [packages/runtime/src/profile-runtime.ts:263](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:263)：materials.instructions 仅有冲突专用文本。
- [packages/runtime/src/profile-runtime.ts:284](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:284)：直接调用 invoke，不经过 executeMaterials。
- 对照 [packages/runtime/src/profile-runtime.ts:393](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:393)：普通执行入口已拼接 executionScopeInstructions。

### 5.2 触发条件及后果

任务进入合并冲突修复，尤其因为用途/绑定变化创建新会话时，接收到的工作包只有“主动补齐解决冲突所必需的接线与调整”等简短文本。

该路径没有收到共享执行边界中以下规则：

- 旧整改文档中的测试真实性和证明工具要求不取得执行权限；
- 必要补齐不得改变既定公共契约和关键架构；
- 只暂停真正受阻部分，其余独立工作继续；
- 同一模型切换到执行角色后按执行职责处理任务。

计划要求所有执行性质入口具有这些边界，不能依赖曾经存在的旧会话记忆。当前方法绕过 executeMaterials，普通执行的修复不能覆盖该路径。

### 5.3 确定修复方案

1. 在 resolveMergeConflict 的 materials.instructions 前接入已经存在的 executionScopeInstructions，然后保留当前冲突专用约束。
2. 保留冲突路径、两方提交、工作目录、禁止 ours/theirs、reset、stash、删除历史和自行提交等现有字段。
3. 不把 reviewScopeInstructions 注入冲突修复，否则会把执行角色错误限制为只读。
4. 不追加 batchExecutionInstructions 的完整通用开发阶段安排；冲突修复沿用当前流程，只补职责边界。
5. 通过本方法实际传入 invoke/adapter 的材料确认接入点，不能仅检查共享常量本身存在。
6. 不改正常冲突回执、合并流程、人工功能影响判断或工作树清理。

### 5.4 完成条件

新冲突修复会话和可恢复会话均收到共享执行规则与冲突专用规则；不会因旧整改里出现证明脚本任务而将其当作当前必须交付项；也不会误用审核只读约束。
