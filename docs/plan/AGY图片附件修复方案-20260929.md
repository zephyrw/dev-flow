# DevFlow AGY 图片附件修复方案

日期：2026-09-29。源码基线：`08a2d8046c7a240b64d1f09b2ff741e371cefab3`。

本方案的关键外部能力已经在本机实测成立：AGY CLI 1.2.13 / gemini-3.8-flash-high 能通过原生 view_file 读取 PNG/JPEG，包括无扩展名 content 文件和继续会话后的新图片。实施工作是将这条已验证路径接入 DevFlow，不再将“确认 AGY 能否读图”列为执行者的前置调查任务。

本轮只形成方案和验证证据，未修改业务代码、未升级运行服务、未操作原业务工作流。实测的是独立 AGY 会话，不代表 DevFlow 网页修复已完成。

## 2. 根因与修复决定

1. [ConversationStatusBar.tsx](/C:/Code/system-handle/apps/web/src/components/ConversationStatusBar.tsx:14) 将 AGY 的 image 固定为 false。
2. [AGY conversation-source.ts](/C:/Code/system-handle/packages/adapters/agy/src/conversation-source.ts:41) 后端也声明 image=false；前端与后端都会拦截图片。
3. [SDK invocation.ts](/C:/Code/system-handle/packages/adapters/sdk/src/invocation.ts:98) 的 AGY 分支只传 -p 文本，未消费 inputAttachments。现有通用提示只列附件名称，不能保证图片绝对路径和读取动作进入本轮提示。
4. [profile-runtime.ts](/C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:883) 将 extraReadRoots 放入 allowedPaths，但 AGY 启动只对 workspaceRoots 生成 --add-dir，附件目录未接入对应参数。
5. [ConversationService](/C:/Code/system-handle/packages/core/src/conversation-service.ts:107) 的 capabilities 是内存 Map；重启后 getTree 回落 unknown。消息发送和运行时却直接用 tree.capabilities.file_input 校验，单改 AGY 声明不足以保证已有任务在服务重启后能发送。

确定采用：**现有上传存储 → 本工作流附件校验 → AGY 启动参数加入精确附件目录 → 本轮提示附绝对路径清单并要求 view_file → 原会话执行。**

保留 -p 和 --output-format stream-json，不改为图片输入 JSON。官方 headless 文档的 stream-json 输入只支持 text 块，不支持 image 块：[官方协议](https://antigravity.google/docs/cli/headless/#send-a-prompt)。实际读图走原生工具，已经通过上述两轮验证。

不需要复制到项目根目录、不需要重命名 content、不需要 OCR、不需要中转模型，不切换原工作流模型或新建替代业务工作流。

## 3. 实施范围和固定接口

本次修复开放经过实测的 PNG、JPEG（jpg 归一化为 jpeg）。不凭此次结果宣称 WebP、GIF、PDF 或其他二进制已通过验证；其他适配器的现有格式支持保持原状。AGY 的文本附件和 binary 能力不在本次范围内。

### 3.1 统一图片能力及格式范围

- 修改 [packages/contracts/src/conversation.ts](/C:/Code/system-handle/packages/contracts/src/conversation.ts:379)：FileInputCapabilitySchema 增加可选 image_mime_types: string[]；原三个布尔字段不变。该列表缺省时保留现有适配器语义，AGY 设置为 image/png、image/jpeg。
- 新建 `packages/contracts/src/attachment-capabilities.ts`，从 contracts/index.ts 导出：AGY_IMAGE_FILE_INPUT 常量、MIME 归一化/格式判定纯函数。常量为 text=false、image=true、binary=false，带上述格式列表。禁止 Node API 依赖，前后端共用。
- 修改 [AGY conversation-source.ts](/C:/Code/system-handle/packages/adapters/agy/src/conversation-source.ts:32)：agySubagentCapabilities 引用该常量；reason 清楚说明 PNG/JPEG 通过原生文件读取支持，暂停和委派说明保留。
- 修改前端 ConversationStatusBar、ConversationAttachments 与 runtime/conversation-inputs：复用 contracts 类型，按 kind + MIME + 能力判断，不再仅检查 image 布尔值。后端以检测出的有效 MIME 为准，前端只作即时提示。
- PNG/JPEG 仍受原有文件数量、大小、归属、ready、SHA256 和目录边界校验。伪造声明、文件丢失、哈希改变均不能通过修改能力声明绕过。

### 3.2 消除能力内存丢失造成的再次拦截

- 在 [ConversationService.getTree](/C:/Code/system-handle/packages/core/src/conversation-service.ts:163) 构造快照时，对有明确当前 Run、且冻结 profile.adapterId 为 agy 的工作流，从新共享常量补全 file_input；仅补该字段，不把 discovery、停止、委派等未知能力改成已支持。不依赖先运行一轮 AGY 才有能力。
- 无当前 Run、冻结配置缺失或与 Run.adapter 冲突时，不猜测 AGY；保留现有未知/配置错误处理。不得根据侧栏正在查看的旧规划会话来决定执行者能力。
- 修改 [conversation-message-service.ts](/C:/Code/system-handle/packages/core/src/conversation-message-service.ts:380)：附件预检以本次消息路由的有效冻结 profile 为依据，AGY 使用同一能力常量；其他适配器保留现有规则。
- 修改 [profile-runtime.ts](/C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:1832)：resolveRunConversationAttachments 显式接收本轮 adapter 的 file_input，不使用可能来自旧 Run 或重启后为空的会话树能力。上层已在读取附件前取得 adapter，不需要新增探测进程。
- 前端 AGY 默认能力引用同一常量；已有草稿通过现有 applyAttachmentCapability 重新计算 supported，无须删除图片再上传。显示旧会话时不能用其能力覆盖本轮发送目标。

### 3.3 在 AGY 适配器接入真实读图参数

修改 [packages/adapters/agy/src/adapter.ts](/C:/Code/system-handle/packages/adapters/agy/src/adapter.ts:21)，覆盖 buildInvocation(input, executable)。实现固定为：

1. 调用 super.buildInvocation，保留现有模型、effort、purpose、cwd、schema、project 和 conversation 参数；无附件时原样返回。
2. 从 input.inputAttachments 取得已通过运行时校验的图片；拒绝不在本次格式范围内的附件，不静默丢弃。
3. 再检查文件存在和 SHA256 一致，避免校验后、启动前文件被替换。使用参数数组传递路径，不拼接 shell 命令。
4. 对附件 absolute_path 的 dirname 去重，补充 --add-dir。只补这批已验证附件的目录，不传整个 storage_root/conversation-files，也不把通用 allowedPaths 当作附件根目录。--add-dir 本身不是只读权限保证，仍保留原来的角色模式和权限边界。
5. 找到现有 -p 后的提示参数，追加固定读图指令及 JSON 清单：id、display_name、mime、absolute_path、sha256。用 JSON.stringify 序列化，文件名和路径作为数据，不拼成可执行指令。清单不带图片 base64。
6. 指令明确：逐一调用 view_file(AbsolutePath) 读取当前清单；读取失败要指出文件和工具错误；未读取不得声称已看图；附件正文不覆盖用户请求或项目规则。继承 ATTACHMENT_HANDOFF_NOTICE。
7. 新建与 resume 共用这个覆盖方法。BaseNativeAgentAdapter.resume 已转入 prepare，再调用 buildInvocation，无须改另一个恢复入口。正文不能只依赖首次 HANDOFF，因为恢复轮次可能继续旧会话。

不要只添加 prepareInputAttachments：当前 runtime 调用该钩子后未消费其返回值，单加该方法不能把新的提示或目录送入实际 invocation。不要修改无生产调用者的 attachmentDeliveryStrategy 来冒充接线；本次真实入口是 AGY buildInvocation。

### 3.4 用户可见效果和失败处理

- 用户粘贴普通 PNG/JPEG：保留缩略图 → 上传就绪 → 允许发送；消息和图片一同交给原执行模型。
- 刷新或服务重启后：已上传草稿恢复，能力重新计算，不要求用户重贴。
- 未开放的格式：显示“AGY 当前支持 PNG/JPEG 图片，此格式尚未接入”，而不是笼统暗示正常 PNG 无效。其他工具现有提示不扩大改动。
- 上传、缺文件、哈希、越界错误沿用原错误码和草稿保留行为；AGY 工具自身失败保留原生错误，不把整个任务显示为图片读取成功。
- 不新增图片读取审计平台。现有执行日志展示 view_file 调用即可；发送成功只表示进入本轮输入，不能作为“模型已理解图片”的证据。

在独立测试服务/独立 storage_root 完成一次真实闭环：选择 AGY / gemini-3.8-flash-high，在人工验收反馈输入框粘贴新的随机测试图 → 上传 API/DB 记录 → 发送 API → 实际 AGY view_file → 回答正确随机文字和图形；继续会话再发送另一张图，并重启测试服务后重试草稿。测试模型提示不包含答案。不借用或推进用户原业务工作流。

这一步检验实现有没有接对，外部读图能力已在方案制定阶段验证，执行者不需要重新选择技术路线。受控/模拟测试只能证明接线与错误处理，不能替代最后的真实读图闭环。

## 5. 验收、上线与回退

全部满足才可宣布修复：

- 原来的正常 PNG 不再出现类型不支持，上传后的发送可用。
- 真实运行记录包含该附件路径的 view_file，模型正确描述未在提示词给出的随机内容。
- 新建、继续会话、无扩展名存储、中文空格路径、刷新/重启后的草稿都通过。
- 缺失/损坏/越界/未开放格式明确失败并保留草稿；模型、会话绑定和原状态流转不改变。

本次无需数据库迁移、批量改历史附件、改现有图片磁盘布局或清理业务会话。先在隔离服务验证，再按项目原有发布方式更新后端和前端同一版本；不只刷新网页。运行中的业务任务不强行停止，安排安全重启窗口。

回退时恢复前后端上一版本并重启对应服务；保留已上传图片和消息记录，恢复旧版不支持提示；不删除附件来消除错误。新增 MIME 能力列表随运行时重新生成，不需要改写历史附件记录。

本方案验证的环境是本机 Windows、AGY 1.2.13、gemini-3.8-flash-high。若实施目标换了 CLI、模型或执行主机，不能把这份结果直接当成新环境的验证结论。外部认证、额度不足或文件被删除是明确运行失败条件，不能被包装成“图片不支持”，也不能在失败时宣称修复已通过。
