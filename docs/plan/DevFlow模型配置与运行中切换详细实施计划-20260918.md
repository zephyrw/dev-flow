# DevFlow 模型配置与运行中切换详细实施计划

日期：2026-09-18。状态：实现前计划；本文件不表示功能已实现，也不授权恢复现有暂停任务。

目标：使执行者按明确合同实现全局默认、任务配置、角色覆盖、临时修复指派、首次模型授权验证以及运行中切换。默认只有规划、执行两套配置。DevFlow 继续只在既有关键节点派发模型，不管理模型内部开发、测试、工具调用和质量判断过程。

配套事实清单：[工具、模型与思考强度核对清单](./DevFlow工具模型与思考强度核对清单-20260918.md)。实现时必须一起阅读；不能把清单中的文档候选模型标为本机已授权。

## 0. 执行合同与边界

### 0.1 必须交付的用户能力

1. 在系统设置中看到、修改全局规划和执行默认配置。
2. 新建任务自动填入全局默认，创建前可以修改工具、模型、思考强度。
3. 任意未结束任务都可以打开“工具与模型”，查看当前轮实际绑定和下一轮配置，修改后续分配。
4. 默认保存不停止当前模型。当前轮结束后创建的新轮使用新配置；用户明确暂停后再继续，也使用新配置。
5. 可以暂停开发、规划、人工前审查、人工后审查、审查整改、人工问题修复；继续时回到对应用途和阶段。
6. 审查、审查修复、人工问题修复可分别覆盖默认角色，不要求普通用户填写五套配置。
7. 人工反馈可指定“本次修复处理者”，支持规划配置、执行配置和任意受支持工具的具体配置。
8. 同一工具不同模型、同模型不同思考强度都属于合法切换；平台不得把思考强度静默忽略。
9. 首次使用某工具的某模型验证实际可调用性；成功后跨任务、角色、重启复用，不因普通切换重复验证。
10. 旧任务首次改配置即可工作，保留原任务、工作区、计划、暂停状态、问题记录和质量轮次。

### 0.2 明确不做

- 不增加开发子步骤、内部计划、模型监督者、额外质量关卡或周期性模型检查。
- 不重建测试证明、宿主调用证明、用例覆盖、交付真实性核验。
- 不改变既有“开发与自测→人工前代码审查/整改→人工功能确认/修复→人工后代码审查/整改→交付”主流程。
- 不因更换模型重做业务计划、重置质量次数、删除历史、改 Git 基线或复制业务仓库。
- 不自动给用户登录，不复制密钥到 DevFlow 数据库，不更改原生工具全局默认模型。
- 不因为一个模型失败而自行换工具、换模型或降低思考强度。
- 不建立项目级、组织级等额外继承层。本期只有系统默认、任务配置和本次修复指定。
- 不把 Auto、Fast、上下文长度、Thinking 开关和 reasoning effort 混成同一个参数。
- 不为本需求引入常驻代理服务；目录读取使用短命 CLI 或已有本地接口，认证检查按需执行。

### 0.3 工作区保护

当前工作区存在大量已暂存、未暂存修改。开始实现先记录 `git status --short` 和当前 diff，仅在本计划涉及文件上增量修改，禁止 reset/checkout 覆盖。参考同日的轻量调度边界计划，若旧 Skill 或旧测试要求重新引入证据门禁，以本计划及当前轻量化边界为准。

开发与测试使用隔离 SQLite 和临时仓库，不操作 `.devflow/devflow.sqlite` 中真实任务。上线迁移与服务重启另行执行；读取计划不等于批准启动真实工作流。

## 2. 统一术语与五个角色

### 2.1 术语

- 工具：用户的原生客户端，例如 Codex、agy、Cursor Agent。不是模型厂商，也不是 MCP 工具。
- 模型：工具接受的精确 ID。不同工具中同名展示模型可能具有不同 ID、能力、账号和路由。
- 思考选择：明确档位、模型固定变体，或原生默认。`high` 只能在对应模型声明支持时选择。
- Profile：一套可复现的工具调用配置，不包含任务要求、提示词或业务状态。
- ExecutionSpec：当前任务模型分配的不可变修订。
- Run：调度平台已经派发的一轮模型工作。保存配置不能修改其绑定。
- 修复批次：一次用户反馈或一份审查整改意见对应的修复工作，可经历续跑和复测，不是新的业务工作流。
- 当前轮：已经创建并绑定配置的 Run；排队且未创建 Run 的任务尚未锁定模型。

### 2.2 固定角色与默认继承

| role ID | 中文名 | 默认来源 | 是否在普通表单显示 |
|---|---|---|---|
| planner | 规划模型 | 任务 plannerProfile | 是 |
| executor | 执行模型 | 任务 executorProfile | 是 |
| reviewer | 代码审查模型 | 跟随 planner | 高级选项 |
| review_fixer | 审查修复模型 | 跟随 executor | 高级选项 |
| functional_fixer | 人工问题修复模型 | 跟随 executor | 高级选项 |

`planner_takeover` 是既有调度用途，默认解析到 planner，不增加第六个用户配置槽。人工前和人工后审查共用 reviewer；不拆成两套默认设置。本期没有独立测试模型，开发和自测由当前执行者连续完成。

### 2.3 路由优先级（唯一算法）

优先级从高到低：

1. 同一逻辑轮的运行故障重试：复用原 Run 的有效绑定。
2. 明确匹配当前修复批次的用户临时指派。
3. 本阶段合法的规划接管标记：使用 planner。
4. 此角色的任务级显式覆盖。
5. 此角色的默认继承：reviewer→planner，两个 fixer→executor。

全局默认只在创建任务时复制为任务配置，不参与运行时的最后一层动态回退。

用户临时指派优先于自动接管，但不删除接管原因或清零次数。界面显示“本次人工指定覆盖自动分配”。仅修改 reviewer 不影响接管者；修改 review_fixer 在已有接管时不暗中撤销接管。想立即换接管者，使用“本次修复处理者”。

### 2.4 用途到角色映射

| Run purpose / 上下文 | routing_role | 说明 |
|---|---|---|
| planning | planner | 首次规划、规划反馈修订 |
| implement，无修复上下文 | executor | 正常开发与自测 |
| implement，dispatch context 的 repair kind=quality | review_fixer | 保留 implement purpose，避免破坏既有计数；靠 routing_role 区分 |
| implement 或 functional_fix，有 functional_fix_intent | functional_fixer | 人工问题修复 |
| quality_review，任一 phase | reviewer | 两道代码质量审查 |
| planner_takeover | planner | 若有本次人工指派则被覆盖 |
| plan_self_check 历史兼容用途 | 当前执行者 | 不因此新增自查 Run |
| merge_conflict | 当前交付/修复执行者 | 复用所关联执行 Run 的配置，避免独立换人 |
| aside | planner | 保持独立只读会话 |
| diagnose | reviewer | 沿用当前诊断定位为审查侧的语义，不新增用户槽 |

functional_fix_intent 只在人工问题修复上下文有效；若同时遗留 quality repair_assignment，按本轮明确的 dispatch context 选用，不能仅检查“数据库里有记录”。所有 intent 必须带阶段、来源和批次 ID。

质量次数保持当前轻量规则：首次审查发现问题不记一次修复失败；一次真实修复 Run 正常交付后复核仍拒绝才加一；两阶段分别计数，第三次符合条件的拒绝触发原有接管。暂停、换模型、访问验证、目录刷新、进程失败不增加次数。一次性指定其他工具修复也仍是同批次修复，不能因模型不同漏记，也不能将同一 review 完成通知记两次。

## 3. 工具与模型目录的实现合同

### 3.1 固定工具清单

顺序固定：Codex、Antigravity CLI、Claude Code、Cursor Agent、Grok Build、Kimi Code、Qoder CLI、OpenCode。内部 ID 沿用现有八种：`codex`、`agy`、`claude-code`、`cursor-agent`、`grok-build`、`kimi-code`、`qoder`、`opencode`。

未安装工具保留在列表中，显示“未检测到”和安装说明；用户可以编辑草稿，但不能把它保存为已验证的活动配置。禁止从展示名猜 executable，也不能把 cursor IDE 可执行文件误认为 agent。

每项返回：ID、中文显示名、实际可执行路径、CLI 版本、探测状态、原生配置来源摘要、目录状态、最近更新时间。禁止返回 API key、Cookie、token、完整认证文件或未脱敏环境。

### 3.2 目录来源与执行参数

| 工具 | 首选目录读取 | 精确模型参数 | effort 传递方式 |
|---|---|---|---|
| Codex | 短命 app-server 的 model/list；本地 models_cache.json 只作缓存降级 | `--model <id>` | `-c model_reasoning_effort="<value>"` |
| agy | `agy models`，只解析 stdout 的模型行 | `--model <slug>` | 优先选择已存在的精确强度 slug；只有已证实支持独立参数的条目才传 `--effort` |
| Claude Code | 原生可用模型接口/受管配置若可读取，否则官方候选目录＋已配置精确模型 | `--model <full-id>` | `--effort <value>`；允许集合按模型、CLI 版本与组织限制求交 |
| Cursor Agent | `agent models`，兼容 `--list-models` | `--model <exact-variant-id>` | 优先原生精确变体 ID；有元数据和版本证据才用括号参数，不发不存在的通用 `--effort` |
| Grok Build | `grok models` | `--model <id>` | `--reasoning-effort <value>`，版本只支持别名时用 `--effort` |
| Kimi Code | 只读解析 `KIMI_CODE_HOME/config.toml` 的 models 元数据 | `--model <alias>` | 本机 0.37.2 的 kimi provider 使用进程级 `KIMI_MODEL_THINKING_EFFORT`；见附录的限制 |
| Qoder | `qodercli --list-models` 或已识别的 qoder 同等命令 | `--model <native-id>` | `--reasoning-effort <value>` |
| OpenCode | `opencode models --verbose`；支持的原生模型元数据 | `--model <provider/model>` | 当前 1.x 使用 `--variant <value>`；v2 仅在版本和帮助匹配时使用 `provider/model#variant` |

不能为了目录刷新启动规划/执行模型。上述命令可以访问客户端自己的缓存或网络，但不携带业务代码。对会加载客户端环境的命令，设置短超时、捕获输出、清理本次创建的进程树，不接管已有客户端后台进程。

### 3.3 模型清单不是永久硬编码

附录列出本次可核实的模型和强度，包括本机 Codex、Cursor、Kimi 的具体结果，以及 agy、Claude、Qoder、Grok 的官方/缓存候选。实现必须做到：

1. 展示当前工具目录返回的全部合法模型，不只展示内置示例。
2. 不同 provider 的同名模型保持不同条目。
3. 目录中没有的 ID 可通过“输入模型 ID”添加为未验证候选；仅允许当前工具的已支持参数方式，不开放任意 CLI 字符串。
4. 自定义 ID 未知时 effort 仅显示“原生默认”；不能猜出 low/high 集合。获得工具元数据后再提供档位。
5. 不把未知档位说成不支持：状态区分 supported、unsupported、unknown。unknown 的明确档位选择不开放，解释“当前客户端未提供该档位信息”。
6. 未登录、离线、目录查询失败、权限受限时，保留上次成功目录并标注缓存时间；没有缓存才显示文档候选。
7. CLI version/help 成功不能把目录条目设为已授权；模型出现在目录也不能把访问验证设为成功。
8. Auto/路由池单列为“原生动态路由”。选择它就明确展示“底层模型由工具决定”；不得标成固定具体模型。
9. 隐藏/内部模型不进入普通列表，例如本机 Codex 的 codex-auto-review 和 gpt-reserve。
10. 模型停用时历史记录仍按原名称展示；不自动替换任务配置。

### 3.4 数据缓存与刷新

- 缓存键：adapterId＋CLI 实际路径/版本＋原生配置作用域指纹＋provider/账号非敏感指纹。
- 新增 `model_catalog` entity，保存规范化目录，不保存原始认证响应。
- 缓存默认 24 小时标为 fresh；过期仅标 stale，不在后台定时刷新。
- 打开模型选择器先立刻返回缓存；首次无缓存或用户点击“刷新列表”才启动 discovery。一次前台会话同一 key 合并请求。
- 手动刷新失败不覆盖最后成功数据，不清空用户已选值。
- 工具扫描默认并发 2；目录查询默认并发 1；本期不启动八个 CLI 常驻进程。
- version/help 超时 10 秒，目录读取超时 30 秒，输出上限 2 MiB。超时终止本次进程树并给出可重试错误，不能把失败当空目录成功。
- 遇到 Windows log/cache/DPAPI/用户目录权限问题，返回 `DISCOVERY_ENVIRONMENT_UNAVAILABLE`，不判定用户账号没有授权。
- 模型目录摘要是页面专用 API，禁止在普通工作流列表刷新中读取全量客户端模型。

### 3.5 思考选择显示与校验

档位标签固定：none=无、minimal=极低、low=低、medium=中、high=高、xhigh=极高、max=最大、ultra=原生 Ultra。未知原生值使用原文。只有条目宣告的值进入下拉，不从全集生成笛卡尔积。

若原生默认可解析，则显示“工具默认（当前 high）”，保存时冻结为 high。若不能解析，显示“工具默认（无法读取具体档位）”，保存 `native-default` 并在 Run 中明确 requested 与 effective unknown，不声称锁定了实际强度。工具相同模型固定变体可将强度显示为只读值；更换强度等价于选择另一个实际存在的变体。

Ultra、ultracode、Fast 等可能附带原生执行行为，不能擅自等价映射为 high/max。本期不增加 Fast、上下文窗口等独立设置；目录中的 Fast/Thinking 变体作为原生完整模型选项保留，不剥离其语义。

## 4. 配置、目录和运行合同

在 `packages/contracts/src` 新增 `model-catalog.ts`、`model-access.ts`、`model-routing.ts`。沿用 `ToolProfileSchema`、`ExecutionSpecSchema`，增量扩展；不得直接替换旧历史对象。

### 4.1 ToolProfile 增量字段

```ts
type ReasoningSelection =
  | { mode: "explicit"; value: string }
  | { mode: "native-default" }
  | { mode: "not-applicable" };

interface ProfileExtension {
  reasoning?: ReasoningSelection;
  nativeConfigProfile?: string; // 原生已存在配置名称，不是凭据文本
  selectionKind?: "fixed" | "native-router" | "native-default";
}
```

保留旧字段 id/revision/adapterId/executableRef/modelSelection/modelId/providerConfigRef/options/toolsetRef。新增配置由服务端生成 profile id/revision，不信任 UI 递增。旧 Profile 缺 reasoning 时按兼容读取，不自动声称 explicit high。

规定：

- 新保存的 fixed Profile 必须有 modelSelection=explicit 和非空 modelId。
- providerConfigRef/toolsetRef 如果适配器尚不能执行，保存时报明确不支持，不能先保存再静默忽略。
- options 仍严格白名单；生产界面不开放 prefixArgs 编辑。兼容测试夹具可继续通过内部构造使用。
- executableRef 新 UI 只允许用户明确选择的路径，后端解析为实际路径且检查产品身份；不能让 MCP 工作模型随意指定另一个可执行程序。
- nativeConfigProfile 只提供已有命名配置选择，不接受 shell 片段。
- profile revision 变化不等于实际运行参数变化。

### 4.2 角色覆盖

```ts
}
```

旧 ExecutionSpec 无 schema_version/roleOverrides 时解析为兼容视图，三个覆盖全 inherit。模式仅为显示信息：所有解析后的角色 adapter 相同才 single_tool，否则 composite；同工具不同模型仍可 single_tool，不代表只有一个配置或共享会话。

### 4.6 实体键、投影视图和版本规则

沿用现有 entities/store，不新增数据库组件。新增实体的 owner：全局默认、工具目录、访问记录、验证作业用 global；任务 spec、repair batch、assignment、停止/保存操作记录用 workflow id。键用固定前缀加 UUID 或规范化 scope 的 SHA-256，不把账号原文、路径或模型里的斜杠直接拼到文件路径。

- `model_defaults/global`：唯一当前默认，CAS 更新；历史概要写现有事件。
- `model_catalog/catalog:<scope-hash>`：最后成功的目录；刷新失败的状态单独保存，不能覆盖成功 entries。
- `model_access/access:<scope-model-hash>`：最后成功访问时间和当前失败状态分别保存。
- `model_verification/verify:<uuid>`：本次短作业状态、访问键、开始/截止/完成时间、脱敏错误；不保存原始 stdout。
- `model_config_operation/op:<uuid>`：保存/切换幂等记录，含 request hash、原版本、目标 Run、步骤、最终 receipt。
- `repair_model_batch/batch:<uuid>`：第 7.4 节定义的批次，不是新工作流或新调度阶段。
- `repair_model_assignment/assignment:<uuid>:r<N>`：不可变配置修订；batch 保存 current_assignment_id。旧项状态通过替换引用和状态事件标为 superseded，不覆盖历史 profile。

旧任务 GET 的 revision=0 仅存在于 `ExecutionSpecView` DTO，不能传入要求 positive revision 的持久化 ExecutionSpecSchema。该 DTO 必须定义 `persisted:false` 与虚拟 spec 字段；首次保存生成真正 ID/r1。已持久化对象 `persisted:true`，所有 Run 只能引用真实 spec ID，legacy 轮继续允许无 spec ID。

所有 hash 先对规范化对象递归排序键，再用 SHA-256。数组顺序只有具备业务意义时保留；effort 的 value 区分大小写，以原生值为准。semantic hash 排除 id/revision、时间、访问状态和标签，包含三个覆盖的 inherit/explicit 模式，即使此刻解析到同一模型，改继承关系仍属于有效配置变化。不能把“explicit 当前恰好等于 planner”当成 inherit 的 no-op。

## 5. 保存与生效：精确事务规则

### 5.1 版本与请求幂等

- task 保存要求 `expected_spec_revision`，旧任务兼容视图 revision=0。
- 工作流状态操作另用 `expected_workflow_version`，不得复用同一字段。
- 系统默认保存要求 `expected_defaults_revision`。
- 请求 ID 用 UUID，不能只用 Date.now。
- 幂等键包括操作类型、实体 ID、request_id；同 ID 同请求返回原结果，不重复调用验证或新增 revision；同 ID 不同内容返回 409。
- 外部 CLI/网络验证放在事务外；开始保存前校验版本，验证完成后事务内再次 CAS。不能在 SQLite 事务内等待模型。
- 变化只影响标签等非语义字段时，不创建新的任务分配 revision；明确 no-op 返回原 revision。有效角色绑定变化才新增。
- 旧字段 `expected_version` 不再自动猜测含义：HTTP/MCP 兼容层给出结构化 `AMBIGUOUS_VERSION_FIELD`，提示新字段；同步升级所有内置调用者和测试。

幂等记录状态固定为 prepared→awaiting_access→ready→committed，切换协调额外有 stopping→stopped；失败分为 retryable 与 rejected。MODEL_ACCESS_REQUIRED/验证进行中只记录 pending，不缓存为最终失败，原 request_id 在验证完成后可继续进入 CAS。提交成功后缓存最终 receipt；相同请求再来即返回它。409 版本冲突是最终 rejected，用户重新加载/修改草稿后必须生成新 request_id。服务重启将孤立 checking 作业标为 temporary_error，不能猜测未收到结果的探测已经成功；原保存操作仍可重试。

### 5.2 默认“保存，下次派发生效”

执行顺序：schema 校验→解析有效配置→复用/完成所需模型访问验证→CAS 写新的不可变 spec→记录配置变更事件→返回解析后的五角色与当前 Run。

绝不改 active Run、workflow.state、plan_revision、plan_hash、review_request_id、反馈状态、质量计数、Git 基线；不执行 stop，不 enqueue 一个新的业务 Run，不自动恢复任务。

已经排队但还没有 Run 的任务，在创建 Run 的短事务里读取最新 spec，因此使用新配置。已绑定的 Run 即使尚在等待子进程启动，也视为当前轮，保持旧绑定。API 返回 must_include：当前 Run 是否不同、pending roles、spec revision。

### 5.3 主界面“立即换用”的操作

基础交互固定为三个动作，避免一个勾选框产生隐式暂停：

1. “保存，下次派发生效”：仅保存。
2. “暂停当前阶段”：调用已有停止能力，带当前 workflow version 和 run id。
3. 停止完成后，“按新配置继续规划/开发/审查/修复”：根据停止前用途恢复。

任务抽屉另提供快捷按钮“暂停后应用”，后端调用同一个协调器，顺序是先验证新配置、再针对捕获的 Run 停止、等旧轮真正退出、最后 CAS 保存；保存完成保持 STOPPED，不自动继续。若模型验证失败，不能先停止当前有效运行。

### 5.4 停止与保存失败场景

| 场景 | 必须行为 |
|---|---|
| 验证失败 | 当前轮继续；草稿保留；不改 spec |
| 停止前 active run 已变化 | 409 ACTIVE_RUN_CHANGED；不能停止接替的新 Run |
| 停止中 | 禁用继续按钮；旧配置与新草稿都保留 |
| 旧进程无法停止 | RUN_STILL_STOPPING；不启动新模型，不宣称切换成功 |
| 已停止，但保存 CAS 冲突 | 保持 STOPPED；显示冲突和最新配置，用户选择重新保存 |
| 已停止，服务崩溃后重启 | 保持暂停，不自动跑模型；可重试原 request_id |
| 保存成功，浏览器丢响应 | 同 request_id 重试只返回原 receipt |
| 保存后当前轮正常完成 | 下一次正常派发用新配置，不抢跑下一阶段 |
| 审查停止后收到旧完成消息 | 按 run_stop/run_id 丢弃迟到结果，不生成新结论或增加计数 |

不要留下没有 expected_run_id 的 spec_switch outbox。旧遗留消息处理为“配置已记录，需用户按当前状态继续”，不得对新 Run 执行 stop。普通配置保存不再投递这种消息。

## 6. 暂停恢复与重试

### 6.1 停止记录

扩展 interruption：`prior_state`、`prior_stage`、`prior_purpose`、`prior_run_id`、`review_phase?`、`repair_batch_id?`、`logical_round_id?`。值来自停止请求确认时的当前 Run/dispatch context，不从 UI 文案推断。

已有 interruption 缺字段时，用被停止的 Run、当前 intent 以及计划状态生成兼容恢复目标。无法唯一判定则返回 `RESUME_TARGET_AMBIGUOUS`，要求用户选择“继续开发”或“继续审查”，不能猜测并启动。

### 6.2 恢复表

| 暂停来源 | 恢复目标 | 使用配置 |
|---|---|---|
| PLANNING | PLANNING/planning | 最新 planner |
| 普通 EXECUTING | QUEUED/implement | 最新 executor |
| 审查整改 EXECUTING | QUEUED/implement，原 repair_batch | 最新 review_fixer 或本次指派/接管 |
| 人工问题修复 EXECUTING | QUEUED/implement，原功能批次 | 最新 functional_fixer 或本次指派 |
| REVIEWING quality_before_human | REVIEW_QUEUED，同 phase | 最新 reviewer |
| REVIEWING review | REVIEW_QUEUED，同 phase | 最新 reviewer，保留已有人工确认语义 |
| QUEUED/REVIEW_QUEUED，尚无 Run | 原用途队列 | 最新角色配置 |
| HUMAN_PENDING 被用户暂停 | 回到原人工等待 | 不因继续按钮自动启动执行模型 |
| 模型访问故障 BLOCKED | 原用途；用户明确点击重试后排队 | 最新配置，除非明确选择“重试原绑定” |

明确“用户继续”与“系统运行故障重试”：前者用最新任务配置；后者为了原会话恢复，使用失败 Run 的冻结绑定。ModelRetry 增加 binding/logical_round 引用，不能在自动重试时重新读最新角色。

配置保存不改变现有业务暂停原因、授权等待和人工确认状态。删除 resumeApproved 中仅因为“模型配置变更”而触发的证据重建或测试重跑；现有业务代码真实变更的处理不在本需求内新增。

### 6.3 会话续用

实际指纹计算：adapterId、实际 executable、nativeConfigProfile、provider/account scope、实际 model ID、effort transport/value、工作区身份和执行权限类别。排除 profile id/revision、显示名称、spec revision、目录刷新时间、验证记录时间。

- 同指纹、同用途族、同工作区、最近执行会话未失效：用准确 conversation ID 续跑。
- 换工具/模型/强度/账号/provider/工作区：新会话，生成现有格式的交接材料。
- A→B→A：新 A 会话，不按 hash 翻出 B 之前的旧 A。
- 每轮代码审查始终独立会话；不能复用开发会话或另一轮审查会话。
- planning 与 execution 的会话隔离；aside 继续独立只读。
- 同 Profile 跨不同工作流不能复用会话。
- 不存在准确会话 ID 或工具不支持 exact resume 时，新建并明确显示“携带材料继续”；不使用 --continue/--last 猜最近会话。

交接只带：需求、批准计划路径/正文、当前工作区、当前用途/阶段、未解决反馈及引用、现有整改意见、上一轮结果摘要。交接沿用当前已有材料生成器，不要求先让额外模型总结，不核验测试证明。

## 7. 本次修复处理者

### 7.1 UI 和作用域

人工功能反馈表单增加折叠项“本次修复由谁处理”，默认“按任务的人工问题修复配置”。选项：按任务配置、使用规划配置、使用执行配置、自定义工具/模型。

规划/执行快捷选项在提交时解析为具体 Profile 快照，显示其实际内容；不能以后因为基础槽修改而悄悄改变这次明确指定。

另有默认关闭的复选框“同时设为该任务后续人工问题修复默认值”。勾选时在同一业务事务中更新任务 roleOverride 与建立反馈/指派，先完成外部验证再事务落库。

代码审查意见和正在修复的卡片增加同样的“更换本次修复处理者”；不要求用户伪造新的问题来换人。正常任务抽屉修改未来默认，不隐式覆盖已有本次指派；抽屉必须显示其优先级，并提供直达入口。

### 7.2 持久化

复用已有 entities，新增 `repair_model_assignment`：

```ts
interface RepairModelAssignment {
  id: string;
  revision: number;
  workflow_id: string;
  batch_id: string;
  kind: "quality" | "functional";
  phase?: "before_human" | "after_human";
  source_review_id?: string;
  issue_ids: string[];
  profile: ToolProfile;
  status: "pending" | "active" | "completed" | "superseded";
  created_at: string;
  created_by: "human";
}
```

质量批次以该阶段本次未解决整改链为单位；功能批次是同次提交/明确选中的 issue 集合。一个工作流同时只派发一个写代码的 Run。不能把两个不同指派的批次合并后只随意选择一方模型。

### 7.3 生命周期

- pending→第一次绑定该批次 Run 后 active；更新与 Run 建立在同一事务中。
- 运行失败、暂停、网络重试不消耗指派，不把 status 改为 completed。
- 质量修复交付后复核仍不通过：同一整改链继续使用本次指派，直到本阶段通过或用户更换。
- 功能修复 ready_for_retest 后人工复测失败：继续原指派；只有本批次所有 issue confirmed 后 completed。
- 修复交付并不能自动确认功能问题。
- 用户中途更换：新增 revision，旧项 superseded，新项在下轮派发生效；当前 Run 保持旧绑定。
- 功能批次之后的最终审查不使用修复指派，继续走 reviewer。
- 任务完成/取消时结束未完成指派，但不删除审计记录。

### 7.4 批次创建、关联和排队算法

新增 `RepairModelBatch`：id、workflow_id、kind、phase?、source_review_id?、issue_ids、status(open/closed)、current_assignment_id?、created_at、closed_at?。即使用户未指定模型，也建立最小批次上下文，以便后续暂停时准确找到“本次修复”。它仅保存引用，不复制完整意见或业务步骤。

质量批次：本阶段第一次 accepted review 结果要求整改且没有 open batch 时创建 UUID；后续同阶段修复→复核不通过全部复用该 UUID，更新 source_review_id 指向最新意见但不换 batch。阶段通过才关闭；另一个 phase 或关闭后的新整改链创建新 UUID。不能用不断变化的 review id 作为 batch id，也不能用只有 phase 的固定 ID覆盖历史。

功能批次：一次人工提交生成一个 UUID，将本次新 issue id 全部关联该 batch。人工选择现存问题换处理者时，它们必须属于同一个 open batch；跨 batch 选择返回 REPAIR_BATCH_MISMATCH，让 UI 分批提交。新反馈不隐式并入正在执行的旧批次。每个 batch 只有一个当前 assignment 引用，按提交时间依次处理，沿用当前人工复测阻塞点，不新增后台并行工作。下一批派发前必须确认前一批已经到达既有允许继续的边界。

“按任务配置”不写冻结 profile 的 assignment；若之前有显式 assignment，提交 clear 会关闭其优先覆盖、保留历史，后续 Run 重新解析角色默认。快捷选规划/执行则在提交事务中复制那一刻的完整 profile。用于快捷选择的 spec revision 必须通过 CAS；不能先验证 A，再在落库时悄悄复制已变成 B 的基础槽。

更新当前批次处理者只影响下一 Run。当前 Run、已提交复核结果、已 ready_for_retest 的修复结果仍指向原 assignment revision。用户想让新处理者立即接手，仍走暂停→保存→人工继续三个动作，不隐式触发第二个写者。

## 8. 首次授权验证与缓存

### 8.1 验证对象

这里的“授权”指工具账号能否调用所选模型，不是项目文件操作授权，也不是人类计划审批。平台不得用已验证模型绕过原生工具权限。

验证键：`adapterId + nativeConfigScope + providerEndpointFingerprint + accountFingerprint + accessModelKey`。

- 能证明只是同一底层模型的 effort 变体时，accessModelKey 合并，改 effort 不再验证授权。
- 配套清单已明确列出的 Cursor 等家族必须建立精确映射，不能因为传给 CLI 的完整变体 ID 改了就重复验证；例如 cursor-grok-4.6-high 与 cursor-grok-4.6-xhigh 共用常规 Grok4.6 访问键。
- 无可靠底层映射时以 exact native ID 为键，不能仅按字符串删掉 -high/-fast 推断。
- Fast/收费套餐/不同模型版本可能对应不同权限，只有原生元数据明确声明共享访问范围才合并。
- 同一个模型经两个不同工具调用，分别验证；不同账号/provider endpoint 也分别验证。
- effort 能力校验单独以 model＋capability revision 为键；这不是账号重新登录。

### 8.2 状态与存储

`model_access` entity 保存：key、status、checked_at、adapter/CLI fingerprint、account/provider scope、accessModelKey、verification_method、nonsecret error code、last_success_at。

status：`unverified`、`checking`、`verified`、`login_required`、`model_forbidden`、`unavailable`、`environment_error`、`temporary_error`。

不设置“每隔一天重新授权”。成功记录持久化到同一 DevFlow 实例，服务重启和新建任务复用。CLI 小版本变化触发参数能力刷新，不自动废弃账号授权。

账号身份优先读取客户端无密钥的 account/status 接口。无法取得账号 ID 时使用该客户端认证配置的不可逆、实例内指纹；不得把原始 token、认证文件内容或可还原秘密写入记录。OAuth token 正常刷新不是账号变化；不能仅凭认证文件 mtime 反复失效。

身份字段增加 `identityConfidence: account|credential|profile-scope`。能读账号 ID 时用实例密钥 HMAC(accountId)；API key 型 provider 若没有账号 ID，可在服务进程中用 HMAC(key) 识别凭据变化，原值不输出、不落库。OAuth 仅能取得刷新 token 而无稳定账号信息时，不能用 token 值作为每次失效键：使用原生配置 profile 的持久 scope id，标 profile-scope。此时界面不宣称已识别具体账号；用户明确切换配置/账号、主动重新验证或运行返回真实认证错误后再失效。不要为解决无法观测的账号变化引入轮询登录状态。

### 8.3 第一次选择的完整流程

1. 用户选择或点击“验证并保存”；此操作允许平台执行一次所选模型连通性检查，不再追加一次确认弹窗。
2. schema/目录/档位/CLI 能力校验。如果参数不支持，在本地直接说明，不调用模型。
3. 查询访问缓存。verified 且当前身份范围未变时直接复用。
4. 当前身份若没有登录，返回该工具官方登录入口，不自动执行 login、不弹浏览器、不登录其他账号。
5. 优先使用工具或提供方明确的模型访问接口；仅有列表/登录状态不够证明可调用。
6. 没有充分访问接口时，通过同一原生工具、同一账号、所选具体模型进行一次最小调用：固定提示“仅回复 OK，不读取文件，不调用工具”。在 DevFlow 控制的空目录内运行，使用该客户端已有的只读/禁用工具能力；禁止带业务目录、计划、MCP 工作流 token、会话 resume 参数。
7. 只使用可实现的只读/工具限制。无法建立受控探测调用时返回环境/能力不支持，不通过“更宽权限”自动尝试。
8. 识别原生成功终态及退出码；字符串输出 OK 不能单独当成功。保存 verified；然后再 CAS 保存配置。
9. verify 接口受理后立即返回 202 和 verification id，不保持 HTTP 连接等待模型；若命中有效缓存则返回 200 verified。服务端作业最长 60 秒，用户可取消。前端仅在该面板打开期间每 1 秒查询本次作业，5 秒后退避到每 2 秒，完成/关闭面板即停止查询；关闭面板不取消其他入口共享的作业。

检查可能消耗极少调用额度，按钮附近一次性说明即可，不增加重复审批。实际选中的多个角色配置相同，应合并成一次验证。

### 8.4 原生工具探测方式

| 工具 | 登录/访问检查 | 禁止事项 |
|---|---|---|
| Codex | account/read 或 `codex login status`；必要时 exec 只读、禁用额外功能并在空目录调用 | 不读出 auth.json 内容，不创建业务任务 |
| agy | 原生模型列表/状态；必要时 `--mode plan --sandbox` 的独立短调用 | 登录信息在当前宿主不可读取时不误报账号已注销 |
| Claude | `claude auth status`；必要时 print＋禁用工具、MCP 的独立调用 | 不利用 fallback 模型成功冒充选定模型通过 |
| Cursor | `agent status`；必要时 `--mode ask --sandbox enabled` 独立调用 | 不传 --force、--approve-mcps 或业务工作区 |
| Grok | 原生配置/模型信息；必要时关闭工具、plan、subagent、web 的短调用 | 不使用 --always-approve；不读取 inspect 原始秘密 |
| Kimi | provider 元数据和原生只读计划调用；具体限制以本机版本能力为准 | 不用假的 --effort，不为检测改用户 config.toml |
| Qoder | 原生状态/list；print 时 tools 为空、严格空 MCP 配置 | 本机不支持 permission-mode plan，不能继续沿用该错误参数 |
| OpenCode | 已配置 provider 元数据；独立只读 agent/禁止工具的短调用 | 不自动 connect 新 provider，不共享已有服务的任务会话 |

每个探测构造函数必须有真实 CLI 帮助快照和独立子进程参数测试。没有可靠账号接口时允许第一次真实模型成功补充 verified，但不能省略首次保存的检查后直接执行业务。

访问状态不确定但本机用户可正常打开原生客户端时，不新建平台登录体系。UI 给出“请在该工具完成登录”及已核实的原生登录命令/入口，登录完成后点击“重新验证”。无 headless 登录命令的工具使用其原生界面，不猜命令。已有 verified 候选普通保存零额外模型调用；手动“重新验证”才忽略该项成功缓存。

### 8.5 缓存失效与失败分类

- 401/明确登录失效：只失效该账号 scope，提示重新在工具中登录。
- 403/明确模型无权限：只失效该模型访问键。
- 模型被提供方移除：该模型 unavailable，要求用户另选，不自动迁移。
- 超时、DNS、网络断开、5xx、额度不足：temporary_error；保留上次成功授权记录，不反复要求登录。
- 本机目录/DPAPI/日志写入权限失败：environment_error；不能标 login_required。
- 组织限制导致 effort 被降低：优先在目录过滤；原生有 applied 信息时显示请求/实际差异，不能声称执行了被限制档位。
- 用户主动“重新验证”只影响选中项；禁止清空所有授权缓存。
- 运行中真正遇到认证错误仍沿用现有故障入口；不存在“曾经验证过，因此永不可能失效”的承诺。

## 9. 适配器和旧运行路径如何改

### 9.1 集中参数构造

新增 `packages/adapters/sdk/src/model-selection.ts`，提供纯函数 `resolveModelSelection(profile, catalogEntry, capability)`，输出 native model token、effort args/env、解析后的默认和选择指纹。`clientInvocation` 和旧 agy/Codex 分支全部调用它，不能再各自读 config.models。

新增 discovery 与 access 扩展接口，不把所有客户端特性塞入 BaseNativeAgentAdapter：

```ts
interface ModelConfigurationAdapter {
  discoverModels(context: DiscoveryContext): Promise<ModelCatalog>;
  readIdentity(context: IdentityContext): Promise<NonSecretIdentity>;
  resolveSelection(profile: ToolProfile, catalog: ModelCatalog): ResolvedSelection;
  prepareAccessProbe(selection: ResolvedSelection, context: ProbeContext): PreparedInvocation;
}
```

实现按工具分文件，公共层只处理超时、输出限制、取消、去重和结果规范化。shell=false；args 用字符串数组；提示词 stdin 或原生单个参数，不能拼 shell 字符串。Windows 用现有 nativeLaunch 解析 npm shim，不能直接 spawn `.ps1`/`.cmd` 并拼参数。

同时处理原生环境的参数优先级：显式选择必须在本次子进程中覆盖会抢先生效的同类模型/effort 环境变量，不修改父进程环境或用户文件。例如 Claude 显式 effort 同步设置本次 CLAUDE_CODE_EFFORT_LEVEL 为同值；Kimi 显式 effort 设置本次 KIMI_MODEL_THINKING_EFFORT。native-default 则按读取的原生选择处理，无法解析时诚实标 unknown。不要删除认证、代理、端点等无关变量；若组织强制设置高于单次参数优先级，返回或展示真实限制，不绕过。

### 9.2 特殊工具要求

- Codex：新模型有 max/ultra 时以原生 model/list 和当前 CLI 能力为准，不受过时文档全集枚举限制；参数必须传入 exec 和 exec resume 两种调用。
- agy：精确 slug 已含强度时默认不再叠加一个冲突的 --effort；中高档切换用目录中实际存在的 slug。未知 slug 不做字符串拼接。
- Claude：使用完整模型 ID，普通字段不得传 opusplan、ultracode 等复合行为作为纯 effort。原生自动路由/策略降级如有发生只能如实展示。
- Cursor：当前 CLI 已列出的变体直接作为 --model；提供一个经过来源验证的 family→effort→exact ID 表用于便捷选择，缺组合就禁用，Fast/Thinking 保持独立变体维度。
- Grok：删除或条件化当前不被帮助支持的 `--no-auto-update`；不是拿 --help 里不存在的参数启动，再把失败误报成模型授权错误。
- Kimi：本机 kimi provider 支持进程级 `KIMI_MODEL_THINKING_EFFORT`，设置前必须校验该 alias.support_efforts；其他 provider 若无受验证的每次调用传参通道，禁用明确 effort 选择，显示能力限制，不能修改全局 config 暂存再恢复。支持这类 provider 的 effort 是将来适配器扩展，不用猜测参数完成本期。
- Qoder：当前版本只读用途使用允许的 permission-mode 配合 Read/Glob/Grep 工具白名单，不传不存在的 plan permission-mode；注意只读授权探测需 tools 为空，不能仅使用提示词约束。
- OpenCode：1.x 与 v2 编码方式互斥，由能力判定选择；v2 不能同时加 #variant 和 --variant。不擅自开启 --auto。

### 9.3 旧任务兼容不能改变业务输入输出

`LocalRuntime.execute/review/diagnose` 不再仅靠 run.execution_spec_id 是否存在决定模型/参数。新增独立的运行协议选择：

1. 旧 native-v2 任务：使用其现有轻量交付与审查协议；指定工具变化时可用 ProfileRuntime，交接仍是同一个正式计划与同一个工作区。
2. 旧 legacy/leaf-v1：继续其现有业务材料和桥协议；把冻结模型选择注入既有启动器。
3. 某旧业务协议确实依赖特定客户端，不能直接支持跨工具时，必须显式提供同任务的“后续 Run 采用原生轻量执行”兼容桥：将已有批准计划原样作为输入、保留原 schema 和历史，复用当前已实现的轻量交付接口；不要重新生成业务计划或绕过人工状态。
4. 本期必须测试本机现有 CRM 类型的 native-v2 旧任务无 execution_spec 时跨工具切换。不能仅测试 CreateWorkflowService 新创建任务。
5. 不支持的老协议组合返回 `LEGACY_RUNTIME_UNSUPPORTED` 并保持暂停，列入明确发布限制；不得宣称全兼容。本机现有任务对应的组合不允许以此作为完成借口。

### 9.4 旧配置只读投影

`readEffectiveSpec(workflowId)`：有保存 spec 用最新；没有时 revision=0，来源 legacy。规划侧先读最近相关 Run 的 profile 和已知旧启动参数，执行侧先读最近执行 Run；缺失才读当前 legacy YAML。外部对话规划身份未知则展示“历史规划由外部对话完成；以下用于平台后续派发”，不能把后续 Codex reviewer 冒充实际历史规划者。

第一次保存以 revision=0 为 CAS 前提写 r1。只新增本任务配置，不扫描写回全部任务，不修改任何历史 Run。

### 10.4 错误编码

至少实现：SPEC_VERSION_CONFLICT、DEFAULTS_VERSION_CONFLICT、ACTIVE_RUN_CHANGED、RUN_STILL_STOPPING、TOOL_NOT_FOUND、TOOL_IDENTITY_MISMATCH、CLI_PARAMETER_UNSUPPORTED、MODEL_NOT_LISTED、MODEL_ACCESS_REQUIRED、MODEL_LOGIN_REQUIRED、MODEL_FORBIDDEN、MODEL_UNAVAILABLE、EFFORT_UNSUPPORTED、EFFORT_METADATA_UNKNOWN、DISCOVERY_ENVIRONMENT_UNAVAILABLE、VERIFICATION_ENVIRONMENT_UNAVAILABLE、MODEL_PROBE_TIMEOUT、IDEMPOTENCY_CONFLICT、RESUME_TARGET_AMBIGUOUS、TASK_TERMINAL、LEGACY_RUNTIME_UNSUPPORTED。

同时实现 AMBIGUOUS_VERSION_FIELD 和 REPAIR_BATCH_MISMATCH。正常读取/命中缓存/保存成功为 200，首次创建实体可用 201，异步 discovery/verify/switch 进行中为 202，权限失败沿用现有 401/403，版本/目标 Run/幂等冲突为 409，选择/能力/访问前置条件不满足为 422。进程环境或网络故障用 503 加准确业务 code；不能用 401 表示用户目录不可写。

错误响应有 code/message/details/retryable。返回字段能让 UI 区分登录、重试、升级 CLI、重新加载版本。不能把全部错误统一显示成“网络失败”。

### 10.5 MCP

- 保留 `devflow_list_tool_profiles`，补充目录、默认和 verified/unverified 摘要；不声称列表等于授权。
- 新增只读 `devflow_get_model_defaults`、`devflow_get_model_configuration`、`devflow_list_models`。
- `devflow_update_execution_spec` 改为严格合同、expected_spec_revision、稳定 request_id；禁止 z.any/用 workflow version 默认填充。
- 修改系统默认或执行验证须沿用显式用户请求范围；工作模型不能自行改变全局设置或切换自己。
- 模型侧返回配置建议时，必要时转为控制台待用户操作卡片，不能用 planner token 冒充 human。
- `devflow_create_task` / 网页 CreateWorkflowService 都使用同一 default resolver，不能客户端各硬编码一套。
- 旧外部规划会话无法被平台原地换模型，MCP 明确返回“后续平台规划/审查配置”；用户若想让平台新模型重新规划，通过现有规划反馈入口触发新 Run。

### 10.6 请求字段补充和响应公约

写路由的 request_id 都必填 UUID。planner_profile/executor_profile/role_overrides 统一使用 HTTP snake_case 容器字段；容器内部 ToolProfile 沿用现有 camelCase，不能同时接受两套别名导致歧义。路由仅转换一次到内部 ExecutionSpec。

- defaults PUT：expected_defaults_revision 非负整数，首次创建为 0；两基础 profile 必填，不接受 role_overrides。
- execution-spec POST：expected_spec_revision 非负整数，两基础 profile 与三覆盖完整提交；缺覆盖不是“保持旧值”，必须显式提交 inherit/explicit，减少表单漏传误清空。
- verify POST：profile 必填，force 可选默认 false；scope 从已确认 executable/nativeConfigProfile 在服务端派生，浏览器不可自行提交账号 hash。
- repair assignment POST：batch_id、expected_assignment_revision（无指派为 0）、expected_spec_revision、selection 必填；selection 严格 union：`{mode:task-default}`、`{mode:planner}`、`{mode:executor}`、`{mode:custom,profile:ToolProfile}`。字符串值落地均使用正常 JSON 引号，此处为类型简写。
- functional-issues POST：原字段保留；repair_model 为上述 selection，可省略，省略等于 task-default；remember_for_task 默认 false。若选择 planner/executor、勾选 remember 或建立覆盖，expected_spec_revision 必填；一次事务内创建 issue、batch、assignment 及可选 spec，失败全部回滚。
- model-switch POST：完整 spec 保存字段加 expected_workflow_version、expected_run_id；expected_run_id 可以为 null 表示“预期当前无 Run”，不能将缺字段解释成允许停止任何 Run。
- discovery POST：adapter_ids 从八工具枚举中选，去重；scope/路径只选本机已发现或用户明确保存的工具配置。不能传 arbitrary command。

mutation receipt 固定含 operation_id、request_id、status、entity_revision、changed、effective_from、current_run_id、pending_roles。effective_from 值只用 new-workflows、next-run、stopped-awaiting-resume；不能返回一个无法实现的“立即换掉当前进程”。错误含 code/message/retryable/details 和 request_id，details 只能含非敏感可操作信息。

异步 discovery 和快捷 switch 也使用已有短作业执行器/本进程 Promise 注册表，持久 operation 记录负责重启恢复，不新增常驻队列服务。补充 `GET /api/model-operations/:id` 返回统一 operation 状态，用于查询 discovery/switch；verify 保留专用查询路径。停止/保存最多等待到现有停止超时，超时返回可恢复状态，绝不自动创建第二 Run。

## 12. 调度伪代码与并发边界

```ts
async function dispatchAtExistingBoundary(workflowId: string, context: DispatchContext) {
  // 外部准备不在事务中，已有并发槽位/工作区租约仍有效。
  const draft = resolveRoutingPreview(store, workflowId, context);
  const prepared = await resolveInvocationFromCachedCapabilities(draft);
  assertCachedAccessOrLegacyContinuity(prepared, context);
  return store.transaction(() => {
    assertSameWorkflowIntent(workflowId, context);
    assertNoStoppingOrTerminal(workflowId);
    const current = resolveRoutingPreview(store, workflowId, context);
    if (current.semanticHash !== draft.semanticHash) throw retryBeforeRunCreated();
    const run = createRunWithFrozenBinding(current, prepared);
    bindAssignmentIfAny(run);
    return run;
  });
}
```

正常 dispatch 仅查询已验证缓存，不在每轮做模型探测。首次 legacy 未修改配置的连续执行可保留原可调用链路，并在真实成功后记录验证；用户首次指定新的工具/模型必须经过访问验证。

`resolveRoutingPreview` 是纯数据读取/计算，不启动模型。若保存新配置与准备 Run 竞争：Run 尚未建立时重新解析最新配置；Run 已写入后不可变。资源租约只在真实 Run 派发路径建立，不因打开选择器或访问验证占用业务 executor/reviewer 配额。

对共享工作区继续使用现有唯一写者约束；不因为两个 repair assignment 不同就开启两个并行写者。

## 14. 开发顺序与每步输出

### P01：建立回归基线

读取本计划、模型清单、当前 git diff 和相邻 Skill。记录相关源码/测试当前状态，定位本机旧任务对应 schema 与 runtimeFlavor，不启动真实任务。产出改动清单及基线失败清单。

### P02：先实现合同和纯路由

先加类型/兼容解析/模型选择纯函数，后改 run-profile。用表驱动覆盖五角色和全部优先级。此步不改 UI，不触发任何 CLI 探测。输出可独立测试的 resolver。

### P03：修正配置 CRUD 和 legacy

实现默认服务、旧任务 r0、GET execution-spec、分离版本、幂等。移除普通保存的 stop/outbox 行为。用 API 集成测试证明旧 workflow.version=67、spec=0/2 的保存正确。

### P04：实现目录发现与八工具参数映射

每工具分别加入版本/帮助/模型输出夹具及 parser。先完成 Codex、agy、Cursor，再完成 Claude、Grok、Kimi、Qoder、OpenCode。不得给未支持字段返回伪成功。

### P05：实现首次访问验证

完成 nonsecret scope、cache、singleflight、cancel、错误分类和模型短探测构造。离线测试使用真实子进程替身，不运行外部大模型。验证普通 dispatch 不增加探测调用。

### P06：绑定 Run 与恢复

接入所有实际启动分支，包括旧 agy/Codex。实现 requested/observed 分离、session lineage、人工恢复/自动重试区别、停止目标身份。此步最重要的回归是开发暂停和两种审查暂停。

### P07：修复指派

接入功能反馈事务、质量整改、复测失败和完成清理。证明修改基础配置不会悄悄覆盖临时指派，且用户能明确更换本次处理者。

### P08：完成全部界面入口

先共享编辑器和全局默认，再新建和任务抽屉，再反馈/运行卡片。处理 async race、版本冲突和草稿保留。不能只做后台 API 就提交“已支持”。

### P09：安装、MCP、Skill 和文档同步

安装两条路径同一服务；MCP 严格字段；重新导出 schema；更新 guide 和 Skill。仅修改仓库源 Skill，安装到用户目录属于实际安装阶段，不因测试覆盖现有用户 Skill。

### P10：统一验证与交付

每层开发时运行受影响测试；最终统一 typecheck、目标集成/E2E、构建，并在独立环境做真实已授权模型的有限烟测。缺账号的工具报告未完成真实调用验证，不编造八工具全部 live 通过。实现审查与用户实际验收分别记录。

真实调用烟测只对用户已授权并选用的模型组合开展，在隔离小仓库验证：创建规划、暂停开发换 effort、暂停审查换工具、人工问题临时指派。每个组合报告“目录发现/参数测试/访问验证/真实业务烟测”四个独立状态。八适配器参数测试通过不等于八个账号都真实可用。

## 17. 发布、回滚与现场保护

1. 开发完成先生成可审查 diff 和目标测试报告，禁止直接重启当前服务来“顺便验证”。
2. 上线时在现有用户控制下停止控制器写入，使用 SQLite 一致备份方式保留数据库及相关状态；不要热复制单独 sqlite 丢 WAL。
3. 应用和用户 Skill 分发按现有安装器进行，不手改凭据和原生工具模型默认。
4. 启动后只读检查默认导入、旧任务 r0 视图、原暂停状态；不自动恢复两个 CRM 任务。
5. 先在新建隔离任务上验证配置保存与切换，再由用户决定真实任务何时继续。
6. 回滚应用时保留新 entity 历史；旧程序不认识新合同可能无法正确启动新配置任务，因此回滚前保持任务暂停，不能让旧程序静默忽略新 override/effort。
7. 不删除历史 Run/spec/assignment；恢复备份必须保持同一批次状态，禁止合并不同时间的 sqlite/WAL。

## 18. 执行者不可自行改变的决策

- 默认两个配置槽，三个高级可选覆盖；不增加新的常驻调度角色。
- 系统默认只影响新任务；任务配置在下次正常派发或用户暂停续跑时生效。
- 当前 Run 不原地换模型；自动运行故障重试复用原绑定。
- 本次修复指派跨续跑/复测保留，并优先于自动分配；审查仍独立。
- 模型/effort 精确映射依据实际工具能力，拒绝假参数和无依据档位。
- 目录成功、登录成功、模型访问成功、业务验证成功四者分开。
- 不重新增加测试证据验证、业务验收裁决或模型过程检查。
- 用户明确要求的工具/模型无法使用时给出事实，不自动替换为“更合适”的模型。
- 本文件中的模型清单是 2026-09-18 快照；动态目录变动按已写明的算法处理，不让执行者自行发明新产品策略。
