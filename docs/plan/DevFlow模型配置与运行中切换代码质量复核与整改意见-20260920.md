## 3. 阻断主要使用链路的问题

### R01 — [P1] 工具发现和目录刷新没有执行实际工作

定位：[model-catalog-service.ts:599](C:/Code/system-handle/packages/core/src/model-catalog-service.ts:599)、[model-catalog-service.ts:630](C:/Code/system-handle/packages/core/src/model-catalog-service.ts:630)。

`discoverTools()` 和 `refreshModels()` 只写入状态为 `ready` 的 `model_config_operation` 并返回。生产调用链没有启动实际扫描、目录读取，也没有消费这类操作的执行者。已有真实发现方法被独立 smoke 脚本调用，不能使页面接口自动工作。

触发及影响：新安装后用户点击“发现工具”或“刷新模型”，操作记录生成，但工具和目录不出现。访问验证又要求模型已存在于目录，因此新环境无法完成默认模型设置。已有缓存也不能通过此入口更新。

确定修复：

1. 两个入口登记操作后，调用已有工具扫描和相应适配器目录发现方法；使用进程内受限并发短任务即可，不增加独立调度平台。
2. 将操作状态与实际结果连接：处理中、成功或失败，记录无敏感信息的失败原因和完成时间；接口返回的操作 ID 必须可用于查询真实状态。
3. 相同请求重复提交复用结果；进程中断后的未完成记录允许恢复或明确失败，不永久显示可处理但无人处理。
4. 目录成功更新后页面重新读取目录；刷新失败保留旧目录及其来源、时间和过期提示。

回归场景：空存储点击发现；有旧缓存点击刷新；发现失败后重试；同请求重复提交。对应原计划目录发现、安装后设置及 P04/P05。

### R02 — [P1] 验证使用目录能力，正式调用却丢掉了这些能力

定位：[invocation.ts:46](C:/Code/system-handle/packages/adapters/sdk/src/invocation.ts:46)、[model-selection.ts:343](C:/Code/system-handle/packages/adapters/sdk/src/model-selection.ts:343)、[profile-runtime.ts:525](C:/Code/system-handle/packages/runtime/src/profile-runtime.ts:525)。

正式调用的 `pushFrozenSelection()` 实际执行 `resolveModelSelection(profile, undefined, ...)`，没有传入目录 entry。agy/Cursor 的显式强度依赖 entry 中的 variants/fixedValue，故保存和验证成功后，正式派发仍会抛出 `EFFORT_UNSUPPORTED`。例如目录中的 agy Gemini high、Cursor Grok high 选择都经过此路径。

同一根因还表现为：

- [invocation.ts:29](C:/Code/system-handle/packages/adapters/sdk/src/invocation.ts:29) 用 Kimi alias 的斜杠前缀猜 provider。配置别名 `work/k3` 即使实际指向 managed provider，也会被猜成 provider `work`，与目录验证结果不同。
- [invocation.ts:25](C:/Code/system-handle/packages/adapters/sdk/src/invocation.ts:25) 固定 OpenCode 使用 flag 编码，没有把实际版本能力传入正式调用，原有针对另一种 variant 编码的分支无法按版本生效。

确定修复：

1. 在创建 Run 的边界，依据选定 profile、对应 scope 的目录 entry 和实际 CLI 能力完成一次解析。
2. 把无敏感信息的实际模型 token、强度参数和环境变量、provider 解析结果、版本相关编码方式保存到该 Run 的不可变调用配置。
3. 正式启动、继续会话和同轮自动重试消费这份配置，不重新猜测 provider，不重新读取可变目录来改变当前 Run。
4. 对历史 Run 没有此字段的情况，用其历史绑定与当前可确认能力做明确兼容；不能删除 reasoning 或降级 native-default 来绕过错误。
5. 访问验证与正式运行共用同一个模型选择解析器，但各自保留探针和业务运行的权限、提示词及输出处理。

回归场景：同一 profile 通过验证后，检查真实适配器 `prepare/resume` 的模型及强度参数；分别覆盖 agy、Cursor、Kimi 自定义 alias、OpenCode 两种版本能力。不能只测试孤立的 resolver。

### R03 — [P1] 旧 agy 通道实际使用旧配置，界面显示的新模型不生效

定位：[run-profile.ts:626](C:/Code/system-handle/packages/core/src/run-profile.ts:626)、[runtime.ts:644](C:/Code/system-handle/packages/runtime/src/runtime.ts:644)。

旧 native-v2 来源且工具为 agy 的 Run 被分配到 `legacy-agy-native`。该执行分支继续使用 `config.models.agy_executable/executor` 和旧 workflow conversation，没有采用新 Run 中选定的模型、强度和会话归属。旧 managed 执行分支也需要一并处理同类遗漏。

触发及影响：旧任务暂停后把 agy 的执行模型或强度改为 B，Run/界面记录 B，实际调用仍取 YAML 中的 A；切换后的会话身份也可能与记录不一致。

确定修复：保留原业务协议、工作包和事件格式，将旧 launcher 的工具路径、模型、强度及可继续会话作为显式参数，从冻结的 Run 调用配置注入；禁止旧 launcher 再自行读取全局模型默认值。会话复用遵守工具、模型、强度与 purpose 的兼容规则。

回归场景：旧任务同工具换模型、仅换强度和未做模型修改正常继续；检查传给实际 launcher 的参数，不只检查 Run JSON。对应原计划 B09、9.1/9.3、IT-R08/R09/R22。

### R04 — [P1] 旧任务已有的 Codex 审查被统一兼容判断拒绝

定位：[run-profile.ts:629](C:/Code/system-handle/packages/core/src/run-profile.ts:629)。

旧协议分支对所有非 agy 工具统一抛 `LEGACY_RUNTIME_UNSUPPORTED`，没有区分执行与审查 purpose。原有 leaf-v1 任务本来就可由 agy 执行、Codex 做代码审查，因此无需用户做任何模型切换，下一轮审查也可能因新判断失败。

确定修复：把兼容规则定义到“任务原协议 × Run purpose × 工具”的粒度，保留原有 Codex 审查路径。只拒绝确实没有实现的执行协议组合，并保持任务当前状态；不要通过放开全部旧协议组合或把审查改成执行来规避。

回归场景：已有 leaf-v1 任务不修改配置，走到 Codex 审查；审查暂停并继续；确实不支持的旧协议执行切换仍返回明确错误。对应原计划 9.3、IT-R22/IT-S08。

### R05 — [P1] 恢复操作先销毁原阶段所需的状态

定位：[recovery.ts:300](C:/Code/system-handle/packages/runtime/src/recovery.ts:300)、[engine.ts:811](C:/Code/system-handle/packages/core/src/engine.ts:811)、[engine.ts:854](C:/Code/system-handle/packages/core/src/engine.ts:854)。

人工 `resumeApproved()` 在判断恢复目标前调用 `engine.invalidate()`，清除 snapshot、人工确认并作废交付版本等状态；之后才恢复到原审查或人工确认阶段。

触发及影响：审查中暂停换模型再继续，新审查缺少原交付上下文；人工确认后的审查暂停再继续，会失去人工确认；功能问题复测可能遇到交付版本已失效。单纯换调度模型因此改变了业务流程结果。

确定修复：

1. 先读取持久化的暂停前阶段、purpose 和批次，确定恢复目标。
2. 单纯暂停、修改未来模型、在原阶段继续时，不作废快照、交付版本、审查输入或人工确认。
3. 只有原有业务规则认定代码或计划发生了需要失效的变化时才执行原失效逻辑。模型配置 revision 的变化本身不是代码变化。
4. 恢复到原阶段，并让下一次真正派发绑定应使用的配置；不得靠额外跑开发、自检或重新人工确认补齐被误删的状态。

回归场景：开发、审查、人工确认后审查、功能问题修复分别暂停并继续，对比暂停前后的业务状态与原始材料。对应原计划 6.2、IT-R13/R14/R16。

### R06 — [P1] 规划阶段不能按设计暂停后继续

定位：[recovery.ts:275](C:/Code/system-handle/packages/runtime/src/recovery.ts:275)、[recovery.ts:290](C:/Code/system-handle/packages/runtime/src/recovery.ts:290)。

恢复入口在分辨原阶段前，先执行读取计划的项目配置校验，并强制要求当前 plan_hash 已被批准。首次规划尚没有正式计划及批准，用户要求修改计划时的新版本也未批准，因而规划暂停后的恢复会被前置条件拒绝。

确定修复：先确定恢复 purpose。规划只检查其实际需要的项目和工作区上下文；进入开发的阶段仍保留原计划批准条件。不要给未批准计划生成假批准，也不要为通过此入口修改工作流状态。

回归场景：首次规划中暂停换规划模型继续；计划反馈后的重新规划中暂停继续；未批准计划仍不能进入开发。对应原计划 6.2、IT-R15。

### R07 — [P1] 首次验证没有覆盖所有能发布模型配置的入口

定位：[model-routes.ts:306](C:/Code/system-handle/apps/api/src/model-routes.ts:306)、[server.ts:466](C:/Code/system-handle/apps/api/src/server.ts:466)、[repair-model-service.ts:381](C:/Code/system-handle/packages/core/src/repair-model-service.ts:381)、[main.ts:324](C:/Code/system-handle/packages/installer/src/main.ts:324)、[create-workflow.ts:168](C:/Code/system-handle/packages/core/src/create-workflow.ts:168)。

普通任务配置和全局设置路由调用了访问校验，但其他路径没有同一保证：

- 修复指派接口直接 `repairs.assign()`；功能问题创建时附带的 customProfile 同样没有经过共享访问校验。
- 将功能修复模型记为任务默认的路径使用 `accessVerified: true`，没有以访问服务的真实结果为依据。
- 安装参数路径先 `service.save()` 覆盖系统默认值，之后才计算 pending。未验证或不可用的新配置已经发布，旧默认值无法靠 pending 提示保留。
- 创建任务遇到 `usedOnlySavedIds` 就跳过验证。引用了已保存的 profile 不等于该模型已验证，更不等于当前账号下已验证。

确定修复：

1. 在发布配置的服务边界统一检查实际解析出的 profile 及其访问记录，供 HTTP、MCP 创建、修复指派、记为默认和安装入口使用。
2. 验证探针在数据库写事务外完成；最终发布时重新核对配置版本和验证对应的身份、模型，不接受调用方自行声明 `accessVerified: true`。
3. 安装中未完成验证的新选择保持待配置草稿，旧生效默认值不变；首次安装允许显示待完成状态，但不把未验证草稿伪装成可派发默认值。
4. 对原有任务连续运行的兼容必须限定到已有相同绑定，不能把所有 saved ID 或所有 legacy 分支都视为已授权。
5. 更换同一模型的思考强度应按规范共享访问记录，不能把统一校验做成每次操作都发起真实探针。

回归场景：对相同未验证 profile，逐一从上述入口提交，均不能发布为生效配置；验证一次后再次保存、修复指派及仅换强度不重复探测。原计划首次授权、安装和角色覆盖要求适用。

### R08 — [P1] 原生 profile 未应用，缓存身份也只用了默认 scope

定位：[model-access-service.ts:665](C:/Code/system-handle/packages/core/src/model-access-service.ts:665)、[model-access-service.ts:708](C:/Code/system-handle/packages/core/src/model-access-service.ts:708)、[model-access-service.ts:740](C:/Code/system-handle/packages/core/src/model-access-service.ts:740)、[invocation.ts:46](C:/Code/system-handle/packages/adapters/sdk/src/invocation.ts:46)。

`readIdentity` 目前只有接口约定，没有接入生产实现。HTTP 访问验证的 identity 来自 `identityFromProfile()`，其中只有 nativeConfigScope，账号与 endpoint 落到默认值。生产构造访问服务也未接入 scope 对应的 catalog，fallback 直接在同工具的全部目录中按 nativeId 寻找。

同时，`nativeConfigProfile` 被用于配置、显示及哈希，但没有对应应用到实际发现、探针和模型调用的原生 profile 参数或环境。因此选了原生配置 X，也可能仍然读取、验证和运行默认配置。

触发及影响：在同一工具下切换原生账号、endpoint 或 profile 后，缓存可能误认为已验证；选定配置与实际调用的账号/provider 不一致。同工具同 ID 的其他 scope 目录也会被误用。

确定修复：

1. 每个适配器实现并接入同一份“原生配置解析结果”：实际工具路径、受支持的 profile 选择方式、provider endpoint、可获取的稳定账号身份及其可信度。
2. 目录、探针、正式运行使用同一原生配置选择方式；不支持原生 profile 的工具必须在保存前明确拒绝该字段，不能接受后忽略。
3. 访问缓存采用对应身份的不可逆指纹；稳定账号 ID 可用时不使用短期 OAuth token 作身份，防止正常 token 刷新引起重复验证。取不到账号时按原计划标明 scope 级可信度和失效规则。
4. 目录读取必须匹配工具、路径、配置 scope 和身份，不允许遍历任意目录取同名模型。
5. 原生工具切换账号或 endpoint 后使用新身份重新查缓存；同账号同模型仅改强度继续复用。禁止输出或持久化明文凭据到日志和页面。

确定修复：验证 helper 接收明确 force 参数，普通首次选择及保存为 false，人工“重新验证”为 true；前端同请求合并不能把强制请求合并进普通缓存读取。后端保留同一真实探针的合理并发去重，结果更新所有订阅者。

回归场景：verified 后点击重新验证确实启动一次探针；普通再次保存不启动；与其他页面普通验证并发时语义不被覆盖。对应原计划 8.4/8.5。

### R25 — [P2] 安装部分覆盖破坏未指定字段

定位：[main.ts:210](C:/Code/system-handle/packages/installer/src/main.ts:210)。

只要某角色提供任一安装参数，overlayRoleProfile 就重新解析 effort。例如原先为 Codex GPT-6 xhigh，升级时只重复指定 `--planner-tool codex`，未指定强度也会被重置为目录默认或 native-default。改工具但不提供模型时，还会留下旧工具的 modelId、providerConfigRef 等字段。

确定修复：

1. 同工具、同模型时只覆盖用户明确提供的字段，未指定 effort 保持原值。
2. 工具改变时清除旧工具专属字段；必须解析成该工具合法的模型选择后才允许发布，缺少必需输入进入待配置状态，不拼出跨工具混合 profile。
3. 模型改变且旧强度不再合法时，按原计划明确处理并展示结果，不静默保留不支持值或降级。
4. 完整合并、目录能力及访问验证全部通过后，才原子更新默认值；与 R07 的待配置草稿规则共用同一路径。

回归场景：无参数升级、只重复指定原工具、只改模型、只改强度、改工具未给模型、完整指定工具模型强度。对应原计划 11.7。
