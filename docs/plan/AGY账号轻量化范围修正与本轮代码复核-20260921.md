## 1. 用户最新范围覆盖旧设计

用户本轮明确要求轻量化，以下决定优先于前两轮整改文档及原计划中冲突的条目。前面的方案把模型池和会话恢复复杂化，造成了不必要的门禁；这部分设计应收回，不再要求执行 Agent 继续补齐。

- **额度只有账号级两个窗口：五小时和周额度。** 本地按周余额排序，排除窗口未重置的耗尽账号；只对将使用的账号串行核验。取消按模型拆池、模型到额度池映射及其注册认证要求。模型仍使用用户原来的选择，但模型配置不决定账号全局额度能否读取。
- **继续本地任务和本地会话。** 保留原目录、模型参数及已记录的 CLI 会话 ID，通过现有 CLI 续接入口继续。不要求云会话迁移、官方跨账号迁移接口或另建迁移系统。实际 CLI 续接失败时报告真实错误，不伪造成功或用内部 Run ID 充当会话 ID。
- **独立模式仍保留。** 零工作流可以逐个登录、保存授权、补测额度、一键自动选或手动指定账号；工作流在可信额度错误后自动切换。手动失败不留下未来自动执行。
- **保留必要的正确性。** 旧账号进程停止后才换凭据、未测额度不当满额、用户停止后不复活任务、同一次恢复不重复启动。这些直接决定核心功能能否工作，不需要新的业务阶段或复杂框架。
- **复用现有调度。** 不再并行维护一个绕过 Engine 正常流程的 `account_recovery` 执行器，也不因多模型批次、跨目录搬迁等非必要模块没有完成而阻塞本次轻量功能。

本文是范围修正和代码审查意见，不是新一套平台规划。后续修复直接按以下实际缺陷局部修改；不要另建实施计划重新扩展范围。旧文档中不冲突的用户需求继续有效。

## 2. 确认的问题与最小修法

### Q01 · P1 · 全局额度及录入仍被无用门禁阻断

位置：[空注册表](../../packages/adapters/agy/src/account-capability-registry.ts:42)、[生产装配](../../apps/api/src/account-service-bootstrap.ts:70)、[探测条件](../../packages/adapters/agy/src/account-probe.ts:211)、[模型池解析](../../packages/agy-accounts/src/service.ts:242)、[业务许可](../../packages/agy-accounts/src/service.ts:793)。

`certifiedRegistry` 为空且产品没有注册调用，配置正确 CLI 也永远不装配 adapter/loginLauncher。另一个独立问题是 parser 返回账号级 windows 和空 pools，probe/enrollment/service 却要求非空 pools 和 model_ids；读到全局五小时和周额度也不能完成录入或切换。这是旧设计造成的功能阻断，应按用户最新范围移除。

最小修改：生产直接装配实际支持的登录、身份和全局额度读取实现，按真实结果校验和报错；不能为了移除门禁把 fixture 当真实数据。探测、录入、存储、排序、等待和许可统一读取每账号两个 windows。为兼容现有存储可使用一个固定内部全局键，禁止再要求模型映射。CLI 无法返回某个字段时显示该字段未知，不增加“官方认证注册表”前提。

同时修正当前许可误用：selector 已区分 `eligible_for_candidate` 与 `eligible_for_permit`，service 却直接按候选排名发业务许可。旧快照为零、reset 到点只代表可以核验，不代表额度已经实测恢复；先串行刷新当前账号，再决定启动或等候。

### Q02 · P1 · 辅助进程协议不完整，登录不能真正交互

位置：[probe spec](../../packages/process/src/agy-account-job-runner.ts:184)、[login spec](../../packages/process/src/agy-account-job-runner.ts:323)、[C# Host](../../host/DevFlow.WinHost/Program.cs:17)、[Go 隐藏窗口](../../host/devflow-host/process_windows.go:234)、[登录结果处理](../../packages/process/src/agy-account-job-runner.ts:379)。

两个 spec 都缺 `env`，C# Host 用 `GetProperty("env")` 读取，选中 C# 时会在 CLI 启动前直接抛错。登录只让 Host `windowsHide:false`，实际 CLI 在 Go 中仍 HideWindow，在 C# 中仍 CREATE_NO_WINDOW 且 stdin 被关闭；需要终端输入时不能完成登录。runner 又把 Host close 的退出码当 CLI 退出码，没有消费结构化 CLI exit 消息；CLI 非零、Host 正常退出为零时会被判登录成功，未消费的输出还可能堵塞管道。

最小修改：复用完整 ProcessSpec，提供受控 env；在用户选中的现有 C#/Go Host 增加真正的交互登录模式，使 CLI 有可见控制台与可输入 stdin，控制 IPC 独立。持续消费 Host 输出，以结构化 CLI exit 和停止结果结束操作；Host 管道中断或缺少终态不能按成功处理。不新建第三种宿主。

### Q03 · P1 · 探测未确认停止，也能继续账号事务

位置：[cleanupAndFinish](../../packages/process/src/agy-account-job-runner.ts:199)。

`await verifyJobStopped()` 的 boolean 被丢弃，随后无条件 resolve。超时、取消、查询失败或后代仍存活时，上层仍可继续切换/回滚凭据，使旧身份进程与新身份重叠。

最小修改：把真实停止结果传回调用方；只有确认整个 owned Job 停止才能完成辅助操作。未确认时保留操作占位和身份屏障并显示具体错误，禁止继续写活动凭据。无需增加新的业务流程，只要不把失败当成功。

### Q04 · P1 · 本地恢复绕开正常调度，并同时启动两条路径

位置：[Bridge 新入队](../../packages/runtime/src/agy-workflow-bridge.ts:658)、[Bridge 旧恢复](../../packages/runtime/src/agy-workflow-bridge.ts:682)、[Engine 新执行分支](../../packages/core/src/engine.ts:2216)、[复制旧账号目标](../../packages/runtime/src/agy-workflow-recovery.ts:215)。

同一次切号先入队 `account_recovery`，之后又 stage retry / resumeApproved 进入普通队列。新执行分支不更新 workflow.run_id/state、不经过正常容量与工作区锁，也不登记正常 running；普通调度随后还能再建一个 Run。固定目标直接复制旧账号 frozen/model binding，拿到新账号许可后会报 `AGY_ACCOUNT_BINDING_STALE`；即使绕过这个检查，结果也可能因 workflow.run_id 不匹配报 `RUN_REVOKED`。该分支还把 planning/review 一律送给 runtime.execute，角色入口和结果结算都错。

确定改法：删除新增的独立 `account_recovery` 直接执行分支及 Bridge 对它的入队，保留现有 `stageAccountModelRunRetry → restoreFailedRole/resumeApproved → Engine.dispatch` 一条路径。实际 Run ID 由该调度路径分配并绑定本次恢复；重复回调已绑定时复用/观察原 Run，不再次入队。沿原 bindProfile 只更新确认后的账号身份，保留原模型、参数、角色及本地会话关联；planning/review/execute/aside 使用已有相应入口和结算逻辑。现有调度创建 Run 时绑定该次本地会话续接信息，不能仍按旧 source key 写、新 target key 读。不要为解决本问题再增加一个调度框架。

### Q05 · P1 · 长等待会超时、丢唤醒或丢失原任务

位置：[到期需求消费](../../packages/agy-accounts/src/service.ts:1319)、[旧 deadline](../../packages/agy-accounts/src/service.ts:1392)、[初始无候选](../../packages/agy-accounts/src/service.ts:1450)、[创建等待](../../packages/agy-accounts/src/service.ts:1546)、[回滚覆盖错误](../../packages/agy-accounts/src/service.ts:2062)、[任务预算](../../packages/runtime/src/agy-workflow-recovery.ts:53)。

存在以下实际断点：初始无候选保留约 300 秒切号 deadline，等几小时后先超时；新 demand 唤醒先清 wake 并标 selected，再创建操作，失败直接吞掉，默认未配置 standalone model 时还因漏传 model_id 而失败。即使新操作创建成功，也未带原 consumer/source 引用，Bridge 按旧 operation ID 找等待记录，切号成功后找不到原任务。A 已耗尽而 B 网络失败时，rollback 又把原 network_wait/no_eligible_account 改掉，后续不再进入自动等待。

此外，coordinator 用账号提交时刻 `now-started_at` 计算执行耗时，把等待额度/认证时间扣掉：原来还剩 20 分钟，等待 30 分钟后就被判超时。

最小修改：保留一份稳定关联原任务/消费者的持久等待；长期等待不使用单次切号超时。创建新尝试和消费等待必须原子完成，失败保留可再次处理状态，继续携带原任务引用和用户控制版本。全局额度路径不再依赖独立页面 model 配置。rollback 只恢复凭据，保留原失败原因，由调用者决定自动等候或终结手动请求。实际执行预算在旧进程停止时保存，恢复使用该剩余值，等待不扣除也不补满。无需补一套多模型批次系统。

### Q06 · P1/P2 · 本地会话和临时提问关联取错

位置：[会话 ID 回退](../../packages/runtime/src/agy-workflow-recovery.ts:46)、[aside 恢复](../../packages/runtime/src/agy-workflow-bridge.ts:577)、[aside 创建](../../packages/core/src/engine.ts:2397)。

原生会话 ID 未记录时，coordinator 最终使用 DevFlow 的 `runRecord.id` 作为 CLI 会话 ID，还可能读到另一个角色的 workflow 通用 conversation；这会接错或接不存在的本地会话。aside 分支读取 Run 上未保存的 aside_id/session_id，实际只有 `aside_session.run_id`；找不到问题后仍删除等待，原问题停在 waiting_account，占着全局提问槽。

最小修改：仅从源 Run/同角色 lineage 取实际 CLI 会话 ID，缺失则清楚报告无法续接，不用业务 ID 冒充。aside 使用现有反向关联找原问题，或在 Run 创建时补正向关联；恢复/取消前检查原问题当前状态，结算原问题而不重新提交。不存在需要“云会话迁移”的问题。

### Q07 · P1 · 停止和取消既可能假成功，也可能永不结束

位置：[取消目标](../../packages/core/src/engine.ts:4730)、[旧 runtime.stop](../../packages/runtime/src/runtime.ts:1588)、[停止时拒绝投递](../../packages/agy-accounts/src/service.ts:1639)、[停止完成条件](../../packages/agy-accounts/src/service.ts:1348)。

Engine 先把 Run 标 cancelled，再 stop 并吞异常，最后无条件返回已取消；真实 Host 停止失败时进程仍在执行。现用 runtime.stop 还可能停止整个 workflow 的共享环境，取消 aside 会影响主任务。账号服务的另一路则在 stopping/cancel 时只返回投递失败，不结算 pending operation，而停止完成又要求 pending 为空，造成永久 stopping。

最小修改：区分暂时恢复回调失败与用户已停止。后者禁止再恢复消费者，完成真实资源收尾后终结操作并清占位，不等待业务恢复回执。单目标 stop 只停止其拥有进程，不关闭其他运行仍使用的环境；确认退出后再显示取消成功，失败保留 stopping/错误。统一取消入口的返回类型，API不能依赖 Engine 没有返回的 `stopped` 字段判断成功。

### Q08 · P1 · 停止中重启会无条件覆盖活动凭据，失败状态还被抹掉

位置：[cleanup rollback](../../packages/agy-accounts/src/reconcile.ts:31)、[外层重启收尾](../../packages/agy-accounts/src/service.ts:1223)。

cleanup 直接 restore backup，未确认 owned Job 已停、外部进程或当前活动项仍属于该操作。用户已在外部换成 C 时，旧日志可以把它覆盖回 A。失败只设置 realm.phase=blocked，外层检查的是 service_state，随后可能显示 stopped/idle，掩盖恢复失败。

最小修改：清理前使用已有进程检查和凭据比较确认归属、停止与活动项；不确定就不写凭据，保留日志并报错。失败同步保持正确 service_state/phase，外层不得重置 blocked。实际备份恢复成功后再更新活动账号/epoch并收尾，不把未知现场当成功。

### Q09 · P2 · 能力接口和页面字段不一致，页面始终显示不支持

位置：[API 返回](../../apps/api/src/agy-account-routes.ts:346)、[页面接收](../../apps/web/src/components/AgyAccountsPanel.tsx:114)、[页面展示](../../apps/web/src/components/AgyAccountsPanel.tsx:316)。

API 把 host/DPAPI/login 等放在顶层，capabilities 内放 identity/dual_quota 等状态对象；前端却把 capabilities 当旧的 host 布尔对象。即使后端支持，页面也会显示空平台及 DPAPI/登录/额度检查不支持。

最小修改：前后端使用同一个小 DTO，页面读取对应真实字段；以账号全局额度状态显示可用性。无需把所有底层宿主信息堆到主要操作界面，保留明确的功能状态和错误原因即可。

### R01 · P1 · 正常调度创建的新 Run 没有接到本地续跑信息，取消也找错对象

位置：[恢复记录](../../packages/runtime/src/agy-workflow-recovery.ts:151)、[续接保存](../../packages/runtime/src/agy-workflow-recovery.ts:179)、[pending retry](../../packages/core/src/model-retry.ts:25)、[实际 Run 创建](../../packages/core/src/engine.ts:2708)、[读取续接](../../packages/core/src/conversation-lineage.ts:83)、[取消查找](../../packages/runtime/src/agy-workflow-recovery.ts:259)。关联 Q04、Q05、Q06。

coordinator 仍把 `target_run_id` 写成 `tgt_<source>_<epoch>`，将 continuation 保存在这个键及旧 Run 键下。正常 Engine 调度创建的是另一个随机 ID；`pending_model_retry.account_recovery` 只携带 frozen invocation，没有携带或转存 continuation，也没有把进度的 target 更新成实际 Run。因此新 Run 按自己的 ID 查不到原会话续接信息，身份指纹变化后会创建新会话。页面取消则查不到假 target，回退到已结束的 source，可能报告成功而实际新 Run 继续执行。

同一交接缺口还让保存的 `remaining_budget_ms` 没有进入启动超时：Engine 的正常启动仍使用完整 agent timeout，aside 仍使用完整十分钟。等待时间虽已不再扣除，每次切号又会把剩余执行时间补满。

**最小修法：** 在现有 pending retry 中携带本次恢复 ID、原生会话续接信息和剩余预算；正常调度创建真实 Run 时，同一保存步骤将 continuation 和 recovery progress 绑定到真实 ID。删除未创建 Run 的预造 ID。取消、完成与页面状态只追踪真实 Run；待派发阶段取消则移除对应 pending retry，不回退取消旧 Run。恢复 Run 使用实际启动时间加剩余预算，普通 Run 保持现有超时。继续只有一条正常调度路径，不新增执行器或会话迁移系统。

### R02 · P1 · 选中账号的实际模型探测没有交给现有访问校验，首次自动接替会被拦住

位置：[候选探测](../../packages/agy-accounts/src/switch-operation.ts:643)、[续跑门禁](../../packages/runtime/src/agy-workflow-bridge.ts:675)、[访问断言](../../packages/core/src/model-retry.ts:37)、[缓存查找](../../packages/core/src/model-access-service.ts:661)、[未接入的验证入口](../../packages/core/src/model-access-service.ts:678)。关联 Q04。

账号 B 可以已录入、额度可用，并通过 `probeModelAccess` 的候选探测；该成功只存在于 probe 的结果/缓存，没有写入 Core 的 `ModelAccessRecord`。Bridge 随即调用 `assertFrozenAccess`，要求 B 的原模型冻结配置已经有独立访问记录。如果 B 未另外在模型访问页面验证过，仍抛 `MODEL_ACCESS_REQUIRED` 并阻断自动续跑。当前生产调用链没有调用 `verifyFrozenForAccountRecovery` 来补齐这一交接。

**最小修法：** 将选中 B 后、基于原 frozen invocation 的真实验证接入现有 ModelAccessService，并保存它使用的同一身份/配置键，再继续正常调度。复用已有验证入口和账号串行队列；不得伪造成功记录、要求用户逐账号手动补模型缓存，或重新引入模型额度池。这里只衔接原任务使用的模型访问结果，不探测全部备用账号。

### R03 · P1 · 到期唤醒仍依赖独立页面的模型配置，并且丢失原任务关联

位置：[模型必填](../../packages/agy-accounts/src/service.ts:1176)、[到期重试](../../packages/agy-accounts/src/service.ts:1381)、[等待创建](../../packages/agy-accounts/src/service.ts:1635)、[原工作流请求](../../packages/runtime/src/agy-workflow-bridge.ts:334)、[恢复按操作匹配](../../packages/runtime/src/agy-workflow-bridge.ts:572)。关联 Q01、Q05。

到期 demand 创建新 switch 时不传 `model_id`，而请求入口仍要求该字段或 `standalone_model_id`。独立页面未配置模型时，会反复失败并还原等待，不能自动接替。账号全局额度和单纯手动换号也仍受到这个无关配置限制。

此外，初始 Bridge 请求没有传真实 `workflow_id`；demand 的 `consumer_id` 会回退到旧 operation ID。唤醒却将它作为 workflow ID 传入新的操作，且没有把旧操作的 consumer/source/wait 关联转给新操作。Bridge 按新 operation ID 找不到原等待，可能账号切换成功但原任务不再启动。

**最小修法：** 全局额度选择和单纯切号不要求 standalone model。工作流需要的原模型来自原 Run。创建等待时持久保存真实 workflow、source Run、consumer 关联；唤醒时沿用这些关联，并让原等待指向新尝试，或沿用原操作身份，两者采用项目现有一条路径实现。不能只补一个 `workflow_id` 参数而不处理 Bridge 的 operation 匹配。失败继续保留可唤醒状态，不另建批次调度。

### R04 · P1 · 停止后的旧等待仍会在重新启动服务时自动执行

位置：[停止清理](../../packages/agy-accounts/src/service.ts:679)、[需求唤醒条件](../../packages/agy-accounts/src/service.ts:1367)。关联 Q05、Q07。

stop 增加 `control_generation`，但只清 domain wait，没有废止对应 waiting/deferred demand。tick 筛选仅检查 demand 状态和时间，不比较其原控制版本或源任务是否仍有效；随后用当前 epoch 创建新操作。存在“等待额度 → 用户停止 → 再启动账号管理 → 旧等待到期自动换号”的路径，旧用户意图被重新授权。

**最小修法：** 停止/取消时结算对应等待需求；唤醒前同时确认原控制版本、源任务和消费者仍有效。服务重新启动只能允许新的请求，不能把旧 demand 换成当前版本继续执行。复用已有 generation 与 demand 状态，不增加新的控制系统。

### R05 · P1 · 新增额度刷新先落库后核对身份，同账号 token 刷新也会被误判

位置：[刷新与写快照](../../packages/agy-accounts/src/service.ts:818)、[后置凭据比较](../../packages/agy-accounts/src/service.ts:861)、[完整凭据比较实现](../../host/devflow-auth-host/main.go:135)。关联 Q01。

`acquireUsagePermitOwned` 在旧快照到达重置时间后，以本地账号 A 的 ID 发起 `/usage`，未校验 `fresh.email` 就把返回额度写给 A。若用户已在外部切成 B 且外部进程已退出，该探测实际读到 B；后面的 `compareActive` 虽会拒绝执行，但 A 的额度快照已经被污染。

该路径也没有像其他探测路径一样 capture 官方 CLI 更新后的凭据。若 `/usage` 期间同一账号正常刷新 token，完整凭据 JSON 与旧 secret ref 不同，后面的比较会报 `external_change`，本来可执行的任务被阻断。

**最小修法：** 使用现有身份核对与凭据捕获逻辑，先确认探测属于预期账号，核对返回身份及请求前后的账号上下文，再保存快照。同账号真实刷新后的 secret ref、credential revision 和 realm 引用一致更新；不同账号则拒绝保存。不要简单删除身份比较，也不要继续用旧凭据的字节相等代替刷新后的账号归属核验。

### R06 · P1 · 未确认进程停止的错误仍被调用方当作普通探测失败

位置：[底层新错误](../../packages/process/src/agy-account-job-runner.ts:227)、[身份探测降级](../../packages/agy-accounts/src/enrollment.ts:119)、[额度探测 catch](../../packages/agy-accounts/src/enrollment.ts:198)、[切号 catch](../../packages/agy-accounts/src/switch-operation.ts:550)、[维护 catch](../../packages/agy-accounts/src/service.ts:2041)、[统一 rollback](../../packages/agy-accounts/src/service.ts:1548)。关联 Q03。

底层现在正确拒绝 `verifyJobStopped=false`，但错误为普通 Error。enrollment 捕获后还能启动第二次探测；switch/maintenance 将它改成 `probe_failed`，服务统一异常分支也没有把它识别为不得写凭据的停止失败。因此旧 Job 尚未确认停止时，上层仍可能继续探测或回滚活动凭据。仅修改 runner 并未闭合 Q03。

**最小修法：** 给该错误稳定的类型/错误码（错误消息可附 Job ID），所有 probe catch 原样传播。账号服务将它接入现有 blocked/停止待确认分支，保留操作占位和当前身份，禁止后续 probe、安装和 rollback。确认原 Job 停止后才能收尾。不要用拼接 Job ID 的完整 message 做固定字符串匹配。

### R07 · P1 · Go Host 的登录窗口仍无法进行终端输入

位置：[Go 标准流绑定](../../host/devflow-host/main.go:191)、[登录 spec](../../packages/process/src/agy-account-job-runner.ts:348)。关联 Q02。

Go 分支虽然设置了 `CREATE_NEW_CONSOLE`，却仍无条件把 CLI stdout/stderr 接到 Host 管道；stdin 只有 `spec.Stdin` 非空才设置。登录 spec 没有 stdin 内容，Go exec 的空 stdin 会接空设备。因此出现需要在终端选择、确认或输入的官方登录流程时，窗口可见但没有可用交互输入，提示也不在该窗口。

**最小修法：** interactive 分支使 CLI 的标准输入输出连接其新控制台，Host 的 JSON 控制通道继续独立；后台 probe 保留当前管道方式。修现有 Go Host，不再引入第三种宿主，C# 已修部分保持不变。

### R08 · P1 · 临时提问仍无法找到原问题，单目标取消还会停止共享环境

位置：[aside 恢复关联](../../packages/runtime/src/agy-workflow-bridge.ts:577)、[aside 创建](../../packages/core/src/engine.ts:2295)、[目标取消](../../packages/core/src/engine.ts:4613)、[环境停止](../../packages/runtime/src/runtime.ts:1588)。关联 Q06、Q07。

aside 分支仍从 Run 读取未保存的 `aside_id/session_id`，而创建端只保存 `aside_session.run_id`。额度切换成功后找不到原问题，仍清除等待，原问题留在 waiting_account 并占用提问槽。这项旧缺陷尚未修复。

Engine 的取消现在能报告 stop 失败，但调用的 `runtime.stop` 仍可能按 workflow 配置停止整个共享环境；取消一个恢复中的 aside 会连带影响正在执行的主任务。

**最小修法：** 沿现有 aside_session 反向查原问题，或补正向关联，恢复时检查原问题未取消并继续原问题/会话/剩余预算；关联缺失不能按恢复成功清除等待。给现有 runtime.stop 明确单 Run 停止范围，单目标取消只停止它拥有的进程，整工作流停止才关闭共享环境。无需另建 aside 恢复队列。

### R09 · P2 · 探测 runner 的退出与取消监听没有统一收尾

位置：[Host exit 结算](../../packages/process/src/agy-account-job-runner.ts:301)、[abort 监听](../../packages/process/src/agy-account-job-runner.ts:261)、[cleanup](../../packages/process/src/agy-account-job-runner.ts:220)。关联 Q02、Q03。

Windows probe 在 Host 的 `exit` 事件上直接结算；该事件发生时 stdout 可能尚未排空，结构化 CLI exit 消息还没被解析。此时用 Host 的退出码（常为 0）和不完整输出先设置 resolved，后续真实 CLI 结果被忽略。登录路径虽已改正，probe 路径仍保留旧问题。

probe 结束后也没有移除原 signal 的 abort listener，且 onAbort 在 kill 前不检查是否已结束。同一操作后续取消时会重新对已退出 Host 的旧 PID 执行 taskkill；PID 被复用时存在误杀无关进程的风险。

**最小修法：** 统一成功、失败、超时、取消的收尾，保存结构化 CLI 终态并等待输出排空；缺失终态按 Host 通道中断处理，不拿 Host 0 替代 CLI 成功。结算时移除 abort listener、清理 timer；abort 先检查结算状态，仅停止仍属于本次操作的存活进程。

### R10 · P2 · 正常回滚后重启仍可能被判为外部账号变化

位置：[恢复期对账](../../packages/agy-accounts/src/reconcile.ts:137)、[实际结果用于投递](../../packages/agy-accounts/src/service.ts:1684)。关联 Q08。

**最小修法：** 与现有 deliverConsumers 使用同一最终结果规则：switched 校验提交的 B；restored 校验恢复后的 A 和恢复 epoch。不要再次写入凭据来强行满足旧 target，也不另建恢复日志。

### 5.2 R03 · P1 · 独立切号和等待唤醒仍有两个确定断点

最小修法：在准备新尝试时，通过已经保存的 original_operation_id/source_run_id 取得原操作的 runs、等待和 checkpoint，绑定到这次尝试，再由同一组消费者恢复。新回调应能够读取这份绑定；只修改末端 matchesOp 不够。不增加第二条调度路径。

### 5.4 R01 · P1 · 待派发取消返回成功，普通队列仍会启动

位置：[cancelRecovery:249](../../packages/runtime/src/agy-workflow-recovery.ts:249)。

无 target 的新分支只删 pending retry 和 continuation，然后返回成功。此前 Bridge 已通过现有入口把 workflow 放到 QUEUED/REVIEW_QUEUED，或写了 planning 的 dispatch job；这些排队状态没有被撤销。恢复等待容量时点击取消，容量释放后任务仍会作为普通 Run 启动，同时丢失已删的续接和预算。

此 early return 还在归属核对、expectedRevision 和 request 去重之前：旧页面请求可以删掉该 workflow 后来新的 pending retry；URL 的 workflow 和 recovery 不匹配时也先按 URL 删除记录。

最小修法：先沿 source/manifest 核对 workflow 归属、revision 和请求去重，再确认 pending/队列仍属于同一个 recovery 与 source。使用现有 Engine 暂停/撤销排队入口，原子撤销这一恢复对应的排队意图和 dispatch，之后才清续接信息并标记取消。不能直接删除 workflow 下任意 pending retry；也不能只改 progress 状态而放任普通调度继续。

### 5.5 R04 · P2 · 取消具体等待操作后仍会到时切号

位置：[取消操作](../../packages/agy-accounts/src/service.ts:1134)、[等待释放 pending](../../packages/agy-accounts/src/service.ts:1737)、[到期筛选](../../packages/agy-accounts/src/service.ts:1402)。

最小修法：取消时同步结算关联原操作的 waiting/deferred/selected demand；唤醒前拒绝已取消的原操作和已失效的源任务。使用已有 ID、状态和 generation，不新增控制机制。

### 5.6 R07 · P1 · Go Host 交互标准流仍为空设备

位置：[main.go:194](../../host/devflow-host/main.go:194)。

本次 interactive 分支跳过全部标准流设置，随后仍调用 cmd.Start。Go 的 nil Stdin/Stdout/Stderr 会接到 os.DevNull，Windows 启动实现会显式使用这些句柄；不会自动接入新控制台。因此 Go Host 的窗口依然无法供 CLI 输入或显示提示。这个语义已只读核对本机 Go 标准库，未进行真实登录。

最小修法：在现有 Go Host 的 Windows 交互启动路径中，采用与 C# 分支等效的原生新控制台创建，不设置 STARTF_USESTDHANDLES，让新控制台提供标准输入输出；保留 suspended→加入 Job→resume，以及独立 Host 控制通道。非交互 probe 保留原实现。仅将三个标准流留空仍然不能工作。

### 5.7 R02 · P2 · 恢复校验无条件覆盖真实访问状态

位置：[ensureAccountRecoveryAccess:661](../../packages/core/src/model-access-service.ts:661)、[通用重试断言](../../packages/core/src/model-retry.ts:71)、[派发时调用](../../packages/core/src/run-profile.ts:134)。

helper 在缓存不是 verified 时直接写 `verified/native-probe/last_success_at`，没有消费本次候选探测成功结果，而且会覆盖已有失败记录。它不仅在切号后的回调执行，还在排队后的普通 bindProfile/恢复断言中再次执行；例如排队期间另一次真实检查已得到 forbidden/login_required，派发又将其改回 verified，错误状态被抹掉。

最小修法：在实际成功的候选 probe 返回处，将相同账号、原模型和实际配置对应的结果写入现有 ModelAccessRecord；通用 assert 只读取和校验，不写成功。已经合并并探测 occupancy 模型列表的逻辑保持不变，不要求探测全部备用账号，也不新增额度池或认证门禁。本项是访问记录正确性问题，不是对执行者测试材料的要求。
