# 本地安全与调度体验优化方案

## 1. 背景、现状与目标

DevFlow 是供本机用户使用的轻量模型调度器。当前主要问题是 AGY 账号切换、额度刷新等待较久，执行过程混入平台内部指令和重复状态。此次目标是缩短操作等待、减少后台消耗、精简展示，并修补已发现的文件边界问题。

保持本地运行和免登录，复用现有 SQLite、账号协调器、受管进程及 WebSocket。实现集中在现有模块内，不引入额外服务、数据库、队列中间件或新的审批关卡。

**本方案已获准实施，改动纳入 v0.3.0。** 实现与验证状态见 [v0.3.0 验证记录](../test/v0.3.0-验证记录.md)。以下检查结论保留调查时口径：2026-10-25，依据当时磁盘工作树、现有服务的只读接口、浏览器页面、数据库计数及历史运行日志。仓库基线为 `00e3e67`，另有大量既存未提交修改。运行服务报告构建为 `workspace-37f338b750a248ed7eb5`，当时尚未证明它与工作树完全一致。

调查阶段未修改产品代码，未实际切换账号、主动调用额度 CLI、重启服务或运行攻击样例。该阶段性能采样只用于定位，不能作为优化后达标数据。

## 2. 检查结论与优先级

| 优先级 | 已核实的问题 | 影响及证据 |
| --- | --- | --- |
| P0 | 自动规划文档可越过项目边界写入 | 首次规划无已登记原件时，模型返回的绝对 `file_ref` 跳过材料定位器；服务在提交计划和人工批准前直接写文件，可覆盖本用户可写的项目外文件。源码链确认，未运行破坏性复现。见 [文档服务](../../packages/core/src/document-service.ts)、[规划入口](../../packages/core/src/engine.ts)。 |
| P0 | AGY 程序指纹被反复同步计算 | [程序定位器](../../packages/adapters/agy/src/executable-resolver.ts) 每次解析都完整读取并计算哈希；[额度探测](../../packages/adapters/agy/src/account-probe.ts) 在合并同类请求前计算一次，执行时再次解析。现场程序为 204,022,936 字节，三次独立读文件加哈希耗时为 1.83、1.52、2.04 秒。普通额度链路的两次处理可能占用数秒，并阻塞控制器事件循环。 |
| P0 | 部分额度采集不能及时让位给切号 | [协调器](../../packages/agy-accounts/src/coordinator.ts) 的前台优先只影响下一个任务；正在执行的任务仍占队列。[账号服务](../../packages/agy-accounts/src/service.ts) 的部分收尾额度采集走默认前台队列，未接入已有后台取消信号。10 月 23 日日志中两次切号分别排队 10.64、3.99 秒，实际执行仅 0.52、0.22 秒；这些是历史样本，不是本轮切号实测。 |
| P1 | 账号页面重复读取，刷新与首屏耦合 | [账号面板](../../apps/web/src/components/AgyAccountsPanel.tsx) 同时请求账号和服务信息，等待两者后才更新；打开后无条件同步刷新，挂载期间每 3 秒再读两次。切号收尾还可能等待旧读取请求。 |
| P1 | 服务接口重复构建展示数据、读取过多历史 | [账号路由](../../apps/api/src/agy-account-routes.ts) 的两个 GET 都构建完整账号展示；操作记录先全量读取、解析、排序，再取 100 条。现场 8 个账号，两份响应合计约 60 KB；暖连接少量样本中账号 GET 约 54–235 ms，服务 GET 约 86–183 ms，已有数秒等待不能只归因于这两个 GET。 |
| P1 | 执行过程展示内部指令及重复状态 | 页面已看到模型恢复提示中的 `need_user/user_interaction` 指令、重复阶段切换、排队与开始提交的重复文案、原始结果 JSON，以及任务完成后仍保留的“将启动独立复核”提示。[活动投影](../../packages/presentation/src/activity.ts) 会直接选取 `instructions` 等字段；部分恢复指令与用户说明共用同一正文。 |
| P1 | Windows 旧文件工具存在大小写策略缺口 | [文件代理](../../packages/workspace/src/files.ts) 对自定义保护路径和依赖文件名使用区分大小写的比较，可能被指向同一文件的大小写别名绕过。仅旧版 MCP 文件工具可达，当前默认原生模式不走此入口，风险较低。 |
| P2 | 调度、展示缓存及目录监听有重复工作 | [调度入口](../../packages/core/src/engine.ts) 循环中重复读取工作流，候选选择和资源检查重复遍历；[页面缓存](../../apps/api/src/server.ts) 受全库变更影响；[工作区监听](../../packages/runtime/src/workspace-observer.ts) 创建后缺少随任务结束的完整回收。详见任务 6。 |

现有安全控制已有基础：服务限定回环地址，检查 Host、Origin、Fetch-Site、写请求格式和 WebSocket 来源；模型接口另校验运行令牌与归属；AGY 凭据通过专用 worker 和系统加密存储。当前证据不支持增加登录。

安全检查发现 1 项高风险、1 项低风险源码问题；完成入口检索、44 个文件完整审阅及重点调用链追踪，未穷尽全仓，也未查询依赖漏洞库、实测系统权限或证明运行构建含相同问题。历史证据路径的旧生产链、全部事件来源分类仍需定向核验，暂不列为已确认漏洞。

## 3. 总体方案

按“修补文件边界 → 消除本机重复耗时 → 让手动操作优先 → 缓存展示与异步刷新 → 精简执行过程 → 收敛后台开销”实施。前两项收益明确，优先完成；后续每项都以独立测量和回归结果决定是否继续扩大改动。

已有的账号快照、同类刷新合并、当前账号刷新、手动切号身份校验及健康任务保护继续沿用。不能把这些已有能力当作本次新增成果，也不能为了速度去掉身份校验、模型能力校验、凭据锁或进程退出确认。

## 4. 实施任务

### 任务 1：统一文档写入边界，保护用户文件（P0）

用途：让规划结果只能更新本任务有权维护的文档，避免模型输出借服务权限覆盖其他文件。

1. `DocumentService` 的新路径和已登记路径全部经过现有材料定位器。新文档默认由平台选择项目文档位置；模型提供的路径只是候选，不能直接覆盖无关联的已有文件。
2. 复用 `material-filesystem` 的安全文件句柄，检查项目归属、链接和目录身份；读取、首次创建、原件更新执行一致的边界规则。兼容项目内绝对路径及合法多仓库原件，不因修复随意迁移原件或生成副本。
3. 发布前完成计划合同、项目配置和当前轮验证。写入期间保留内容冲突检查，防止覆盖并发人工编辑；文件发布与数据库登记失败时可恢复，拒绝操作不得先改目标文件。复用现有材料发布机制，不另建文档审批流程。
4. 顺带修补旧版文件代理的大小写比较：保护路径、依赖文件名及同批别名遵守实际文件系统语义，保留 POSIX 大小写区分。

验收：项目外路径、目录逃逸、链接到外部、失效轮次及内容冲突均拒绝且目标不变；合法原件更新、多仓库引用及用户已有进度保持正常。修复失败时保留原件并返回可操作错误，不能退回裸路径写入。

### 任务 2：消除 AGY 指纹重复计算（P0）

用途：先移除完全发生在本机的确定性等待，同时避免同步大文件处理卡住其他请求。

1. 将“定位程序”与“计算指纹”分开。按实际路径、文件身份、大小及修改信息缓存指纹；程序更新、路径改变或显式失效时重新计算。
2. 同一程序的并发调用共用一个异步计算任务。用流式读取计算哈希，避免每次分配约 204 MB 缓冲；计算前后核对文件身份，变化时丢弃结果。
3. 一次探测从验证适配器到启动 CLI 复用同一个已解析程序描述。把同类请求合并放到昂贵准备工作之前；保留程序更新后的适配器重新验证。
4. 在现有诊断日志增加必要分段耗时：排队、程序准备、CLI 启动与响应、解析、提交。只记录时长及已有操作关联信息，不记录凭据，也不新增监控页面。

验收：同一未变化程序的连续与并发探测不重复全文件哈希；程序替换能失效；探测期间其他本机 API 不再因指纹处理停顿数秒。冷启动耗时单列，不与缓存命中混算。

### 任务 3：让账号切换及时获得执行机会（P0）

用途：切号主要等待本地身份切换，不被可延后的额度统计拖住。

1. 在现有协调器内明确顺序：用户切号优先，其次本轮启动所必需的验证，最后是可延后的额度、模型列表和收尾统计。
2. 将所有可延后的探测接入统一取消和截止时间，尤其是 `releaseUsagePermit` 的收尾额度采集。人工切号到来时取消本服务拥有的辅助探测；确认其真实退出后才释放域锁并继续。
3. 不可中断的必要校验在安全边界完成后重新排队；不得通过只结束等待 Promise 的方式，把仍运行的 CLI 留在后台。
4. 同一系统用户的 AGY 活动凭据仍按同一目标串行处理。不得并行换入多个账号来“加速”；保留账号、凭据版本、身份代次及当前轮绑定，过期探测结果不得写到新账号。
5. 手动切号继续只完成必要身份流程。成功后立即返回并更新界面，额度和模型目录按原有能力边界补齐。健康任务、已取得的运行许可和会话绑定保持有效。

验收：覆盖空闲切换、额度探测中切换、收尾采集中切换、连续点击、任务启动竞争、CLI 卡死及停止失败。停止未确认时准确显示等待或阻塞；不得虚报切换成功、误杀健康模型进程或遗留凭据域锁。

### 任务 4：账号快照立即展示，额度按需刷新（P1）

用途：打开面板先看到可用信息，外部额度查询慢时仍能操作账号。

1. 合并管理面板的本地读取为一份快照，包含账号列表、当前账号、必要服务状态、正在执行及最近完成的操作。保留原接口兼容调用方，面板只读新快照；历史记录按需分页，不再每次取 100 条。
2. 快照读取不执行 CLI，也不顺带做状态修复。过期操作清理回到已有维护流程；使用数据库条件和 `LIMIT` 限定操作记录，避免先全量解析再截断。
3. 打开时立即展示已有缓存，再取本地最新快照。当前账号额度默认超过 60 秒才自动查询；有效期内重复打开不启动 CLI。手动刷新可跳过时间判断，但仍合并同账号、同凭据版本的在途请求。
4. 刷新请求快速返回受理结果，沿用已有操作关联与状态通知完成更新。额度查询进度独立于列表、切号按钮；切号完成不等待旧快照请求，过期响应不得覆盖新状态。
5. 复用现有 WebSocket 发送账号状态变化通知，收到后合并一次快照读取。连接正常且无变化时不轮询；断连兜底仅在面板可见时运行，操作中约 1 秒、空闲约 30 秒。隐藏或关闭后停止轮询，不取消其他使用者仍需要的共享操作。
6. 额度保留每个额度池的真实更新时间。失败时展示上次值及“更新失败/已过期”，未知值保持未知；不得清零、推算重置后的满额，或把其他账号旧数据算成最新数据。取消因切号触发时不显示失败警报。
7. 继续只自动刷新当前账号。其他账号显示各自已知值及时间；在没有证实官方 CLI 支持独立凭据上下文前，不自动轮换所有账号查询额度。

验收：开关面板、双标签页、手动刷新、连续切号、慢网、断线重连及晚到响应均不重复探测、不串账号、不阻塞本地操作。前后端共用刷新状态，移除重复的 `syncing/refreshing` 控制。

### 任务 5：执行过程只展示对用户有用的信息（P1）

用途：用户能看清做了什么、结果如何、是否需要行动，平台内部调度不占据主要阅读空间。

| 当前内容 | 调整后的展示 |
| --- | --- |
| 平台工作包准备、来源版本选择、会话绑定、内部续接和恢复指令 | 默认不进入用户时间线；诊断数据保留在已有详情或日志中。 |
| 连续“进入测试”“等待复核”“开始复核”等状态 | 同一阶段只保留一个必要分隔和当前状态；阶段完成后撤掉过期通知。 |
| “提交已排队”“正在提交”的重复说明 | 当前状态显示一次，完成后展示实际结果和提交号。 |
| `need_user/user_interaction`、内部错误 JSON、续接模板 | 用户正文只说明问题、影响和可执行动作；技术信息进入既有可展开详情。 |
| 平台结果协议的原始 JSON | 识别已验证的结果合同，展示摘要、实际检查结果、产物及提交信息；不渲染协议空字段。 |
| 平台专用材料文件的机械读取 | 能根据来源和精确路径可靠识别时默认收起；与业务命令混合或来源不明时保留。 |
| 用户指导、模型提问与用户回答、真实模型正文、业务命令及失败结果 | 保留原文、换行、关联顺序和实际状态；不改成“已发送给模型”等占位提示。 |

实现集中到 `packages/presentation`，历史 HTTP、实时 WebSocket、主执行区和子代理记录使用同一规则。优先根据已有事件类型、来源及字段分类；确实无法区分的生产者补最小来源标识，不新增用户设置页。

同时修正生产源：把引擎发给模型的恢复指令与用户协助说明分开，避免继续复用同一段正文。禁止按关键词、`HANDOFF` 字样或“所有 JSON”粗暴删除，不能隐藏用户项目中的正常代码、文件名和模型回答。历史事件按已知合同兼容投影，未知内容保留；不改写或删除数据库中的原始事件。

验收：真实页面中的内部恢复模板、重复状态和已过期提示消失；错误仍说明原因与下一步；原文指导、回答、正常 JSON 内容及诊断脱敏保持正确；实时显示与重新打开历史记录一致。

### 任务 6：收敛后台调度和数据读取成本（P2）

用途：任务和历史增长后，后台工作仍与活跃任务相关，避免空闲消耗持续增加。

1. 调度：每轮读取一次工作流、候选和资源租约，按快照选择可启动任务；提交/释放等事件触发合并唤醒，保留低频兜底。维持优先级、公平性、并发上限和租约检查，不在整轮期间持数据库写事务等待外部进程。
2. 展示缓存：将全库变更导致的失效收敛为对应工作流和必要全局依赖的失效；纳入计划文件变化。保留有界缓存，验证外部计划编辑、重连及其他数据库连接写入不会留下旧页面。
3. 历史查询：操作和额度历史按查询条件、排序与条数在数据库层读取；先检查查询计划再决定是否需要增量索引。现场数据库约 441.5 MiB、事件 230,221 条，这只证明需要有界读取，不足以证明应清库或更换数据库。
4. 目录监听：按实际仍需监听的工作区核对集合，关闭已无引用的 watcher；在读取计划前排除 `.git`、依赖和构建产物事件。共享工作区保留必要引用，恢复任务或修改计划时能重新监听。
5. 前端：已有会话增量读取、事件缓冲和局部更新继续沿用。仅在构建体积与页面采样证实有收益时，延迟加载 Mermaid 并限制 SVG 缓存；不为小幅收益重做整个前端。

验收：任务完成、关闭及重新打开不会累计 watcher；空闲时不启动 AGY 查询；调度不丢任务、不重复启动、不突破资源限制；历史增长时接口只读取展示所需数量。不得以清理空间为由删除任务记录或停止活跃服务。

## 5. 性能验收指标

以下为实施目标，实际结果与未验证项见验证记录。优化前后使用同一机器、同一构建模式与相同数据，区分冷启动、缓存命中、外部 CLI 和队列等待；本机指标至少采集 30 次，报告中位数、P95 和失败数。

| 场景 | 目标与判断口径 |
| --- | --- |
| 面板已有缓存 | 打开后 300 ms 内显示可操作列表；额度刷新不遮挡列表。 |
| 本地读取及操作受理 | 暖机快照、切号/刷新受理 P95 ≤ 200 ms；端到端 UI 另计，不能只报接口时间。 |
| 空闲切号 | 从点击到目标身份已验证且界面更新，P95 ≤ 2 秒；以暖机、锁可用为条件。 |
| 可取消采集占用时切号 | 正常可停止采集场景 P95 ≤ 3 秒；停止失败单列，不能放宽退出确认来达标。 |
| 额度查询 | 受理后立即可操作；保留现有 10 秒 CLI 预算，将准备与清理纳入整体截止时间，目标总等待上限 15 秒。若进程无法确认退出，返回明确阻塞状态，不强行解锁。官方响应速度不作“秒出”保证。 |
| 重复打开与空闲 | 60 秒有效期内重复打开不启动额度 CLI；每个凭据域至多一个在途探测；隐藏面板无轮询。 |
| 本地请求量 | 同一现场数据下，面板单次读取总响应体较当前两份合计约 60 KB 至少减少一半；稳定连接无变化时不重复拉取。 |
| 对现有任务的影响 | 切号、取消采集前后，健康任务的进程、运行许可及会话绑定保持有效；额度不串账号。 |

达不到目标时按分段耗时继续定位，不用缩短超时、隐藏失败或降低必要校验来制造改善。

## 7. 实施顺序、兼容与回退

1. 开始实施时重新盘点未提交变更和运行构建，明确本次修改文件；现有 10 月 23 日 AGY 整改继续保留。
2. 先完成任务 1、2，再完成任务 3、4；任务 5 独立完成后统一验收。任务 6 按实测收益逐项纳入，避免同时改写调度、存储与界面导致问题难以定位。
