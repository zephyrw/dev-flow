额外复核修复：合法 Mermaid 图在每轮整改重新冷启动时可能超过原 60 秒期限，导致质量流程被误报阻断。现在对成功解析的完整图表内容缓存最多 64 个 SHA-256，重复并发请求共享解析任务，不同图表串行解析，工作线程结束即释放；失败结果不缓存，新图表仍必须经过真实语法解析。Windows 控制器身份查询由 10 秒调整为 30 秒，服务启动和安装等待期限同步延长，仍以实际身份记录及健康端点确认成功。

补充修复：`@` 文件菜单通过浮层避免被原布局裁剪；创建失败保留需求草稿；规划阶段旁路提问转反馈后重新规划；新安装可通过 MCP 获取八个原生配置 ID。CI 先构建服务/Host，再运行单元、集成及真实浏览器回归。

六个源码 Skill 和本机 Codex、Antigravity 安装副本均使用原始/正式整改计划作为唯一实施依据，禁止执行模型另建替代计划。程序强制单独派发自查轮次并核对完整计划正文、版本/哈希和实际测试证据，随后仍由规划模型独立审查。

## 上一轮结论（修复前）

本轮增加的“执行模型按正式计划再次复核”接入既有 native-v2 执行、交付和规划审查入口；Skill 源码与本机安装副本同步更新。**agy 补充后的整个平台仍未通过独立复核，不应提交为已经全部完成的交付。**

尤其不能把本轮自查门禁验证通过，解释成新任务创建、八工具调度、两道质量循环、安装和 Git 整合均已完成。下列问题分别列明复现事实、程序入口及验收边界。

## 本轮直接完成的修改

1. 普通开发及整改成功退出、交付核验通过后，程序持久化自查请求，再通过既有执行队列启动一个新的执行轮次，保留原执行模型配置及会话。当前服务没有增加额外后台轮询。
2. 自查输入包含原始计划及已批准的正式整改版本。完整正文、任务/测试编号、native work_items/acceptance_items 都进入核对范围；design_ref 必须解析到哈希一致的完整正文，不能以摘要替代。
3. 报告绑定请求、源交付、计划版本/hash、正文集合、反馈/环境上下文及执行轮次；普通开发轮次无法自称完成了程序自查。
4. 漏项、重复编号、空证据、未关闭问题、旧版本、失败/停止进程、无效当前交付不能进入规划审查。修复必须重新交付有效测试证据。报告本身不证明语义正确，规划模型仍独立检查代码和测试。
5. 自查不增加质量关卡三次拒绝计数。人工前/人工后的审查意图分别保留；既有两关卡及接管机制本身仍需解决下文 V04 的集成缺口。
6. 现有界面布局保留，在原文档工具区增加“查看计划自查记录”；阶段提示显示自查、修复与规划审查。
7. 更新仓库六个标准 Skill、三份合同引用、相关指南/方案，以及本机 Codex 与 Antigravity 中对应副本。保留各安装目录原有独立配置。

主要实现：`packages/contracts/src/plan-self-check.ts`、`packages/core/src/plan-self-check.ts`、`packages/core/src/engine.ts`、`packages/runtime/src/runtime.ts`、`packages/adapters/agy/src/handoff.ts`。报告通过交付清单的 `plan_self_check` 字段提交，完整 JSON Schema 随自查工作包提供。

### 复核过程中发现并已修复的自查绕过

最终逐段检查发现引擎出现了按任务名称启用门禁的条件：仅标题为“计划自查”“原生执行交付核验”，或存在 `plan_check_enabled` 时才运行新流程；普通标题仍走直接人工验收。这个条件不在用户要求中，也不能作为兼容模式保留。

已保存[修复前源码条件与哈希](evidence/devflow-selfcheck-review-20260916/conditional-bypass-before-fix.json)。将同一真实调度夹具改为每次不同的普通标题后，[反例测试](evidence/devflow-selfcheck-review-20260916/conditional-bypass-red.json)明确失败：实际阶段是 `manual_acceptance`，预期是 `executor_plan_self_check`。

本轮已删除所有上述标题/可选开关分流，并将随机普通标题保留为回归夹具。这同时说明：固定样例测试通过不能替代对生产分支的复核。不对该条件的作者或动机作推断。

## 修复前问题与验收基准（V01—V10）

### V01 / P1：新建任务的调度消息被消费，但规划模型没有运行

位置：`apps/api/src/main.ts` 的 outbox 消费循环；`packages/core/src/engine.ts` 的 `dispatch`；`packages/core/src/create-workflow.ts`。

真实 API 创建后状态为 PLANNING，SQL outbox 存在。按主程序现有逻辑入队、标记 delivered，再调用真实 Engine.dispatch：调度器只接受 QUEUED/REVIEW_QUEUED，删除规划任务队列。复现结果：模型调用次数为 0、状态仍 PLANNING、队列已无记录、待消费 outbox 为 0；创建服务却已写入 running 的 Run。

必须由统一调度入口识别 planning、implement、plan_self_check、quality_review、planner_takeover、functional_fix、aside 等明确用途，并调用真实对应运行时。未知用途不得当成功消费；不得先写 running 再没有进程地遗留。恢复必须能根据持久化队列/运行意图补派而不重复执行。

验收必须从 POST /api/workflows 开始，执行真实消费者，观察规划子进程/适配器收到完整需求并产生可展示的计划；拒绝路径要检查无进程、无伪成功状态，不能只断言 outbox 插入成功。

### V02 / P1：新功能确认接口绕过证据校验，且没有派发终审

位置：`apps/api/src/server.ts` 的 POST /api/workflows/:id/confirm-function。

接口只检查没有未关闭问题和状态为 HUMAN_PENDING，直接写 AFTER_HUMAN_REVIEW。隔离复现中，没有计划快照、有效交付及 acceptance 记录，接口仍返回 200；没有新增调度消息，后续终审也无法运行。

接口必须复用统一人工确认领域入口，绑定当前版本、交付、执行计划自查、第一道质量结论和用户功能确认；同一事务落确认记录与终审派发，不能直接赋值状态。保留用户真实确认，不由模型生成确认凭据。

验收：空证据、失效版本、未关闭问题均拒绝且不改变状态；有效确认派发一次终审，重复确认返回原回执，旧反馈不能被覆盖。

### V03 / P1：清理入口能把尚在规划的任务标成完成

位置：`apps/api/src/server.ts` 的 cleanup/retry；`packages/git/src/delivery-coordinator.ts` 的 cleanupWorkspaces。

没有检查任务已提交/合并及对应整合收据。对仍 PLANNING、使用非自有工作区的任务调用真实接口，返回成功清理收据并将状态改为 COMPLETED；实际没有提交记录。对 owned 工作树还会在未核实合并的情况下尝试删除。

只允许已确认提交/整合的合法清理阶段进入。逐仓库核对目标提交和收据、Git worktree 真实所有权与路径，失败保留 CLEANUP_PENDING；不得以“没有需要删除的目录”推导业务已完成。

验收：规划/执行/未整合任务调用必须拒绝，目录、分支、状态不变；合并后清理可幂等重试且不再提交/合并。主工作区模式完成必须以实际提交确认为依据。

### V04 / P1：质量协调器仍可接受没有计划和运行证据的通过结论，主链路没有接入该协调器

位置：`packages/core/src/quality-coordinator.ts` 的 evaluateReviewResult；生产 Engine/Runtime 调用关系。

Schema 校验只在 changes_required 分支执行。对 plan_revision=0、无交付的 VERIFYING 工作流，仅传 workflow_id、phase、verdict=passed，即返回 action=pass。生产 Engine/Runtime 也没有调用 QualityCoordinator；辅助类计数用例不能证明两道质量循环及第三次接管已进入真实执行链。

所有 verdict 先统一严格校验，再校验真实 Run、退出结果、当前计划/交付/反馈游标及本轮执行计划自查。去重键相同而内容变化应拒绝，不能再次增加拒绝计数。将协调器接入实际规划审查完成事件，整改派发及第三次接管必须产生真实 Run。

验收必须从正常任务流转到两道质量关卡，实际执行整改和接管写入/新只读自审；不能预置 VERIFYING 后连续调用三次辅助函数代替完整流程。

### V05 / P1：适配器为不存在的运行返回虚构执行事实

位置：`packages/adapters/sdk/src/base-adapter.ts` 的 readExecutionFacts。

传入不存在的 workflowId/runId，返回一条 command=noop、status=completed 的事实。该事实没有对应宿主进程、命令开始/结束、真实退出码和原始报告。仅 --version 含产品名时也把全部能力标为 true，不能证明只读、续接、浏览器和事实提取已经认证。

必须从对应客户端/宿主原始事件读取与运行绑定的真实事实；未执行返回空事实，能力不支持明确返回不支持。不能合成 completed 占位结果。按工具分别验证支持的能力和版本。

验收：不存在的运行、未结束命令、非零退出、错误会话、旧报告都不能形成有效交付；真实成功运行须能追溯原始事件和报告。

### V06 / P1：安装器只写状态文件就宣布安装完成

位置：`packages/installer/src/main.ts`、`components.ts`、`manifest.ts`，及 bootstrap 脚本。

隔离复现传入不存在的 sourceDir，选择 Codex，指定全新临时安装目录：runInstaller 返回 0，目录内只有 state.json，node/host/skills 均标 VERIFIED。没有组件下载/安装、服务、Skill 或 MCP 配置。组件解析忽略 selectedTools；发布清单还指向 devflow/devflow，且使用空文件 SHA-256 作为非空二进制校验值。

必须落实原计划规定的组件依赖、真实安装、六个 Skill 及 references、配置合并和实际健康验证；每一步按成功副作用推进状态。正式发布使用用户指定 zephyrw/dev-flow 的实际资源及真实校验和。不存在的源/资产不能返回 0；安装缺少认证时返回明确待用户动作状态。

验收使用临时 HOME/USERPROFILE/CODEX_HOME，从零执行安装入口，核对真实文件与 MCP 配置及服务健康；中断、恢复、坏哈希、配置冲突和卸载分别验证。禁止把状态枚举完整等同安装完成。

### V07 / P1：保存了工具 Profile，但生产执行仍写死 agy/Codex

位置：`packages/core/src/engine.ts` 的 Run 创建；`packages/runtime/src/runtime.ts` 的 execute/review；`packages/core/src/create-workflow.ts`。

实际 Run 仍使用 reviewer=codex、executor=agy；运行时直接调用 agy_executable 和 Codex 复核命令，没有从 ExecutionSpec 选择注册适配器。创建时非 agy/codex 的 plannerAdapter 也被落成 agy。因此“选择 Claude 规划、Kimi 执行”或指定单工具不会按保存的配置执行。

唯一运行源应是本次固定版本的 ExecutionSpec/Profile；所有用途包括新增 plan_self_check 都经同一适配器派发，续接相同工具及会话。未知 Profile 必须拒绝，不通过字符串包含关系静默改成 agy。

验收检查实际子进程 executable/argv、模型选择和会话 ID，不只检查数据库里存入了 Profile 名称。未安装工具须明确阻断，不回退到其他工具执行。

### V08 / P1：Codex 适配器的只读命令参数无效

位置：`packages/adapters/codex/src/adapter.ts`、SDK 的通用 resume。

本机实际执行 `codex exec --read-only --help` 被 CLI 拒绝：unexpected argument '--read-only' found。适配器和通用 resume 会添加该参数；通用追加 --resume 也不能替代各工具自身的续接命令结构。

按当前客户端实际 help/协议生成每个用途的专用命令，并通过已认证的沙箱/权限机制实现只读。只读工具调用不能依赖客户端忽略未知参数。不要以统一拼参数代替各客户端合同。

验收先校验真实 CLI 参数解析，再在临时仓库核对只读不能写、精确会话续接、超时停止和事实事件。--version 成功不能算完整认证。

### V09 / P1：补充的 E2E 仍模拟整个后端，并允许关键操作被跳过

位置：`tests/e2e/devflow-v2-workbench.spec.ts`。

`page.route("**/api/**")` 替换全部 API，在测试内直接把状态改为 EXECUTING；批准和反馈按钮用 isVisible 条件包裹，不可见时直接跳过。测试没有真正驱动规划、执行、质量审查、人工确认和交付；因此不能发现 V01/V02。

保留此类测试时应明确归为界面交互测试。原计划要求的 E2E 必须连接真实隔离后端/数据库/仓库，只替换付费模型外部边界为可控子进程，断言主流程真实副作用及拒绝行为。必需按钮缺失应失败，不可条件跳过。

验收同时覆盖新需求全流程及受影响旧流程；原始报告明确列出实际经过的状态、运行、交付、确认和 Git 结果。不能只统计新增测试文件数量。

### V10 / P1：Git 整合吸收主分支后直接合回，缺少新候选的补测复审

位置：`packages/git/src/delivery-coordinator.ts` 的 executeDelivery。

只在方法开始调用 requireValidDelivery；任务树合入主分支最新提交 S 后，读取新的 finalCandidate，检查主分支没有推进便立即 ff-only 合回，随后清理。中间没有对合入后新代码重新建立测试/自查/质量证据。候选已改变时，合入前的交付不能证明新候选有效。

按原计划持久化“已吸收、待验证”的候选及目标提交 S，先补测和必要复审，再对同一已验证候选合回。目标分支推进则返回重新吸收阶段；所有仓库整合成功前不得清理。禁止吞掉候选提交错误后继续视为成功。

验收构造主分支在开发期间新增与任务有交互的改动，证明合入后的失败会阻止 ff-only 和清理；成功路径必须使用新候选的证据，并验证部分失败后的幂等恢复。此项为源码静态确认，本轮未操作任何真实用户分支。
